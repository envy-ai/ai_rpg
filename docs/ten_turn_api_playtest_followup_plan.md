# Ten-Turn API Playtest Follow-Up Plan

## Governing goal alignment

The purpose of this goal is not to make generated prose technically perfect, force it to contain exactly the information a reviewer expects and nothing else, or achieve 100% factual precision in every sentence. The work must remain aligned with these three outcomes, in priority together rather than treating any one as an absolute:

1. **Prose that flows naturally.** The output should read like a good story continuation. Additional connective, atmospheric, reactive, or character prose is allowed when it helps the story and does not create a material conflict with authoritative actions or state.
2. **Event detection and bookkeeping that stay in sync with prose and player actions.** Structured events, tool outcomes, movement, time, inventory, status, and other persisted state should reflect what materially happened, while the prose should not contradict those authoritative outcomes.
3. **Finding and fixing bugs in prompts and game code.** Testing should expose genuine orchestration, context, parser, prompt-contract, state-mutation, and persistence defects and produce general fixes for those defects.

This goal is explicitly **not benchmaxxing and not passing tests for the sake of passing tests**. Test cases are diagnostic instruments and retained evidence, not the product objective. Do not optimize prompts, fixtures, scenario inputs, assertions, or runtime behavior for the benchmark at the expense of ordinary play. A change is successful only when it improves or protects the real game behavior represented by the case. A green test does not justify overfitting a prompt to its wording, manipulating a fixture to avoid the behavior under test, weakening a meaningful expectation, or adding a special path that works only for the test scenario.

Natural prose is not improved by accumulating a prohibition for every sentence that once failed human review. Every prose rule consumes model attention and can make narration more rigid, literal, or robotic. Do not optimize the prompt for one reviewer's ideal wording, exact detail selection, or one failed generation. A prompt change must address a general prompt-contract defect, not merely make a recorded example come out differently.

Continue human review of every applicable live-model result. When review finds a prose problem, add it to `tmp/prose_issues_log.md` with:

- the scenario/case/attempt and artifact paths;
- the player action, relevant seed/tool result/state, and other lead-up needed to understand it;
- the failing prose verbatim;
- a specific explanation of what is wrong and which governing goal it affects;
- whether the problem is prose-only or exposes a prompt, parser, bookkeeping, or game-code defect;
- whether slower-model routing might help; if so, its expected benefit, prompt frequency, latency cost, and why it should be discussed rather than applied immediately.

A prose-only imperfection is a review observation, not an automatic instruction to edit a prompt and not automatically a mechanical test failure. Preserve it for joint review in the log. If the prose materially disagrees with the player action, accepted structured event, tool result, or authoritative state, investigate that synchronization failure during the test because it affects the second goal; still record the prose example, but fix the underlying general defect rather than policing its surface wording. Prefer authoritative context, structured parser/domain validation, and game-code invariants for mechanically knowable facts. Before adding or strengthening a free-form prose instruction, assess and record the naturalness cost and why a narrower structural fix cannot solve the problem.

### Goal-aligned decision framework

The guiding principle is: **let the model tell the story; let code own facts and state. Validate what can break the game, and tolerate what merely makes a response imperfect.** Apply that principle through all remaining tests, audits, and fixes:

1. **Be strict about authoritative game state and permissive about storytelling.** Movement, time, ownership, inventory, health, status, tool results, accepted events, and persisted bookkeeping must remain coherent. Word choice, connective detail, atmosphere, emphasis, and other harmless narrative variation remain the model's judgment.
2. **Do not ask the model to repeat an answer the program already knows.** When an exact value, decision, accepted draft, XML wrapper, acknowledgement, or final result can be derived from authoritative state or a prior validated checkpoint, skip that completion and build or carry the result forward in code. Do not compensate for a redundant prompt by retrying until the model reproduces known text exactly.
3. **Prefer a few broad, reusable prompt contracts.** State each genuinely necessary narrative boundary once in the narrowest shared scope and reference it where needed. Do not accumulate checkpoint-specific restatements, exception lists, or restrictions in response to individual human-review examples.
4. **Preserve narrative judgment where the correct answer is not mechanical.** Do not freeze a draft merely because a later draft may choose different actors or details, force a seed to be followed when it no longer makes sense, prescribe one canonical phrasing, or reject harmless elaboration. A plausible alternative is not a defect merely because it differs from the reviewer's preferred version.
5. **Put semantic validation at structured boundaries.** TinyBrain and other structured parsers must reject malformed syntax and unsafe or impossible semantics before mutation. Domain code must enforce mechanical invariants. Do not shift those responsibilities into prose instructions or free-form prose inspection.
6. **Handle harmless duplicates and no-ops without lecturing the prose model.** Where a duplicate or spurious structured event is syntactically valid and can be proven to have no new effect, ignore it at the event/domain boundary rather than adding another prose prohibition or retrying solely for cleanliness. This does not permit ambiguous or unsafe mutation to pass silently.
7. **Protect NPC and narrative agency.** Do not add restrictions that make NPCs passive, prevent them from reacting or taking plausible follow-up actions, or erase useful story material merely to simplify a test's expected output. Player-agency boundaries and authoritative mechanics still apply.
8. **Use human prose review diagnostically.** Preserve the full response, lead-up, authoritative facts, and precise concern in `tmp/prose_issues_log.md`. Look for recurring, general causes before proposing a prompt change. One awkward response is evidence for discussion, not permission to optimize production behavior around that sample.
9. **Do not change model routing on your own.** Human review may identify a prompt that could benefit from the slower, more capable prose model, especially when it is rare and narratively difficult. Record that recommendation in `tmp/prose_issues_log.md` with the prompt family, observed failure, approximate frequency, expected quality gain, expected latency cost, and why a prompt/parser/code fix is not preferable. Do not add a prompt to the slower-model routing list, remove one, or otherwise change model assignment without discussing the specific tradeoff with the user and receiving approval. Almost any prompt could be argued to benefit from the slower model; for common prompts, marginal quality gains can be overwhelmed by large cumulative speed losses.

These rules govern implementation choices as well as test acceptance. A technically cleaner output is not automatically a better game result, and a more capable model is not automatically the right operational choice.

## Non-negotiable rule: do not mechanically police generated prose

> **Do not add regular expressions, keyword checks, dialogue detection, prose classifiers, or chains of `if` statements that try to determine whether free-form generated prose obeyed a narrative instruction.** Do not make a playtest pass by adding application-code heuristics for particular wording seen in a failed generation. Those checks are brittle, overfit individual responses, and produce false positives.
>
> Enforce syntax and mechanically knowable semantics only in parsers for explicitly structured outputs. Guide free-form prose through prompting, and record prose-quality or instruction-following problems in `tmp/prose_issues_log.md` for later joint review. A prose expectation in this plan is not authorization to turn that expectation into a regex, ad hoc content validator, or a new prompt prohibition tailored to one response.
>
> **This rule applies to every automated assertion and every proposed implementation fix in this document.** A prose or dialogue defect may fail human review, but must never be converted into executable wording detection. Automated pass/fail decisions must come from structured model output or authoritative game state.

## Test-run contract

### Runtime and isolation

1. Start from one named baseline manual save and record its player, location, world time, inventory, party, quests, currency, needs, status effects, and faction standings.
2. Start the game outside the sandbox with the qwen-combo-router configuration plus a temporary override under `tmp/` that disables image generation. Do not pass a save on the startup command line; load the baseline through the normal API after startup. Enable only the background systems required by the current scenario.
3. Maintain one WebSocket client for the entire request. It must record prompt progress, answer `quest_confirmation_request`, and answer forced `player_input_request` rolls when a case calls for `<f>`.
   The API harness must use a local HTTP transport without a client-side response deadline: a complete turn can legitimately take more than five minutes when several prompt families and model swaps run in sequence.
4. Run only one scenario on a loaded fixture. Restore the scenario fixture before every success, failure, cancellation, or edge-case variant.
5. Never use an earlier scenario's mutated world as the next scenario's starting state.
6. If a prompt, parser, bookkeeping step, or game-code operation fails, preserve its response JSON and prompt/error logs, stop the game server, make and document the smallest general fix, restart from the latest pre-case autosave, and replay the exact case. If human review finds a prose-only issue, record it in `tmp/prose_issues_log.md`; do not stop the defect loop or edit the prompt solely to make that individual prose sample pass.

### Standard `@@` fixture protocol

`@@` setup messages are generic tool-bearing prompts. They are allowed to create or update test fixtures, but they are not the behavior under test unless a case explicitly says otherwise. Prefix each setup request with this contract:

```text
@@ QA FIXTURE SETUP ONLY. Use game tools to perform exactly the requested setup. Do not advance time, move the player, start combat, award rewards, or write story prose. Do not create anything not requested. At the end, report every canonical created or changed entity name and ID, grouped by entity type, and report any requested operation that did not succeed.
```

After every setup command:

1. Inspect `toolInvocations` and reject a fixture with any unsuccessful or unrequested mutation.
2. Resolve canonical IDs using `GET /api/player`, `GET /api/players`, `GET /api/locations`, `GET /api/regions`, and `GET /api/things` as applicable. Requested names are hints; generated canonical names and returned IDs are authoritative.
3. Validate location membership, ownership, containment, health, hostility, party state, and flags before testing.
4. Save the validated fixture under a scenario-specific name. Do not repair setup drift during the behavioral case.

### Evidence required for every case

Store artifacts under `tmp/followup-api-playtest/<scenario>/<case>/`:

- request body and response JSON;
- relevant before/after API snapshots;
- the logical prompt log path and any parser/tool error logs;
- event-summary, check-results, tool-call-debug, and visible prose entries for the turn;
- world time and `timeProgress` before and after;
- a short assertion report listing each pass/fail condition;
- for UI-visible cases, Playwright screenshot, rendered visible text/state, and console/page errors.

A case does not pass merely because it returned HTTP 200. Its mechanical state, structured event summaries, time, persistence after save/reload, and absence of duplicate effects must satisfy the case contract. Human review must also compare the prose with the player action and authoritative outcomes. A material prose/action/state contradiction is a synchronization failure to investigate; a stylistic imperfection, harmless extra story detail, or non-ideal wording is logged for later review and does not by itself redefine the case contract.

### Configuration variants

Create a separate temporary override for each row instead of editing the shared qwen-combo-router configuration:

| Variant | Required differences from the normal no-image fixture |
| --- | --- |
| Default isolated | Image generation off; random events off; ordinary and combat NPC turns off unless the case explicitly needs them. |
| Combat | `combat_npc_turns.enabled: true`, deterministic friendly/hostile limits, ordinary `npc_turns.enabled: false`. |
| Quest | `quest_checks.enabled: true`, `quest_checks.interval: 1` except the acceleration case, and confirmations handled by the active WebSocket client. |
| Long time/WYWA | Small explicit WYWA threshold, random events off, and scheduled events enabled through their normal runtime path. |
| Random event | Only the selected random-event category enabled with a deterministic always-run frequency; unrelated categories disabled. |
| Relationship housekeeping | Small explicit housekeeping interval when testing parsed relationship add/update/remove output. |

Record the effective `/api/config` or equivalent runtime configuration with every scenario so a pass is reproducible.

## Automated regression gate after a fix

After fixing a discovered defect:

1. Run syntax checks for every altered JavaScript file.
2. Use `rg --files tests` to select the focused suites for the affected subsystem; include parser, API, model, and UI tests when those layers changed.
3. Rerun the live case from its saved fixture.
4. Rerun all other cases in that scenario that share the changed path.
5. Run the TinyBrain runner/parser/event suites whenever a staged prompt, parser, or event application rule changed.
6. Run the browser test and inspect screenshots whenever player-visible rendering changed.
7. Update this document by checking off only cases that passed mechanically, narratively, after persistence, and without new console/server errors.
