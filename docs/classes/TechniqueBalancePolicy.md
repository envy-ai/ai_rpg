# TechniqueBalancePolicy

`TechniqueBalancePolicy.js` compiles ordinary self/single-target healing and optional standard damage from engine-owned policy. `resolvePolicy(config)` reads `techniques.balance` and captures the numeric `baseWeaponDamage` reference (5 by default); `validatePolicy(policy)` rejects malformed versions, unknown fields, nonfinite/negative coefficients and invalid resource/improvement rules. A missing policy uses the shipped defaults, including older configurations. A present policy retains its existing required fields. Historical policies may omit the newly introduced damage section; resolution supplies independent shipped damage defaults, while saved healing snapshots remain unchanged. Configuration cannot set the derived `referenceBaseWeaponDamage` field.

The default healing formula is `round(2 * B + 3 * level + skill + 0.5 * attribute_modifier)`. The default cost is `ceil(100 / (1 + 0.05 * skill + 0.02 * level))`. Selected skills and attributes must exist on the actor; canonical identifiers come from `TechniqueFormulaVariables.keyFor`. Level and rank must be nonnegative and the evaluated denominator must be finite and positive. Effects must be finite and nonnegative. No clamping is added.

At B=5, level=3 and attribute modifier=4, ranks 3/5/7/10 produce healing 24/26/28/31 and costs 83/77/71/65. The default efficiency step multiplies base cost by 0.9, producing 75 cost at rank/level 3; the default power step adds 2 healing without changing cost. These are initial calibrated targets, not a guarantee of exactly two enemy hits across every matchup.

`materializeRevision(raw, { actor, origin, config, policy })` accepts a canonical `recipe: { recipeId: "standard-healing", skillName, attributeName, resourceProfileId, effectId? }`; `effectId` defaults to `restore`. Recipe proposals omit numeric costs/effects, `failureCosts` and `balance`. The compiler supplies one healing effect and one configured need cost. Self/single targets are supported; area/mixed/multiple-effect healing and explicit failure vectors reject. Existing requirements/checks are preserved. `materializeDefinition` applies this contract to each revision, and `validateRecipeProposal` checks the strict canonical recipe DTO independently.

The default resource profile `mana` explicitly selects active need ID `mana`, direction `decrease` and capacity `max - min = 1000`. Selecting a missing/inactive pool, conflicting direction or different capacity throws an exact profile/pool error. Other resource profiles require deliberate configuration; no pool is guessed, created or resized. Unavailable profiles are omitted from authoring options without preventing unrelated actors/settings from loading.

Authoring validation identifies eligible selector values when a choice is ambiguous, and explains when the actor has no offered facts/resources for a recipe. Profile errors retain the pool/direction/capacity mismatch and direct selection toward compatible offered profiles. Recipe errors explain supported target/check choices and engine-owned mechanics; automatic healing continues to require its recipe and deliberate custom nonhealing mechanics remain supported.

Compiled revisions contain `balance: { schemaVersion, recipeId, policy: { version, digest, snapshot }, selections, parameters }`. Snapshots contain only the selected recipe’s healing or damage coefficients, captured B, selected resource profile and allowed improvement rules. Selections include actual skill/attribute names, profile/need IDs and stable effect ID. Parameters contain base cost, cumulative healing bonus and ordered applied step IDs. SHA-256 uses canonical JSON keys. Actor level/ranks/modifiers remain dynamic formula inputs rather than saved scalar mechanics.

`validateManagedRevision(revision, actor?)` verifies strict metadata, snapshot digest, step-derived parameters and exact canonical costs/effects without consulting live configuration. With an actor it also checks selected facts, active pool/capacity, positive denominator and resolved effects. Saved revisions therefore retain their policy across reloads. Domain normalization validates present metadata throughout histories and receipts; absent historic metadata remains valid.

New automatic full managed revisions must match the current authoring policy and contain no pre-applied improvements. Automatic unmanaged healing rejects even if its provenance claims `editor`. Trusted callers must explicitly pass `origin: "editor"` to author custom mechanics. Existing catalogue matching/loading/use remains compatible with historic custom formulas.

`compilePersonalImprovement({ learned, proposal: { stepId, reason? }, actor })` uses the owner's saved snapshot and appends a configured efficiency/power step. Evidence and operation receipts are owned by `TechniqueService`. Automatic managed improvements must use this DTO rather than arbitrary full mechanics.

`getAuthoringContext({ actor, policy })` exposes bounded recipe/profile options, actual formula facts, current step options. Selected numeric previews use the existing server preview API. This projection does not expose unrelated configuration. Learned source context separately exposes the owner's saved improvement steps and applied IDs.

## Semantic authoring and standard damage

Model-authored `recipe` objects select `kind: "healing"` or `kind: "damage"` and actual `skillName`, `attributeName`, `resourceProfileId` only where a choice exists. `validateAuthoringRecipeProposal` accepts this envelope and consistent voluntarily supplied canonical `recipeId`/`effectId`; contradictory kind/ID pairs reject. `resolveAuthoringRecipeProposal(proposal, { actor, policy })` fills exactly-one eligible selections and known recipe/effect identities. No eligible option or an omitted ambiguous choice throws; there is no best-skill inference or resource fallback. Direct `validateRecipeProposal` and compiler/editor DTOs retain their canonical contract.

`compileDamageRecipe` uses independent `damage.standard` coefficients, initially equal to the shipped healing coefficients, and the selected existing resource profile’s cost formula. It emits one `damageMode: "technique"` effect, with default effect ID `strike`; healing retains `restore`. Standard damage requires an explicit self/single target and nonautomatic check. It does not add ordinary weapon damage or supply a difficulty. Deliberate custom damage remains supported even when a recipe is available, including existing free/health/need costs, automatic checks where valid, area and mixed effects. Selecting a standard recipe never silently converts an invalid proposal into custom mechanics.

Damage snapshots carry `damage` coefficients and `damageBonus`; old healing snapshots/digests retain their original shape and `healingBonus`. Both use immutable saved snapshots for installed revisions and personal improvements. The full actor-aware context exposes available recipe kinds; the compact shared recipe catalogue remains identical for actors with the same policy, while actual eligible resource profiles are actor-specific.

Recipe shape, kind/ID consistency, optional populated values and actor skill/attribute/resource selection errors share the [ten-issue collector](ResponseValidation.md). For example, ambiguous omitted skillName and attributeName are reported together; malformed effectId can accompany those independent selector failures. Invalid populated selectors retain actual actor choices or the original resource-profile mismatch guidance. Compilation aggregates independent actor fact/resource checks and rejects before constructing managed mechanics; it does not choose replacement facts or pools. Policy configuration and dependent managed-snapshot checks remain strict and may fail first.
