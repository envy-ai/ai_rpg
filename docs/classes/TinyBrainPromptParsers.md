# TinyBrainPromptParsers

`TinyBrainPromptParsers.js` contains side-effect-free parsers for staged prompt checkpoints and final responses. Every returned value is JSON-serializable so `TinyBrainPromptRunner` can retain it in render state without carrying DOM nodes or game objects. XML parsers use [TinyBrainXmlResponse](TinyBrainXmlResponse.md) with their known root names to accept surrounding commentary or Markdown fences around the final expected XML envelope, including self-closing roots. They then return the extracted XML as `normalizedResponse` where applicable; empty-root permission and all strict structural/mechanical validation remain unchanged. A malformed or incomplete final expected envelope fails rather than selecting an earlier valid response or an inner child. Comments, CDATA, quoted attributes, and matched single/double-backtick inline tag mentions outside an active XML envelope cannot supply fake envelopes. Fenced XML remains eligible, and XML content inside an active envelope retains strict validation. Plain-prose and scalar contracts retain their existing behavior.

`getTinyBrainParserOutputContract(parser, parserArgs = [])` returns the function's
generation contract: `{ xmlOutput: true, expectedXmlRootTags: [...] }` for XML,
`{ xmlOutput: false }` for plain/scalar/prose output, or `{ xmlOutput: "auto" }`
for an unregistered custom function. Built-in XML extraction and the runner's
live guard use the same registered roots. Exact-root contracts derive their root
from parser arguments; turn narratives derive their allowed roots from
`allowTravel`. Delegating/staged XML parsers also carry their own contract.
Scheduled-event tool execution validates a plain completion receipt and remains
plain; it does not require an invented XML wrapper.

`defineTinyBrainParserOutputContract(parser, contract)` registers reusable function
metadata and returns that parser. `resolveTinyBrainOutputContract(contract, args)`
normalizes a descriptor or a resolver called with `...args`. Descriptors accept
`xmlOutput` and either `expectedXmlRootTag` or `expectedXmlRootTags`, using the
same names as LLMClient. Root declarations imply XML when `xmlOutput` is omitted;
plain output cannot declare roots. Invalid descriptors fail explicitly. The runner
also accepts local custom/checkpoint and final-model contracts without globally
registering functions; see [TinyBrainPromptRunner](TinyBrainPromptRunner.md).

Regular non-legacy TinyBrain player actions register
`player_action_resolution_plan` from
[PlayerActionResolutionPlan](PlayerActionResolutionPlan.md). This stricter
attribute-free plan parser accepts ordered mixed checks and attacks, validates
all action fields before execution, and returns JSON-safe resolver inputs.
The server's post-parse hook supplies authoritative results; malformed plans
retry the same checkpoint, and a known partial-execution failure requests only
the remaining unexecuted suffix.

Need-bar character responses, quest reward coverage, WYWA character updates and grouped item/scenery moves collect up to ten independent issues through [ResponseValidation](ResponseValidation.md). The combined WYWA final collects errors from its independent sections as well. Field and record context distinguish sibling failures; dependent checks, such as magnitude/direction combinations and indexed reward matching, run only with valid prerequisites. Partial values remain local and every parser throws before accepting an invalid response. Other checkpoint families and malformed XML/root boundaries retain their existing fail-fast behavior.

Optional XML fields accept omission where their existing empty or `N/A` form has the same no-value meaning. `optionalSingleDirectChild` retains strict single-child validation, so duplicates and invalid supplied values still fail. Empty optional scalar leaves, including whitespace-only and self-closing leaves, use the same text value as omission; nested objects/lists retain their own validators. The audited cases are container-check modifier lists and unused skill/attribute selectors, scene details, location-modification effect text, WYWA update/item/need-change lists and no-change need values, and scheduled-plan direct-update/tool lists. Omitted or blank unused selectors and need values normalize to `N/A`. Each check still needs a meaningful skill or attribute for each actor. An affected-need-bar character still requires an actual changed bar. Required roots, names, decisions, durations, outcomes and nonempty narration remain strict. See the [omission audit](../superpowers/plans/2026-10-30-optional-xml-field-audit.md).

WYWA staged comparisons treat missing empty need-change containers and `N/A`/omitted/blank-value no-op effects equivalently. Missing whole update/item lists still cannot discard staged nonempty updates or moved items: count, identity and numeric-value comparisons remain enforced.

Generic parsers cover revision decisions, allowlisted character selections, narrative travel scope, exact XML roots, and exact outcome acknowledgements. Exact-root checkpoints reject empty roots by default and accept them only through the explicit `allowEmptyRoot` option; while-away item/scenery moves enable that option when nothing moved. Additional reunion selection accepts an empty selectedCharacters list; an empty roster skips selection locally. Outcome acknowledgements remain available for families that genuinely need them, but craft no longer asks the model to repeat server-rendered facts. Domain parsers validate quest-reward coverage, game-intro XML, turn/move prose, craft/location results, checked-container plans/results, while-away updates, scheduled-event applicability/tool plans/tool execution/summaries/results, and scheduled-event interruption rewrites. The checked-container plan parser accepts exactly one `<containerOpenCheck>` with either an unopposed difficulty or an opposed character and resistance pairing. It validates the skill/attribute selections, difficulty enum, integer circumstance modifiers, and type-specific fields before server code invokes the matching resolver. Circumstance amounts accept a single leading `+` or `-` and retain safe-integer checks. While-away need-bar percentages also accept a leading `+` while retaining their finite 0–100 bounds; reference indices retain their existing digit-only syntax. Scheduled-event applicability requires one `<applicability>` root containing exactly one `yes`/`no` `<decision>` and one nonempty `<reason>`. Its `<toolPlan>` parser does not require the raw event or event value to be copied. It derives whether state changes are present instead of asking the model for that flag, accepts one exact id-or-name reference per direct update instead of two alternatives, and omits unused purpose prose from calls whose exact name and JSON arguments are already known. It validates supported object types/fields, parseable JSON, available tool names, and semantic argument contracts that ordinary JSON `required` lists cannot fully express. In particular, if an available tool list includes `editChatLogEntry`, a planned call must contain nonempty replacement content plus either a nonempty string `entry` reference or a zero-based non-negative integer `index`. The scheduled-event runtime itself excludes that generic-prompt-only Story Tool. Identical direct updates or other calls are collapsed while conflicting updates to the same target field fail. The execution parser remains available to validate a supplied server-execution transcript, but the current scheduled-event program uses the runner's post-parse hook to execute the accepted plan and feeds any tool failure back into the plan checkpoint directly. A scheduled-event summary checkpoint requires one text-only `<summary>` root and rejects empty or explicit null-sentinel answers.

The need-bar characters parser accepts `<characters>` results with optional surrounding commentary, permits an empty root when no bar changed, and validates every affected-character block. It rejects unknown configured need-bar ids, duplicate characters or bars, missing fields, invalid direction/magnitude keywords, directionally impossible `decrease/full` or `increase/empty` pairs, and unexpected elements. The harmless structured aliases `fill` and `drain` normalize to canonical `full` and `empty`, respectively. The prompt still asks for reasons of ten words or fewer to discourage paragraphs, but reason length is not parser-enforced and cannot fail a turn.

Scene-summary parsing is split across two strict contracts. `parseSceneSummaryBoundaries(...)` requires one `<sceneBoundaries>` root containing at least two exact `<boundary><index/><reason/></boundary>` children; indices must be positive, within the supplied indexed-history length, unique through strict ascending order, and paired with nonempty text-only reasons. `parseSceneSummaryEntry(...)` requires one `<scene>` for the exact assigned start/end interval, rejects a changed start index or unexpected/nested fields, requires nonempty summary text, treats omitted details as an empty list, normalizes detail bullet lines, and accepts at most two exact structured quotes. Both return JSON-safe data and normalized XML, so a malformed proposal, correction, or individual scene retries without discarding accepted earlier stages.

The TinyBrain player-action terminal uses compact non-XML parsers for pre-draft destination names, movement, state-dependent vehicle decisions, prose scopes, location/region destinations, destination-change planning, exact durations, accompanying characters, required prose, optional hidden notes, and time reasoning. It also has a structured hidden-contest parser for server-owned reveal/hide mechanics. That parser accepts an empty `<hiddenContests/>` or exact `<contest>` children, resolves complete canonical names and aliases against a server-supplied local roster, and permits only player-versus-hidden-NPC reveal attempts or visible-NPC-versus-player hide attempts. It rejects malformed/nested fields, unsupported actions, unknown or ambiguous identities, wrong actor/opponent roles, invalid current visibility, and duplicates before any roll occurs. The API then resolves accepted contests with the configured perception/hiding skills and attributes—including an injected test/player roll—and places those authoritative results back into later prompt stages. The model is not required to repeat the plan through a check tool.

Unambiguous choice answers tolerate `Answer:`, outer emphasis, and trailing sentence punctuation. The pre-draft destination-name parser accepts exactly one location-name line or `N/A`, harmlessly normalizes an optional Markdown bullet, `Location:` label, or matching quotes, rejects XML/multiple lines, and rejects any current-checkpoint tool invocation. Prose scopes accept commas, semicolons, newlines, or `and`, canonicalize their order, and deduplicate repeated choices. Destination lines may be ordered either way and may use Markdown bullets. Revisit-change planning accepts exact `NONE`/`N/A` or a Markdown bullet list; it rejects headings, surrounding prose, numbered lists, XML, mixed sentinels, empty bullets, and normalized duplicate bullets. The prompt requests brevity, but the parser deliberately does not enforce a character limit. Accompanying characters use exact canonical-name/alias selection and return canonical names; partial names, unknown/ambiguous identifiers, and duplicate selections remain errors. Player-action no longer predeclares or freezes a general checked-actor roster before drafting; the hidden-contest roster is scoped only to the server-owned hide/reveal checkpoint. Duration parsing reuses `Utils.parseDurationToMinutes()` and validates minimum/integer constraints without clamping. The normal-turn time-passed checkpoint alone supplies the captured player-action world minute, enabling validated `until` clock targets while travel and vehicle duration checkpoints remain relative-only. Builder-bound prose drafts and revisions ordinarily use the required-prose parser; optional while-you-were-away drafts and their audit-requested revisions use the optional-prose parser, which maps exact `N/A` to `null`; bare arrivals without other narration continue to use required prose for both drafts and revisions. XML markup at either prose-only checkpoint is rejected and retried before a local result builder can treat it as approved prose. Ordinary comparison text such as `less than < two` remains valid because it is not XML markup. Hidden-note parsers continue to reject result wrappers and hidden wrappers so the model cannot bypass staged control flow.

Required prose rejects a whole-response `N/A` sentinel using the same case-insensitive presentation normalization as optional prose, rather than treating it as meaningful narration. Real prose that contains `N/A` within a sentence remains valid. This applies to required drafts and audit revisions, including bare WYWA arrivals.

The higher-risk parsers enforce cross-stage invariants:

- quest reward coverage must have every original index exactly once and can be checked against the original reward strings;
- craft and location-modification output must resolve to the mechanically selected duration, while equivalent duration wording is accepted;
- a container final must correspond to exactly one successful resolver invocation (native in the one-shot path or server-executed from a TinyBrain plan), name that resolver, agree with its authoritative success value, prevent permanent opening on failure, and contain a parseable duration;
- each while-away candidate checkpoint must use the candidate's exact name and canonical `<name>`, `<needBarChanges>`, optional structured `<travelDestination>`, and required `<update>` fields; need-bar values must be `N/A` or percentages from 0 through 100. Additional reunion names first use `allowed_character_selection` against the supplied eligible existing-NPC roster, with zero selections allowed. Each selected name then receives one `while_away_arrival_update` checkpoint. `parseWhileAwayArrivalUpdate(response, expectedName)` delegates to `parseWhileAwayCharacterUpdate(response, expectedName, { requireHere: true })`, sharing its canonical field/need-bar validators while additionally requiring literal `HERE`. The pure grouped `parseWhileAwayArrivalUpdates` validator remains available for canonical grouped XML, but the staged program uses individual updates. The combined final validator accepts omitted or trimmed-empty `<proseForPlayer>`, accepts the exact `HERE` sentinel alongside ordinary structured destinations, but rejects duplicate player-prose elements, arbitrary destination text, and mixed text-plus-child destinations. It also rejects nested structured wrappers or changes to staged character updates, arrivals, or item/scenery moves, while permitting harmless reordering of character and item/scenery entries;
- a scheduled-event final must preserve its approved hidden summary and omit player prose for offscreen events (an empty optional proseForPlayer leaf has the same meaning as omission);
- an interruption rewrite may change player-facing prose fields only; its root, hidden notes, time data, travel destinations, vehicle data, and every other non-prose XML field must remain equivalent.

Malformed XML, unknown values, missing required fields, conflicting duplicates, and invariant drift throw descriptive parser errors. Safe exact duplicates that cannot add state may instead normalize away at their domain boundary. The runner retries the same checkpoint without applying domain mutations. Terminal XML that contains no remaining model judgment is assembled by `TinyBrainResultBuilders.js`; API consumers still run their ordinary downstream domain parser before applying it. The remaining semantic hardening backlog and the explicit decision to skip heuristic prose-to-fact validation are recorded in `docs/tinybrain_parser_hardening.md`.

Interactive player-action vehicle destinations set `currentVehicle.routeRecoveryAvailable`: syntax, canonical context, ambiguity, and retry anchoring remain validated, but an off-route answer is preserved for the shared [TurnEventRecovery](TurnEventRecovery.md) modal at the movement boundary. Acceptance relocates characters as a time-skip without altering the vehicle route. Non-interactive prompts retain strict early route rejection. New-location region-name validation runs before fixed-route retry anchoring; its vehicle-specific feedback offers region travel or a different destination, while preserving the existing fixed-route locks and recovery semantics.

`parsePlayerActionDestinationDecision(response, options)` parses the mechanical player destination checkpoint as `<playerDestination><decision>travel|stay</decision><location>...</location><region>...</region></playerDestination>`. `travel` requires at least one populated destination field; `stay` forbids populated destination fields. Omitted, self-closing, empty, whitespace-only and `N/A` location/region fields all mean no supplied value. Nested fields, unknown children, duplicate fields and unsupported decisions reject with repair guidance. A travel answer then runs [PlayerActionDestinationContext](PlayerActionDestinationContext.md)'s read-only creation-name validation before acceptance. A new location colliding with a live or pending region receives short feedback naming the conflict and offering region travel, a different location, or staying. This decision retries locally and returns `{ decision, destination }`; the pre-draft name lookup remains advisory and generic/vehicle destination parsers retain their existing compact two-line contract.

Production also passes the captured `originLocationId` in that options object.
Travel resolving to the same canonical location is rejected at this checkpoint,
before vehicle selection and final prose, with the location name/ID and exact
`<playerDestination><decision>stay</decision></playerDestination>` alternative.
The shared normalized/pending-aware lookup catches spelling variants of that
same identity without fuzzy matching. Unknown new destinations remain possible,
and zero-minute routes to distinct locations remain valid. Earlier accepted
drafts, checks and tool outcomes are not replayed when this decision retries.

Shared field errors distinguish missing, duplicate, empty and unexpected fields and give the specific repair. See the [18-family validation audit](../superpowers/plans/2026-11-01-tinybrain-validation-guidance.md) for the reviewed checkpoint and final-parser boundaries.

Staged WYWA and scheduled-interruption invariant failures also identify the differing XML path and ask the model to restore the accepted field/block. The comparison and accepted-value rules are unchanged; locating the difference only improves rejected-response feedback.
