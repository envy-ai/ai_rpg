# TinyBrainPromptParsers

`TinyBrainPromptParsers.js` contains side-effect-free parsers for staged prompt checkpoints and final responses. Every returned value is JSON-serializable so `TinyBrainPromptRunner` can retain it in render state without carrying DOM nodes or game objects. XML parsers accept a single final complete XML block surrounded by commentary or an `xml` Markdown fence, then return the extracted XML as `normalizedResponse`; malformed or ambiguous mechanical content still fails.

Generic parsers cover revision decisions, allowlisted character selections, narrative travel scope, exact XML roots, and exact outcome acknowledgements. Exact-root checkpoints reject empty roots by default and accept them only through the explicit `allowEmptyRoot` option; while-away arrivals and item/scenery moves enable that option because their prompts require empty roots when nothing changed. Outcome acknowledgements remain available for families that genuinely need them, but craft no longer asks the model to repeat server-rendered facts. Domain parsers validate quest-reward coverage, game-intro XML, turn/move prose, craft/location results, checked-container results, while-away updates, scheduled-event applicability/tool plans/tool execution/summaries/results, and scheduled-event interruption rewrites. Scheduled-event applicability requires one `<applicability>` root containing exactly one `yes`/`no` `<decision>` and one nonempty `<reason>`. Its `<toolPlan>` parser does not require the raw event or event value to be copied. It derives whether state changes are present instead of asking the model for that flag, accepts one exact id-or-name reference per direct update instead of two alternatives, and omits unused purpose prose from calls whose exact name and JSON arguments are already known. It validates supported object types/fields, parseable JSON, available tool names, and semantic argument contracts that ordinary JSON `required` lists cannot fully express. In particular, if an available tool list includes `editChatLogEntry`, a planned call must contain nonempty replacement content plus either a nonempty string `entry` reference or a zero-based non-negative integer `index`. The scheduled-event runtime itself excludes that generic-prompt-only Story Tool. Identical direct updates or other calls are collapsed while conflicting updates to the same target field fail. The execution parser remains available to validate a supplied server-execution transcript, but the current scheduled-event program uses the runner's post-parse hook to execute the accepted plan and feeds any tool failure back into the plan checkpoint directly. A scheduled-event summary checkpoint requires one text-only `<summary>` root and rejects empty or explicit null-sentinel answers.

The need-bar characters parser accepts XML-only `<characters>` results, permits an empty root when no bar changed, and validates every affected-character block. It rejects unknown configured need-bar ids, duplicate characters or bars, missing fields, invalid direction/magnitude keywords, directionally impossible `decrease/full` or `increase/empty` pairs, and unexpected elements. The harmless structured aliases `fill` and `drain` normalize to canonical `full` and `empty`, respectively. The prompt still asks for reasons of ten words or fewer to discourage paragraphs, but reason length is not parser-enforced and cannot fail a turn.

The TinyBrain player-action terminal uses compact non-XML parsers for movement, state-dependent vehicle decisions, prose scopes, location/region destinations, destination-change planning, exact durations, accompanying characters, required prose, optional hidden notes, and time reasoning. It also has a structured hidden-contest parser for server-owned reveal/hide mechanics. That parser accepts an empty `<hiddenContests/>` or exact `<contest>` children, resolves complete canonical names and aliases against a server-supplied local roster, and permits only player-versus-hidden-NPC reveal attempts or visible-NPC-versus-player hide attempts. It rejects malformed/nested fields, unsupported actions, unknown or ambiguous identities, wrong actor/opponent roles, invalid current visibility, and duplicates before any roll occurs. The API then resolves accepted contests with the configured perception/hiding skills and attributes—including an injected test/player roll—and places those authoritative results back into later prompt stages. The model is not required to repeat the plan through a check tool.

Unambiguous choice answers tolerate `Answer:`, outer emphasis, and trailing sentence punctuation. The destination lookup parser accepts a response beginning with `N/A`/`NA` only when the current checkpoint made no successful tool call, and a response beginning with `READY` only after at least one successful current-checkpoint `moreInfo` call. Any trailing text is discarded through `normalizedResponse`; other tools, failed calls, or choices inconsistent with the tool record still fail. Prose scopes accept commas, semicolons, newlines, or `and`, canonicalize their order, and deduplicate repeated choices. Destination lines may be ordered either way and may use Markdown bullets. Revisit-change planning accepts exact `NONE`/`N/A` or a Markdown bullet list; it rejects headings, surrounding prose, numbered lists, XML, mixed sentinels, empty bullets, and normalized duplicate bullets. The prompt requests brevity, but the parser deliberately does not enforce a character limit. Accompanying characters use exact canonical-name/alias selection and return canonical names; partial names, unknown/ambiguous identifiers, and duplicate selections remain errors. Player-action no longer predeclares or freezes a general checked-actor roster before drafting; the hidden-contest roster is scoped only to the server-owned hide/reveal checkpoint. Duration parsing reuses `Utils.parseDurationToMinutes()` and validates minimum/integer constraints without clamping. Every builder-bound prose draft and optional revision uses the required-prose parser; XML markup at a prose-only checkpoint is rejected and retried before a local result builder can treat it as approved prose. Ordinary comparison text such as `less than < two` remains valid because it is not XML markup. Hidden-note parsers continue to reject result wrappers and hidden wrappers so the model cannot bypass staged control flow.

The higher-risk parsers enforce cross-stage invariants:

- quest reward coverage must have every original index exactly once and can be checked against the original reward strings;
- craft and location-modification output must resolve to the mechanically selected duration, while equivalent duration wording is accepted;
- a container final must correspond to exactly one successful check-tool invocation, name that tool, agree with its authoritative success value, prevent permanent opening on failure, and contain a parseable duration;
- each while-away candidate checkpoint must use the candidate's exact name and canonical `<name>`, `<needBarChanges>`, optional structured `<travelDestination>`, and required `<update>` fields; need-bar values must be `N/A` or percentages from 0 through 100. Arrival checkpoints additionally require literal `HERE`. The combined final validator accepts that exact text sentinel alongside ordinary structured destinations, but rejects arbitrary text and mixed text-plus-child destinations. It also rejects nested structured wrappers or changes to staged character updates, arrivals, or item/scenery moves, while permitting harmless reordering of character and item/scenery entries;
- a scheduled-event final must preserve its approved hidden summary and omit player prose for offscreen events;
- an interruption rewrite may change player-facing prose fields only; its root, hidden notes, time data, travel destinations, vehicle data, and every other non-prose XML field must remain equivalent.

Malformed XML, unknown values, missing required fields, conflicting duplicates, and invariant drift throw descriptive parser errors. Safe exact duplicates that cannot add state may instead normalize away at their domain boundary. The runner retries the same checkpoint without applying domain mutations. Terminal XML that contains no remaining model judgment is assembled by `TinyBrainResultBuilders.js`; API consumers still run their ordinary downstream domain parser before applying it. The remaining semantic hardening backlog and the explicit decision to skip heuristic prose-to-fact validation are recorded in `docs/tinybrain_parser_hardening.md`.
