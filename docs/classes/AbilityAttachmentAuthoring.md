# AbilityAttachmentAuthoring

`generateAbilityAttachmentDraft({ actor, abilityId, config, setting, clientId })` authors mechanics for one **owned** ability. The model returns a fully nested XML `<abilityAttachments>` response. `buildAbilityAttachmentPrompt` supplies the inline XML instructions for both standard and TinyBrain configuration; it does not include the JSON candidate examples used by other prompt families. The parser validates XML structure and scalar types, permanent duration, unsupported ability need-bar deltas, shared automatic technique candidate/discipline rules, and the entire detached proposal through `TechniqueService.previewAbilityAttachmentBatch`. Every attempt, including corrections and transport failures, is logged through `LLMClient.logPrompt`; transport/cancellation errors propagate. XML and domain errors share the existing configured correction budget and exact-error feedback; changing response syntax does not add a retry boundary.

The authoring request places common actor, setting and catalogue context in one user message before a final ability-specific user message, and omits artwork fields from the latter. Consecutive abilities for an unchanged actor/world can therefore share a longer prompt prefix with providers that cache one; no latency reduction is assumed where the provider does not cache it.

The response uses child elements only, with no attributes or JSON payloads. Object fields occur at most once, unknown fields and text outside child fields reject, and scalars contain text only. Numbers must be finite decimal/scientific-notation text; empty values, units, hexadecimal, `NaN` and `Infinity` reject. Booleans must be exactly `true` or `false`. Existing domain validators enforce integer and range requirements after parsing. Text must XML-escape `&` and `<`. Empty lists use self-closing containers; an explicitly empty `<statusEffects/>` is accepted when the ability has no supported mechanics. There is no legacy JSON-response fallback.

```xml
<abilityAttachments>
  <statusEffects>
    <statusEffect>
      <name>Steady practice</name>
      <description>Unconditional improvement from the owned ability.</description>
      <duration>-1</duration>
      <attributes>
        <attribute><attribute>Strength</attribute><modifier>1</modifier><percentModifier>10</percentModifier></attribute>
      </attributes>
      <skills>
        <skill><skill>Spellcasting</skill><percentModifier>10</percentModifier></skill>
      </skills>
      <maxHealthPercent>10</maxHealthPercent>
      <techniqueEntries>
        <techniqueEntry><techniqueId>existing_technique_id</techniqueId><definitionRevision>1</definitionRevision></techniqueEntry>
      </techniqueEntries>
    </statusEffect>
  </statusEffects>
</abilityAttachments>
```

Names and catalogue identities above are structural examples; authored responses must use actual actor facts. List containers and their children are `statusEffects/statusEffect`, `attributes/attribute`, `skills/skill`, `techniqueEntries/techniqueEntry`, `aliases/alias`, `revisions/revision`, all requirement containers/`requirement`, `costs/cost`, `failureCosts/cost`, `effects/effect`, nested status `needBars/needBar`, and nested status `techniqueGrants/techniqueGrant`. An attribute or skill entry contains its same-named identity child as shown above. Each revision entry contains the numeric field `<revision>1</revision>`. Non-list objects (including `candidate`, `candidateDiscipline`, `target`, `check`, `recipe` and nested effect `status`) use the existing DTO field names as child tags. A technique entry chooses a catalogue reference or a complete candidate; a new candidate discipline is its sibling. Server-owned attachment IDs, timestamps and provenance remain excluded.

Numeric technique amounts use direct text, such as `<amount>2</amount>`, or nested `<amount><formula>max(1, level)</formula></amount>`. The same formula shape works for nested technique status modifiers and percentages. Permanent attachment status modifiers and percentages are numeric only. New healing uses a `recipe` containing `recipeId`, `skillName`, `attributeName`, `resourceProfileId` and optional `effectId`; the engine still materializes canonical costs/effects/balance. Nonhealing candidates retain checks, explicit normal/failure cost vectors, requirement lists, effects, per-effect checks, nested status grants, stacking and refresh policies, potency and formula validation. The typed parser also preserves valid existing DTO formula bindings (`bindings/binding` with `variable`, `kind` and optional `name`) and managed balance fields; guidance requests canonical formula variables without bindings and recipe proposals without copied balance metadata. Managed balance `improvementSteps` maps use `improvementStep` children with `id` plus step fields; `appliedImprovementIds` uses `improvementId` children. These parsed DTOs remain subject to the same domain policy checks.

Draft statuses may have fixed and percentage attribute or skill modifiers, `maxHealthPercent`, and nested `techniqueEntries`. Technique entries reference a current catalogue definition or provide a complete technique candidate plus optional new discipline. The shared technique schema, balance policy, resource rules, and formula validation apply. Status-granted techniques remain available only while their source status is active. Conditional targeting, auto triggers, reactions, weapon-based damage, and unsupported utility mechanics are excluded from authoring guidance; a conditional prose claim never becomes an unconditional bonus.

The shared standard/TinyBrain prompt gives a mechanical placement guide. An outer ability status is continuously active on the owner and represents an explicitly permanent, unconditional benefit or drawback. An activated action, including a temporary self buff, uses a technique entry in a permanent grant-only outer status. A grant-only status is complete without numeric modifiers. Its revision selects `self`, `single`, or `area` targets. Direct harm uses a damage effect; a buff or debuff applied on successful use uses a nested effect status on the recipient with a duration in integer world minutes or `-1` for permanent. An ability with explicit ongoing and activated components can use both outer modifiers and a technique. If the ability has no supported mechanical component, the prompt requests an empty `<statusEffects/>`.

This guide steers model authoring; XML and domain validation still check mechanics and structure, not whether the ability prose describes a passive or an attack. Reviewed drafts should be checked for semantic placement before application.

Generation returns `{ draft, expected }` without installing statuses, disciplines, techniques, or grants. `expected` identifies the current game epoch, character, and target ability snapshots (excluding artwork). Ordinary character-state and unrelated catalogue changes do not invalidate generation; current attachment mechanics and references are still validated before application. `authorNewAbilityAttachments` generates every newly accepted ability's draft first, previews the combined batch, then calls the atomic service apply once. Its `draftsByAbilityId` input instead applies already prepared drafts without another model call. Player option generation passes a server-trusted `pendingAbility` to the same XML authoring and read-only preview path; returned pending drafts contain stable proposal IDs and persist separately from the option's inactive `statusEffects`. The chooser displays the saved draft, and selection commits that same draft after validation. Explicit empty `statusEffects` is a complete preview. Loading or probing pending options without `ensureOptionsForNext` does not author drafts; older saved options are enriched only during ordinary ensured generation. Pending and declined cards never install catalogue entries. Initial NPC generation attaches mechanics after gear and quantity expansion and before starting-technique authoring. NPC level-up attaches after adding ability records and before progression allocation, restoring the old ability set if attachment generation fails.

The manual API uses `GET /api/players/:actorId/abilities/:abilityId/attachments` for the current editable draft and baseline, `POST .../generate` for a new staged proposal, and `PUT .../attachments` with `{ draft, expected }` for reviewed application. These internal DTOs and HTTP editor payloads remain JSON; only model-authored response syntax changes. Apply re-previews the edited draft to allocate stable proposal IDs, then commits one transaction against the supplied baseline. A different game or character, or edited target abilities, fails before mutation. See [players API](../api/players.md).
