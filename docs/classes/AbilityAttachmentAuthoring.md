# AbilityAttachmentAuthoring

`generateAbilityAttachmentDraft({ actor, abilityId, config, setting, clientId })` authors mechanics for one **owned** ability. The model returns a fully nested XML `<abilityAttachments>` response. `buildAbilityAttachmentPrompt` supplies the inline XML instructions for both standard and TinyBrain configuration; it shares nested technique XML guidance with first-use and starting-technique families. The parser validates XML structure and scalar types, permanent duration, unsupported ability need-bar deltas, shared automatic technique candidate/discipline rules, and the entire detached proposal through `TechniqueService.previewAbilityAttachmentBatch`. Every attempt, including corrections and transport failures, is logged through `LLMClient.logPrompt`; transport/cancellation errors propagate. XML and domain errors share the existing configured correction budget and exact-error feedback; changing response syntax does not add a retry boundary.

Standard generation uses one queue reservation for two phases per ability. A catalogue lookup first receives actor facts, the ability description and the complete lightweight discipline outline below. It returns strict XML `<techniqueSelections><techniqueId>EXACT_LISTED_ID</techniqueId></techniqueSelections>`; an empty root means no existing detail is needed. Unknown IDs, duplicates, attributes and extra fields reject. A genuinely empty catalogue skips this known-empty lookup. The lookup uses `ability_attachments` model/profile routing with `metadata.phase: catalogue_selection`, and logs attempts/transport failures through `LLMClient.logPrompt` with prefix `ability_attachments_selection`.

With the effective TinyBrain master switch and `ability_attachments` family enabled, `generateAbilityAttachmentDraftBatch({ actor, abilities: [{ abilityId, pendingAbility? }], config, setting, clientId })` processes the complete list sequentially in **one native TinyBrain program**. Its fixed prefix supplies actor/setting/mechanics context and the complete catalogue outline once. Each ability then has a strict selection checkpoint and a strict authoring checkpoint, reusing the existing parsers. The exact selected definitions and latest revision pins are captured when that lookup succeeds. Empty catalogues omit the known-empty selection checkpoint; empty batches return `[]` without a model request. Results are ordered `{ abilityId, draft, expected }` entries. Mixed owned/pending batches and repeated IDs reject explicitly.

The new `_includes/ability-attachments.tinybrain.njk` program shares one queue reservation, progress group and `ability_attachments_tinybrain` prompt log. Parser errors retry only the current checkpoint; accepted earlier answers remain in the conversation. A local terminal builder validates completion without another model request. No native tools or output-token override are added. The current ability description alone establishes its benefits; earlier abilities, authored attachments and lookup choices do not grant benefits to later abilities. `generateAbilityAttachmentDraft` routes a single manual request through a one-entry program. Disabling TinyBrain or this family retains the standard two-phase path.

Owned batches validate each accepted candidate cumulatively against the original combined target baseline projected to the current prefix, then retain the final combined preview and single atomic apply. Pending offered options are mutually exclusive, so each draft has its own baseline and independent detached preview. Later failure/cancellation installs no statuses, disciplines, techniques or grants. Server pending-option preparation calls the batch once and retains its existing promise/persistence lifecycle. `draftsByAbilityId` continues to apply already prepared drafts without generation.

```text
discipline_example ("Example practice"):
  technique_example ("Example technique") - Concise existing technique summary
```

Every catalogue entry appears, without a count limit or truncation. Only its stored short description is used; missing legacy summaries leave the known ID/name alone. The inspected live catalogue had summaries for all 116 definitions; no automatic backfill or full-description substitution is introduced.

The final authoring conversation receives only selected canonical definitions' latest mechanics, rendered as nested XML by `TechniqueSelectionContext`, plus actual actor skills/attribute modifiers/resources, policy/formula facts and discipline choices. Standard authoring keeps the full outline in its separate lookup conversation; TinyBrain retains its one shared outline in the batch transcript without appending another copy during authoring. Actor-owned technique sources are excluded from the authoring projection even when selected, so old source pins and existing large grant lists cannot reintroduce full historical or unselected mechanics. The target ability contains only identity, name/descriptions, type and level; existing status attachments and artwork are excluded. Lookup selection requests information and never itself grants a technique. Only supported capabilities described by the target ability justify a grant.

The authoring phase uses `metadata.phase: authoring` with the same model routing and ordinary configured correction budget. Standard phases retain one native reservation per ability; TinyBrain phases share one reservation across the complete batch, including corrections and nested ownership. Configured independent free concurrency remains available. No output-token budget change, top-K filter or fallback authoring flow is added.

Validation feedback pairs the actual rule with a brief correction at its source. Complex branches explain catalogue references versus new candidates, existing parent `disciplineId` versus new parent metadata, reserved identity fields, permanent owner statuses versus activated technique effect statuses, kind-specific mechanics, formula syntax/variables, and actor-eligible recipe/resource choices. XML schema guards explain misplaced fields before domain parsing; domain wrappers retain the attachment status/entry path, original message and error cause. Diagnostics do not classify error text, guess repairs, relax validation, or change correction retries. See the [validation audit](../superpowers/plans/2026-10-31-ability-attachment-validation-guidance.md) for coverage and preserved behavior.

The typed decoder, discipline entries and pure status/candidate checks collect up to ten distinct actual problems per rejected response using [ResponseValidation](ResponseValidation.md), with numbered shared correction feedback. Checks within one candidate/revision can contribute multiple issues. Invalid partial drafts never reach preview. The final actor-aware `previewAbilityAttachmentBatch` runs once after pure validation succeeds and aggregates independent status/technique entries, owner attribute/skill references, evaluated amounts, costs and prerequisites. Invalid entries are never added to its detached catalogue maps, and a failed status discards its detached additions before sibling validation. Constructor failures and checks requiring invalid prior values still stop that dependent branch; no invented defaults are used.

The response uses child elements only, with no attributes or JSON payloads. Object fields occur at most once, unknown fields and text outside child fields reject, and scalars contain text only. Numbers must be finite decimal/scientific-notation text; units, hexadecimal, `NaN` and `Infinity` reject. Self-closing, explicitly empty and whitespace-only optional leaves mean omission: outer status `name`, attribute/skill `modifier` and `percentModifier`, `maxHealthPercent`, and entry `techniqueId`/`definitionRevision`, plus the [shared candidate/discipline optional leaves](TechniqueXml.md). Explicit zero and false remain values; nested technique amounts retain formula support. Required leaves and nonempty malformed values still reject. Attributes, unknown children and duplicate occurrences still reject, including an empty occurrence followed by a value. Booleans must be exactly `true` or `false`. Existing domain validators enforce conditional required fields, meaningful modifiers, integer and range requirements after parsing. Text must XML-escape `&` and `<`. Empty object wrappers keep their existing meaning. Empty optional lists may be omitted or use self-closing containers; missing or empty `<statusEffects/>` means no attachment mechanics, while `<abilityAttachments>` remains required. There is no legacy JSON-response fallback.

```xml
<abilityAttachments>
  <statusEffects>
    <statusEffect>
      <name>Steady practice</name>
      <description>Unconditional improvement from the owned ability.</description>
      <duration>-1</duration>
      <attributes>
        <attribute><attribute>Strength</attribute><modifier>1</modifier><percentModifier>10</percentModifier></attribute>
      </attributes>
      <skills>
        <skill><skill>Spellcasting</skill><percentModifier>10</percentModifier></skill>
      </skills>
      <maxHealthPercent>10</maxHealthPercent>
      <techniques><technique><techniqueId>selected_existing_technique_id</techniqueId></technique></techniques>
    </statusEffect>
  </statusEffects>
</abilityAttachments>
```

Names and catalogue identities above are structural examples; authored responses must use actual actor facts. List containers and their children are `statusEffects/statusEffect`, `attributes/attribute`, `skills/skill`, `disciplines/discipline`, `techniques/technique`, `aliases/alias`, `revisions/revision`, all requirement containers/`requirement`, `costs/cost`, `failureCosts/cost`, `effects/effect`, nested status `needBars/needBar`, and nested status `techniqueGrants/techniqueGrant`. An attribute or skill entry contains its same-named identity child as shown above. A fresh single revision may omit its known inner `<revision>1</revision>` field. Non-list objects (including `discipline`, `candidate`, `target`, `check`, `recipe` and nested effect `status`) use the existing DTO field names as child tags. An existing reference goes directly under the status's `techniques/technique`, supplying only its selected `techniqueId`; its known parent is resolved server-side. A new candidate remains under an enclosing `disciplines/discipline/techniques/technique/candidate` group and chooses its existing parent ID or new parent metadata there. Candidates never repeat disciplineId. Server-owned attachment IDs, timestamps and provenance remain excluded.

Numeric technique amounts use direct text, such as `<amount>2</amount>`, or nested `<amount><formula>max(1, level)</formula></amount>`. The same formula shape works for nested technique status modifiers and percentages. Permanent attachment status modifiers and percentages are numeric only. New healing uses a semantic `recipe` with `kind: healing` and skill/attribute/resource selectors only where a choice exists; optional standard damage uses `kind: damage`, while deliberate custom damage remains available; the engine still materializes canonical costs/effects/balance. Nonhealing candidates retain checks, normal costs, requirement lists, effects, per-effect checks, nested status grants, stacking and refresh policies, potency and formula validation. The typed parser also preserves valid existing DTO formula bindings (`bindings/binding` with `variable`, `kind` and optional `name`) and managed balance fields; guidance requests canonical formula variables without bindings and recipe proposals without copied balance metadata. Managed balance `improvementSteps` maps use `improvementStep` children with `id` plus step fields; `appliedImprovementIds` uses `improvementId` children. These parsed DTOs remain subject to the same domain policy checks. Omitted failureCosts retains ordinary costs; an explicitly empty failureCosts vector means free failure. This distinction is preserved.

Model statuses may have fixed and percentage attribute/skill modifiers, `maxHealthPercent`, direct existing `techniques` references and grouped new-candidate `disciplines`. The parser combines these into the existing internal `techniqueEntries` DTO. New parent metadata stays outside its child candidates. The shared grouped-reference decoder remains subject to its ordinary canonical-parent validation when that shape is supplied; generation guidance uses the simpler direct references. The shared technique schema, balance policy, resource rules, and formula validation apply. Status-granted techniques remain available only while their source status is active. Conditional targeting, auto triggers, reactions, weapon-based damage, and unsupported utility mechanics are excluded from authoring guidance; a conditional prose claim never becomes an unconditional bonus.

The shared standard/TinyBrain prompt gives a mechanical placement guide. An outer ability status is continuously active on the owner and represents an explicitly permanent, unconditional benefit or drawback. An activated action, including a temporary self buff, uses a technique entry in a permanent grant-only outer status. A grant-only status is complete without numeric modifiers. Its revision selects `self`, `single`, or `area` targets. Direct harm uses a damage effect; a buff or debuff applied on successful use uses a nested effect status on the recipient with a duration in integer world minutes or `-1` for permanent. An ability with explicit ongoing and activated components can use both outer modifiers and a technique. If the ability has no supported mechanical component, the prompt permits omitting statusEffects or using an empty `<statusEffects/>`.

This guide steers model authoring; XML and domain validation still check mechanics and structure, not whether the ability prose describes a passive or an attack. Reviewed drafts should be checked for semantic placement before application.

Generation returns `{ draft, expected }` without installing statuses, disciplines, techniques, or grants. `expected` identifies the current game epoch, character, and target ability snapshots (excluding artwork). Ordinary character-state and unrelated catalogue changes do not invalidate generation; current attachment mechanics and references are still validated before application. `authorNewAbilityAttachments` generates every newly accepted ability's draft first, previews the combined batch, then calls the atomic service apply once. Its `draftsByAbilityId` input instead applies already prepared drafts without another model call. Player option generation passes a server-trusted `pendingAbility` to the same XML authoring and read-only preview path; returned pending drafts contain stable proposal IDs and persist separately from the option's inactive `statusEffects`. The chooser displays the saved draft, and selection commits that same draft after validation. Explicit empty `statusEffects` is a complete preview. Loading or probing pending options without `ensureOptionsForNext` does not author drafts; older saved options are enriched only during ordinary ensured generation. Pending and declined cards never install catalogue entries. Initial NPC generation attaches mechanics after gear and quantity expansion and before starting-technique authoring. NPC level-up attaches after adding ability records and before progression allocation, restoring the old ability set if attachment generation fails.

The manual API uses `GET /api/players/:actorId/abilities/:abilityId/attachments` for the current editable draft and baseline, `POST .../generate` for a new staged proposal, and `PUT .../attachments` with `{ draft, expected }` for reviewed application. These internal DTOs and HTTP editor payloads remain JSON; only model-authored response syntax changes. Apply re-previews the edited draft to allocate stable proposal IDs, then commits one transaction against the supplied baseline. A different game or character, or edited target abilities, fails before mutation. See [players API](../api/players.md).

The browser editor's optional maximum-capacity round-trip behavior is documented in [AbilityAttachmentsEditor](AbilityAttachmentsEditor.md).

## File-backed structure

New attachment authoring selects `ability-attachments-selected.schema.xml`, with direct existing references and reusable candidate/discipline layouts. The original `ability-attachments.schema.xml` retains its prior structure for an already-running older process, because schema files are read per completion; changing source code does not require hot-changing that process's model-response contract. The typed parser and XML mechanics guidance are shared through [TechniqueXml](TechniqueXml.md) with starting techniques. The shared outer `discipline` groups its child references or candidates. Repeated parent IDs or normalized titles append children in encounter order, preserving first canonical metadata; detached parent lookup spans all statuses in the response. Outer status names are optional where the existing status parser permits unnamed effects; description and duration remain required. Scalar and formula-object amounts are both accepted. Conditional healing/custom effects, existing/new references and omission semantics remain validated by detached domain preparation.

Actor-aware preview persists resolved singleton recipe selectors and canonical recipe/effect IDs in returned draft entries. Applying a pending draft uses current policy coefficients, preserving the existing uncommitted-draft contract; already installed managed revisions retain their saved snapshots. Target/check choices remain explicit for standard damage.

## Selected-reference validation

Generated existing grants must have been selected for lookup, including newly authored nested effect-status grants. This is checked again after detached preview: semantic-key candidate deduplication cannot silently resolve an unselected existing technique into an accepted grant. Errors identify the offending path/ID and require lookup selection before reuse or removal of an unrelated grant; they never suggest inventing an identity or changing equivalent mechanics to evade validation. Recipe field aggregation is unchanged.

Lookup details capture each selected definition's latest revision. ID-only generated references receive that captured pin on the server, so a later unrelated catalogue revision cannot silently substitute unseen mechanics. An explicit generated pin must match the lookup revision or produces correction guidance to omit the pin or use that revision. Canonical deduplication is normalized to that selected reference for later previews. Existing manual/editor DTOs and standalone parsing without a generation selection retain valid explicit older pins and their existing domain validation. No selection token is saved, and existing ability grants, catalogue IDs, discipline membership and saved data are not rewritten.

Catalogue lookup is deliberately independent of ordinary `use`/`discover` eligibility. Ability-backed status grants already establish source-bound access and can reuse catalogue entries the actor has not learned or currently accessed; the new lookup does not narrow that policy. Requirements referencing a technique ID retain ordinary domain validation and are not treated as grants requiring selection.
