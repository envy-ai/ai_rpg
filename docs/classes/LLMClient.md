# LLMClient

The default-off `chat_tools.mutating_prompts_only` native-call gate classifies original execution permissions before checkpoint narrowing. `chatCompletion({ nativeToolMutationsRequired })` accepts `null` for capability inference, `false` to veto calls under this setting, or `true` which still requires an original mutator. TinyBrain uses its run-start execution snapshot. Disabled requests expose no native tool definitions and send `tool_choice: "none"`, without a generated tool-permission message; restricted requests expose only executable definitions. Pre-callback rejection prevents forbidden calls from reaching `captureResponsePayload` or `onResponse`. Server-owned XML/plans remain executable. See [ChatToolPolicy](ChatToolPolicy.md) and [configuration](../config.md#chat-tools).

## Purpose
`LLMClient.js` is the shared text-completion orchestration layer. It selects the configured backend, builds chat-completion payloads, enforces concurrency, runs retries, reports prompt progress, handles cancellation, validates structured output, logs prompts/errors, supports deterministic test outputs, and records per-prompt output-character statistics.

Callers use it from gameplay routes, world-generation helpers, event checks, status-effect generation, chat-tool loops, and `scripts/run_prompts.js`. The class returns the final assistant text string; callers that need normalized response metadata or tool calls use `onResponse`.

## Backends
- `openai_compatible`: sends HTTP requests with `axios` to a normalized `/chat/completions` endpoint using `ai.endpoint`, `ai.apiKey` or OAuth refresh-token auth, and `ai.model`.
- `codex_cli_bridge`: delegates transport to `CodexBridgeClient.chatCompletion(...)`. `LLMClient` keeps ownership of retry handling, validation, progress tracking, prompt stats, cancellation, and Codex usage/quota reporting around the bridge response.
- `cline_cli_bridge`: delegates transport to `ClineBridgeClient.chatCompletion(...)`. It uses the authenticated local Cline CLI, keeps retry/validation/progress/cancellation behavior in `LLMClient`, and does not use endpoint/API-key config.
- `kimi_cli_bridge`: delegates transport to `KimiBridgeClient.chatCompletion(...)`. It uses the authenticated local Kimi Code CLI through a fresh ACP stdin session, streams decoded wrapper `content` deltas into prompt progress, rejects native tool events, keeps retry/validation/cancellation behavior in `LLMClient`, and does not use endpoint/API-key config.

Backend aliases are normalized through `CodexBridgeClient.normalizeBackend(...)`; backend-specific validation routes to the selected adapter. See [CodexBridgeClient.md](CodexBridgeClient.md) for Codex app-server transport, [ClineBridgeClient.md](ClineBridgeClient.md) for Cline one-shot CLI transport, and [KimiBridgeClient.md](KimiBridgeClient.md) for Kimi ACP JSON-RPC transport.

## Configuration Inputs
- `Globals.config.ai` is cloned for each request attempt. Matching `ai_model_overrides` profiles are applied by normalized `metadataLabel` before that attempt is dispatched.
- Allowlisted region/location and entity-population prompts use root `world_generation.max_tokens` (merged default `20000`) after model-profile, caller and payload token limits. Each completion or TinyBrain stage receives that output budget; token-chunked transport retains smaller windows. See [WorldGenerationTokenBudget](WorldGenerationTokenBudget.md) for coverage and the existing CLI-bridge limitation.
- `chatCompletion({ multimodal: true })` uses the effective main AI profile directly when `ai.has_vision` is `true`. The effective profile includes matching `ai_model_overrides`, so an override can enable or disable direct vision routing for its prompt labels. When effective `has_vision` is false or omitted, `ai_multimodal` overrides the text config as before and must exist and be enabled; matching model overrides are then applied over it.
- `ai.custom_args` injects provider-specific top-level payload fields. Reserved core payload keys are rejected in configured custom args.
- `ai.headers`, override-profile headers, and per-call `headers` are merged for HTTP requests. OAuth-backed requests always set `Authorization` from the refreshed access token.
- `ai.cachebuster: true` prepends `[cachebuster:<uuid>]` to the final user message in the outbound payload copy. Caller-provided message objects are not mutated.
- `ai.prefill` adds a final assistant message for OpenAI-compatible requests so providers that support assistant prefill can continue from that text. Matching `ai_model_overrides` profiles can replace it or set it to `null`; per-call `prefill`/`assistantResponseSeed` takes precedence. Prefill is rejected for CLI bridges and ordinary tool-call requests. The explicit non-stream token-chunk mode used by live deslop permits tools plus prefill because the target llama.cpp API supports that combination.
- Independent `ai.xml_closing_tag_guard` opts supported OpenAI-compatible endpoints into raw XML branch rejection. `xmlOutput: true/false/"auto"` and TinyBrain scope control eligibility; false avoids logprob overhead. Structural inspection composes before prose hooks and observes opaque markup without fabricated tokens. See [XmlClosingTagGuard](XmlClosingTagGuard.md).
- `ai.live_deslop` is validated as a boolean. The player-action integration supplies the live token handler and provider log-probability payload described in [LiveDeslop.md](LiveDeslop.md).
- `ai.xml_repetition_fix` is validated as a boolean. `TinyBrainPromptRunner` activates it only for staged prompts and supplies the current prompt label plus the `ai.retryAttempts` continuation budget.
- `ai.sysprompt_append` adds an additional model-specific system-instruction message to the outbound payload copy. Matching `ai_model_overrides` profiles replace it or set it to `null`; the caller-provided `messages` array is not mutated.
- `ai.reasoning_effort`, override-profile `reasoning_effort`, payload `reasoning_effort`, or per-call `reasoningEffort` opt into OpenAI-compatible reasoning by sending `reasoning: true` and `reasoning_effort`.
- `ai.unload_during_image_generation` defaults to `false`. It can be overridden per prompt profile; when true, server validation requires an OpenAI-compatible text backend and the ComfyUI image engine. Every real transport attempt with an effective true value invokes the registered strict ComfyUI cleanup handler after acquiring the shared model-lifecycle gate and before contacting the text backend. Cleanup failure is propagated without running the prompt.
- Optional `ai.image_generation_handoff: { provider: strata, min_free_vram_mib: 12288 }` participates in the same strict pre-prompt ComfyUI cleanup and lifecycle gate. It selects cache resizing around render batches without llama.cpp management or model/process unloading. Absent/null preserves existing behavior; see [StrataVramClient](StrataVramClient.md) for validation and minimum total-free MiB semantics.
- Optional `ai.strata_runtime` enables server-owned native Strata startup and guarded shutdown. Each managed real transport checks captured ownership and its actual endpoint/model inside the lifecycle gate; RAM standby retains the same API identity. See [StrataRuntime](StrataRuntime.md).
- A nonblank root `ai.local_startup_script_path` makes `server.js` start and own the executable before router preloading and startup prompts, independently of `ai.unload_during_image_generation`. `ai.terminate_during_image_generation` defaults to `false`, requires a startup path, and is mutually exclusive with router unload mode; only termination mode adds per-prompt startup-script switching and stop/restart around ComfyUI renders. `LLMClient` validates the basic value types and required pairing, while `server.js` validates executable paths and the required OpenAI-compatible backend.
- `ai.router_slot_cache_enabled` defaults to `false`. When enabled for both effective prompt targets, `ai.router_slot_cache_directory` selects the absolute slot-cache directory and must match the game-owned local llama.cpp router's `--slot-save-path`; the directory continues to default to `/dev/shm`.
- `ai.force_outputs_file` or `LLM_FORCE_OUTPUTS_FILE` supplies deterministic fixtures for tests and scripted runs. Legacy by-label fixtures remain supported; version 2 cassettes use a strict globally ordered, request-fingerprinted completion trace.
- `ai.record_outputs_file` or `LLM_RECORD_OUTPUTS_FILE` records accepted logical completions into a version 2 cassette. Recording and forced replay are mutually exclusive and fail before transport when both are configured.
- Root `max_concurrent_requests_all_models` optionally adds a positive-integer cap across all real chat-completion requests, independent of model/backend/auth semaphore keys.
- Root `router_preload_model` optionally names the llama.cpp router model loaded during server startup. Blank or omitted values fall back to `ai.model` whenever router-backed lifecycle settings require startup preloading.

## Public API
- Terminal direct-completion failures emit one transient `prompt_failed` notification, including the legacy empty-string return path. Matching-label tool loops and TinyBrain programs own their enclosing failure instead; see [PromptFailureReporter](PromptFailureReporter.md).
- `chatCompletion(options)`: runs one completion request and returns assistant text.
- `withPromptQueueReservation(callback)`: creates an opaque queue reservation, passes it to an awaited callback, and releases retained permits in `finally`. Sequential `chatCompletion(...)` calls pass that reservation to keep one logical prompt's queue slot. Inside an explicitly owned nested scope, another reservation callback joins the existing owner and leaves release to its outer callback.
- `withPromptQueueReservationNested(reservation, callback)`: runs awaited child work with async-scoped ownership of the existing reservation. Nested completions inherit the token without caller plumbing; nested TinyBrain runners join it. This helper retains the optional all-model slot and cassette permit. A same-model child reuses the model permit; a different-model child releases the old model permit before awaiting its new one. The next parent completion switches back by the same rule. Keeping only one model lease prevents opposing nested model switches from deadlocking. Children inherit the owner's foreground/background lane. Root callbacks themselves do not implicitly adopt unrelated work: only the explicit nested scope enables inheritance. Awaited parallel leaf completions inside that owned scope serialize through a native per-owner request semaphore, including nested runner stages that pass the inherited token explicitly. Explicit concurrent token reuse outside an owned scope still fails. Request-local context rejects attempts to start an awaited same-owner completion from an active completion callback, rather than self-deadlocking. A nested callback boundary drains its outstanding child requests before returning or propagating an error, so a parser can retry after a failed parallel child without colliding with its siblings. Root callback failure aborts and drains its active/queued children before releasing resources, preserving the original failure.
  TinyBrain parser and post-parse contexts expose this lifecycle as `withNestedPrompt(callback)`. Location roster resolution passes it to item-family authoring; native prompt-launching tools use the same retained owner, including at both concurrency limits of one.
- `hasPromptQueueReservation()`: reports whether the current async scope owns an active, non-yielded reservation. Event checks use this native status to sequence complete event and need-bar programs only inside an owned section sequence; independent calls retain their parallel launch.
- The per-owner request gate serializes leaf completions, not whole sibling programs launched with `Promise.all`. Native location population captures this status before launching lazy Things/NPC callbacks: owned programs finish sequentially; unowned callbacks retain independent parallel launch. A location Things batch itself retains one owner through roster/families/expansion/corrections and optional naming, without holding it for image work.
- `withPromptQueueReservationYield(reservation, callback)`: deliberately releases the model, optional all-model, and cassette permits and clears inherited ownership while waiting for `requestUserInput`. Its asynchronous mod responder may therefore generate an answer independently. Before returning, it reacquires the retained resources at the front of their foreground/background lanes. Invalid, released, active-request, and recursively yielded reservations fail explicitly. Ordinary internal prompt-launching work uses `withPromptQueueReservationNested`, not this human-wait exception.
- `withExclusiveModelLifecycle(callback)`: waits for active real text requests to finish, blocks new real text transport attempts, runs the callback, and releases queued requests in `finally`. The image-render lifecycle uses this around llama.cpp unload/render/reload or terminate/render/restart.
- A streamed prompt may enter prompt-progress tracking before it acquires the model-lifecycle gate so the UI can show and cancel it while queued. Its start-timeout deadline remains inactive during that wait. The full configured start timeout is activated only after model-lifecycle preparation and ComfyUI cleanup complete, immediately before the transport begins; image-render time and the Cache Monitor VRAM-release wait therefore cannot consume a queued local prompt's timeout.
- `resolveUnloadModelOnSwitch(config?)`: validates the root `unload_model_on_switch` boolean and defaults it to `false`. Enabled real transports take exclusive lifecycle access, compare their effective endpoint/model with the previous real prompt target, and keep the lock through the replacement transport so an active request cannot be unloaded. A game-owned local router optionally saves and restores slot 0 when both targets enable slot caching; model unloading continues normally when caching is disabled.
- `resolveRouterSlotCacheEnabled(aiConfig?)`: validates `ai.router_slot_cache_enabled` and defaults it to `false`.
- `resolveRouterSlotCacheDirectory(aiConfig?)`: resolves the absolute local slot-cache directory and defaults it to `/dev/shm`.
- `resolveRouterContextCachePaths(config?)`: returns the exact model-derived cache paths owned by configured local routers. It covers the root model, startup preload model, prompt-override models, and local-router models observed at runtime. `deleteRouterContextCacheFiles()` removes those paths during graceful shutdown, while `deleteRouterContextCacheFilesSync()` provides an idempotent direct-exit fallback. Missing files are harmless; other deletion failures are aggregated and reported. Cleanup never scans the shared cache directory or deletes unrelated files.
- `resolveRouterPreloadModel(config?)`, `shouldPreloadRouterModel(config?)`, `resolveRouterPreloadTarget(config?)`, and `preloadRouterModel(options?)`: validate and resolve startup router preloading, reuse the main endpoint/authentication/headers, idempotently load the selected model under exclusive lifecycle access, and register it as the initial model-switch target.
- `resetModelSwitchTracking()`: clears the process-local previous-prompt target; it is exposed for isolated tests. Forced outputs are not tracked because they skip transport.
- `getCompletionCassetteStatus()`: reports active replay and recording paths, format versions, completeness, entry totals, consumption, cassette-serialization ownership/queue depth, and latched replay failures.
- `assertCompletionCassetteConsumed()`: requires an active version 2 replay with no active or queued cassette completion, no unused entries, and no earlier mismatch/exhaustion/concurrency failure. A later completion cannot hide an earlier replay failure.
- `completeCompletionCassetteRecording({ description? })`: marks the configured recording complete after the scenario request settles. It rejects active or queued cassette work; an unmarked recording is diagnostic evidence only and cannot be replayed.
- `setComfyModelCleanupHandler(handler)`: registers the server-owned cache-preserving ComfyUI VRAM-release operation used before enabled prompt transports. The handler uses Cache Monitor first and may reach `/free` only through its failed-release fallback. Passing `null` clears it for isolated tests; an enabled request with no handler fails explicitly.
- `setManagedLocalLlmGuard(handler)`: checks process-session manual-off intent for actual managed targets inside the lifecycle gate before any auto-start or transport. It preserves explicit remote-provider overrides; manual-off errors use the existing nonretryable model-lifecycle path. See [ManagedLocalLlmController](ManagedLocalLlmController.md).
- `setManagedStrataRuntimeHandler(handler)`: registers native Strata readiness verification with `{ target, endpoint, model, allowRamStandby, signal }`. Missing-handler, target and ownership errors stop transport through the existing prompt failure path. Passing `null` clears the hook.
- `setManagedLocalModelStartupHandler(handler)`: registers the server-owned managed-process switch operation. It receives the prompt's effective AI config, label, and startup-script path after exclusive lifecycle access is acquired. Missing-handler and switch failures prevent transport and propagate explicitly. Passing `null` clears it for isolated tests.
- `resolveEffectiveAiConfiguration(metadataLabel, config)` and `resolveOpenAICompatibleModelManagementTarget(metadataLabel)`: resolve prompt-specific model overrides and the authenticated endpoint/model target used for llama.cpp router management.
- `resolveStrataVramManagementTarget(metadataLabel = 'image_prompt_generation')`: resolves the effective Strata handoff target and `minFreeVramMiB`, sharing endpoint/authentication/header/OAuth preparation with router management. It requires explicit Strata handoff and a model; it does not activate router preloading or model-switch unloading.
- `withPromptProgressGroup({ progressGroupId, progressGroupTargetLabel }, callback)`: establishes an async-scoped logical progress group. Every nested `chatCompletion(...)`, including calls made by a tool loop, automatically inherits the stable group id and dedicated whole-run target label unless it supplies the identical values explicitly. Conflicting or nested groups fail clearly.
- `hasActivePromptProgressGroup()`: reports whether the current async call chain already owns a prompt-progress group, allowing shared runtimes to join it without attempting an unsupported nested group.
- `withTinyBrainXmlRepetitionFix(...)` and `withTinyBrainXmlRepetitionLogger(...)`: establish the matching staged-prompt detector and a stage-local transcript appender. The runner owns these scopes; ordinary callers should use TinyBrain routing rather than enabling them directly.
- `cancelPrompt(streamId, reason)`: aborts one tracked in-flight prompt and rejects that logical completion with `PromptCancellationError` (`code: PROMPT_CANCELLED`). Cancellation is terminal; structured/TinyBrain parser loops and ordinary transport retry loops must not reinterpret it as an empty provider response.
- `retryPrompt(streamId, reason)`: aborts one tracked attempt and restarts the same `chatCompletion(...)` loop without consuming an automatic retry attempt. The retry keeps or reacquires the front position in its foreground/background semaphore lane instead of joining the back of the queue.
- `recordPromptProgressGroupFailure(progressGroupId, responseText)`: records one parse-failed response for a logical prompt group, marks its current progress entry failed, and broadcasts an immediate `prompt_progress_group_failure` update.
- `clearPromptProgressGroup(progressGroupId, { recordOutputCharacters })`: releases transient failed-response history and completes a grouped logical prompt. With aggregate recording enabled, it writes the cumulative received-character total once under the group's dedicated target label before the completion pulse.
- `getBaseContextEndMarker()` and `applyBaseContextToolPolicy(messages, options)`: internal base-context boundary/schema helpers exposed for template and transport tests. They do not insert execution instructions into the retained transcript.
- `cancelAllPrompts(reason)`: advances the process-local cancellation generation, invalidates active staged queue reservations, and aborts every active real completion attempt, including non-stream/silent requests, configured retry-delay waits, and attempts still waiting in model-switch or pre-prompt cleanup work. It returns cancellation counts plus tracked prompt ids, active-attempt diagnostics, and active-reservation diagnostics. A TinyBrain runner cancelled between checkpoints therefore cannot start its next stage.
- `hasActivePrompts()`: read-only, constant-time activity check across prompt-progress entries, tracked prompt controllers, independent active attempts, and staged queue reservations. It includes silent/non-stream requests and staged work between checkpoints, without relying on visible progress. Managed Strata header status checks use it to waive their short inspection deadline during prompt processing.
- `waitForPromptDrain({ timeoutMs, pollIntervalMs })`: waits until prompt-progress entries, tracked prompt controllers, the independent active-attempt registry, and staged queue reservations are all empty.
- `ensureAiConfig()`, `resolveBackend(aiConfigOverride)`, `getConfigurationErrors(aiConfigOverride)`, `isConfigured(aiConfigOverride)`, `getMaxConcurrent(aiConfigOverride)`, `resolveMaxConcurrentAllModels(configOverride)`: configuration helpers used by settings and tests.
- `resolveChatEndpoint(endpoint)`, `baseTimeoutMilliseconds()`, `resolveTimeout(timeoutMs, multiplier)`, `resolveTemperature(explicit, fallback)`, `resolveOutput(output, fallback)`: request utility helpers.
- `calculatePromptProgressFraction(receivedCharacters, targetCharacters)` and `resolvePromptProgressCharacterTarget(label, config)`: prompt-progress math and configured target lookup, with a 5,000-character cold-start default when no target matches or the target map is absent.
- `getPromptOutputCharacterStats(label)`, `listPromptOutputCharacterStats(options)`, `recordPromptOutputCharacters(label, outputCharacters)`, `clearPromptOutputCharacterStats()`: persistent output-character statistics helpers used by `/promptstats`.
- `logPrompt(options)`: writes prompt/response logs under `logs/`; callers can append later sections to the same file with `filePath` and `append: true`. Filesystem failures return `null` and emit a console warning by default; internal callers that provide their own higher-level warning can pass `warnOnFailure: false`. Tiny-brain prompt programs treat initial log creation as required, but warn and continue the running turn if a later prompt, response, diagnostic, or parse-failure append cannot be written.
- `writeLogFile(options)`: writes `ERROR_<prefix>_<metadataLabel>_<timestamp>.log` files for validation, chat-completion, and tool-call failures.
- `formatMessagesForErrorLog(messages)`: renders chat messages into readable system/prompt/other sections for logs.
- `resetForcedOutputState()` and `resetPromptOutputCharacterStatsForTests()`: test helpers.

## `chatCompletion(...)`
Important options:

- `messages`: required OpenAI-style chat messages.
- `metadataLabel`: prompt label used for override matching, logging, prompt progress, stats, and Codex usage labels.
- `progressDisplayLabel`: optional nonblank string that changes only the visible progress label before its existing `[counter]` suffix. Null/undefined uses the normal metadata label; blank/non-string values throw even for silent or forced-output calls. Prompt routing, logs, progress IDs, character-stat keys/targets, cassette fingerprints and retry ownership continue to use the base metadata label. Existing progress-group reuse keeps its stable first display label. NPC level-up ability calls use `levelup_abilities_<full character name>` without creating per-character routing or statistics keys.
- `errorLogLabel`: optional error-log label. Error logs otherwise prefer `metadata.promptName`, then `metadata.promptType`, then `metadataLabel`.
- `additionalPayload`: extra request body fields such as `tools`, `tool_choice`, or provider-specific parameters. Provider-visible fields must be placed here unless `chatCompletion(...)` has an explicit top-level option for them.
- `allowToolCalls`: boolean, default `true`. Setting it to `false` removes native tool definitions, sends `tool_choice: "none"`, and rejects provider tool calls before response callbacks.
- `headers`: per-call HTTP headers.
- `model`, `apiKey`, `endpoint`, `temperature`, `maxTokens`, `topP`, `frequencyPenalty`, `presencePenalty`, `seed`: per-call request overrides.
- `prefill` or `assistantResponseSeed`: optional OpenAI-compatible assistant response prefill. `null` suppresses configured `ai.prefill` for that call.
- `timeoutMs`, `timeoutScale`, `retryAttempts`, `waitAfterError`, `waitAfterRateLimitError`, `waitAfterNetworkError`: timeout and retry controls.
- `stream`: OpenAI-compatible streaming control. CLI bridge requests are sent through the bridge with `stream: false` while bridge events feed prompt progress.
- `runInBackground`: marks the request as background for progress display and lower semaphore priority.
- `queueReservation`: an opaque reservation supplied by `withPromptQueueReservation(...)`, inherited automatically only inside an explicit owned nested scope. Owned requests execute sequentially and keep the same all-model concurrency configuration and owner priority; parallel standard child requests queue safely within their owner. Model changes hand off one current per-model permit while retaining the optional all-model slot; no unrelated queued request takes that retained slot between parent/child stages.
- `progressGroupId`: optional non-empty logical prompt id copied into prompt-progress entries. Sequential TinyBrain calls reuse one stable progress entry/id for that group until `clearPromptProgressGroup(...)` completes it. Grouped requests must also provide `progressGroupTargetLabel`, whose dedicated historical whole-run average or configured character target supplies one fixed expected-output denominator for the entire group. Both values can be inherited from `withPromptProgressGroup(...)`.
- `multimodal`: sends image-bearing messages through the effective main AI profile when its `has_vision` is `true`; otherwise merges `Globals.config.ai_multimodal` before applying model overrides.
- `preferDedicatedMultimodalConfiguration`: used by seasonal location-image prompt generation with `multimodal: true`. If the effective main profile lacks vision, dispatch uses the root AI configuration merged with the dedicated multimodal configuration, excluding prompt-specific overrides. This prevents a non-vision override from replacing the selected vision model or its inherited connection settings. An effective `has_vision: true` profile still handles the request directly. Other callers retain the existing multimodal override order.
- `validateXML`, `validateXMLStrict`, `expectedXmlRootTag`, `expectedXmlRootTags`, `requiredTags`, `requiredRegex`: response validation controls. `expectedXmlRootTag` declares one required complete XML root; `expectedXmlRootTags` declares alternative accepted roots. The expected-root options are mutually exclusive, and their completeness check also runs when whole-document XML validation is disabled.
  The live guard and final XML tool-call policy scan use the first declared root
  (or named schema root), ignoring unrelated markup before it and after it closes.
  Final response parsers retain their existing final-envelope selection. Expected
  roots can also be inherited from `withXmlOutputScope`; explicit request roots
  override the scope, and a nested plain scope clears inherited root declarations.
  Built-in TinyBrain XML checkpoint functions, native custom checkpoint contracts
  and final-model closures all supply roots through the runner's shared output
  contract metadata. This does not change the provider's live-guard opt-in flag.
- `responseValidator`: optional synchronous or asynchronous function, default `null`. Runs on tool-free response text after the built-in format checks and before successful completion; throw the original error to reject a domain-invalid response. Return values are ignored. Validation shares the completion's existing retry budget, and the callback must not mutate game state.
- `responseValidationRetryFeedback`: optional boolean, default `false`. When enabled, retries after required-regex, expected-root, strict-XML, required-tag, custom `responseValidator`, or forbidden-tool-call failures receive the rejected response followed by the exact error and a correction instruction. Rejected tool names/arguments are included as plain-text diagnostics explicitly marked **NOT EXECUTED**, including when the response had no text; they are also retained in the error log. No native tool-call message or fabricated execution receipt is added. Corrections omit native tool definitions and send `tool_choice: "none"`. Feedback replaces rather than accumulates earlier rejected attempts. Transport and provider retries do not receive this feedback. Standard non-TinyBrain `player_action` and `quest_generate` enable this option.
- `forceOutput`: deterministic string or response-shaped object that skips network transport and runs normalization, validation, stats, and hooks.
- `captureRequestPayload`, `captureResponsePayload`, `onResponse`: testing and integration hooks.
- `onStreamToken`: optional async OpenAI-compatible token hook. In ordinary stream mode content deltas with aligned `choices[0].logprobs.content` entries are exposed to live-token inspection. Content deltas without logprobs are still appended verbatim to the response but remain opaque to the hook because no sampled alternatives exist; this preserves XML tag pieces that some llama.cpp builds omit from logprob metadata. Structured `delta.tool_calls` data is accumulated separately and never treated as prose. The final inspectable text token is called once with `responseComplete: true`, including when the provider reports completion in a later empty SSE chunk. With `nonStreamTokenChunkSize`, the same hook processes each visible token in a non-stream response batch and receives `responseComplete` on the final visible token. llama.cpp's trailing zero-byte stop/control record is excluded from the callback and retained-token history. The hook receives full response text (including prefill and opaque content), generated text, the current token, and sampled token records. Returning a rewind offset plus alternative token restarts the logical completion with corrected assistant prefill; throwing fails explicitly. Legacy/direct forced output remains incompatible with this hook. Strict version 2 replay accepts a configured hook but does not invoke it because a logical cassette has no token stream; live-token behavior requires a live verification run.
- `nonStreamTokenChunkSize`: optional positive integer that requires `stream: false`, `onStreamToken`, and the OpenAI-compatible backend. Each transport request is limited to this many new tokens. A clean `finish_reason: "length"` response continues from assistant prefill without consuming an error retry, up to the original logical `max_tokens` budget. Aligned non-stream `choices[0].logprobs.content` metadata is mandatory. Tool definitions and selection policy remain unchanged across continuations and corrections.
- `liveTokenStreamFallbackChunkSize`: optional positive batch size for adaptive live-token transport. The request first uses streaming; invalid or misaligned supplied prose-token logprobs, or an HTTP 400 provider message explicitly rejecting streaming (including `stream + tools + logprobs unsupported`), mark the current capability key as failed and immediately retry through bounded non-stream logprob batches of this size. Empty responses, transport failures, timeouts and generic HTTP errors use the existing bounded retry policy without changing streaming capability. A content delta with no logprobs is preserved as opaque response text and does not trigger fallback.
- `liveTokenStreamCapabilityKey`: required with `liveTokenStreamFallbackChunkSize`. Failed keys remain latched for the lifetime of the game-server process. Player actions include the effective llama.cpp endpoint and managed process PID, so restarting managed llama.cpp produces a new key and re-enables one streaming probe.
- `onLiveTokenStreamFallback`: optional callback used with adaptive fallback. It runs once when a capability key is first latched and receives the exact console message plus timestamp, prompt label, failure classification, capability key, HTTP status, error name/code/message, server response body, backtrace, and fallback chunk size. Callback failures propagate instead of silently losing diagnostics.
- `logStreamChunksToConsole`: dumps raw OpenAI-compatible streamed `data:` payloads.
- `output`: `stdout`, `stderr`, or `silent`; `silent` suppresses normal console output and prompt-progress tracking.

Request flow:

1. Detect base-context prompts through their internal end marker, remove that marker, and preserve the caller’s native tool scope before any provider-visible payload is built. Then expand internal message-boundary markers and convert any `image_url` data URLs in message content to WebP through `sharp`. Non-data image URLs in this preprocessing path fail with an explicit error.
2. Resolve deterministic output from `forceOutput` or a forced-output fixture, if configured.
3. Resolve retry count from the call option or `ai.retryAttempts`.
4. For each attempt, clone AI config, apply `ai_model_overrides`, merge custom args/headers, resolve backend, append configured system-prompt text, apply cachebuster, append OpenAI-compatible assistant prefill when configured, resolve model/temperature/token/top-p/reasoning settings, and choose a semaphore key.
5. Acquire the per-key and optional all-model slots atomically through the existing semaphore queues. A queued request consumes neither slot while its other limit is full, leaving independent model capacity usable and preventing a queued outsider from holding a nested child's model while waiting for its parent's global slot. Background requests share the same semaphores but runnable foreground requests are dispatched first; with a limit above one, background work leaves one slot available for foreground prompts. A joint foreground waiter blocked on another resource does not prevent an owned background child from acquiring a free model slot. A failed unreserved attempt keeps its permits when no higher-priority foreground request is waiting, so its immediate retry stays ahead of queued peers at both gates. A failed unreserved background attempt yields to waiting foreground work, then reacquires at the front of the background lane. A reservation retains its logical slot across checkpoints, retries and explicitly owned nested work; lifecycle-gate access remains scoped to each real transport attempt. Only deliberate human-input waiting yields the owner.
6. Start prompt-progress tracking when the request is trackable and output is not `silent`, before waiting for model-lifecycle access or router switching. The client therefore receives an immediate progress entry while a local replacement model is loading/restoring instead of appearing idle.
7. Acquire model-lifecycle access. Normal requests use shared access. Effective managed-local requests and root `unload_model_on_switch: true` requests use exclusive access. Managed-local requests first ensure their effective startup script is active; a changed script is stopped and replaced before transport, while an unchanged script retains its PID. Router-switch requests unload the previous effective llama.cpp model when the target changes. For the same game-owned local router, the switch optionally saves/restores slot 0 only when both targets enable `router_slot_cache_enabled`; otherwise it only unloads and dispatches the replacement prompt so llama.cpp autoloads/waits. Cache save/restore failures warn and continue. An old-model unload failure logs a warning, broadcasts `llama_router_unload_warning` with diagnostic details, and still dispatches the replacement prompt; the replacement can still fail if the router cannot load it while the old model remains resident. Both paths retain exclusivity through transport, so a switch cannot terminate an active request.
8. Dispatch through `axios.post(...)`, `CodexBridgeClient.chatCompletion(...)`, `ClineBridgeClient.chatCompletion(...)`, `KimiBridgeClient.chatCompletion(...)`. OpenAI SSE chunks are processed in arrival order. Adaptive live-token requests prefer streaming with tools and prose-token logprobs. Content deltas without logprobs are appended verbatim but excluded from live-token inspection, while structured `delta.tool_calls` are assembled separately. An explicit streaming compatibility failure switches the same logical completion to bounded non-stream batches, and later requests reuse that decision for the same server-process key; an empty or interrupted stream does not disable streaming. A length-limited non-stream batch continues from the accepted assistant prefix. A requested branch correction rewinds retained token records and starts a new transport request without consuming a normal error retry. The caller decides whether tools remain available; player-action live deslop preserves them in both modes.
9. Normalize the response into an OpenAI-style `chat.completion` payload, merge assistant prefill into returned text exactly once, call capture/on-response hooks, strip `<think>...</think>` blocks from returned text, validate output, update prompt stats, and return assistant text.

## Response Normalization And Validation

After a valid XML envelope, independent missing `requiredTags` share the [ResponseValidation](ResponseValidation.md) budget of ten distinct problems in the existing correction attempt. Required-tag matching accepts multiline contents and XML attributes, and matches complete tag names. Domain `responseValidator` callbacks run only after these structural prerequisites pass; malformed XML still stops envelope validation immediately. Nested domain aggregates retain the same ten-problem budget and reach correction feedback unchanged.

- Streaming OpenAI-compatible responses are assembled from SSE `data:` chunks. Text deltas are concatenated and `delta.tool_calls` chunks are assembled into complete function calls. `[DONE]` ends the SSE data sequence, but `chatCompletion(...)` waits for the HTTP transport's `end` event before releasing the caller so a following request cannot overlap a response the provider still considers active. Completion is guarded so `end`, `error`, and timeout paths cannot settle the same request twice. Providers that hold streaming responses open after `[DONE]` can be configured with `ai.headers.Connection: close` to request immediate transport closure while preserving streaming.
- Each HTTP stream uses a UTF-8 `StringDecoder`, preserving characters split across network buffers. At transport end, the decoder and any final SSE line without a terminating newline are drained through the ordinary content/tool/finish-reason/usage parser before settlement. This prevents dropping a supplied final character or terminal metadata; it never adds missing XML, changes validation, or repairs content genuinely omitted by the provider. Regression fixtures cover unterminated final content/metadata frames, ordinary framing, genuine missing markup, and split UTF-8 bytes. Existing stitched error logs alone do not establish whether a historical malformed response originated in the provider or in discarded wire data.
- A matching `withTinyBrainXmlRepetitionFix(...)` scope forces OpenAI-compatible streaming and inspects the stitched logical response after every content delta. `TinyBrainXmlRepetitionDetector` recognizes an exact completed-element `AA` suffix or exact direct-sibling `ABAB` sequence when each candidate element is longer than 50 characters. Detection destroys the transport, removes the duplicate suffix, and resends the original messages with the accepted prefix as an assistant message followed by `{ role: 'user', content: 'continue' }`. Continuation output is joined to the prefix before response hooks and normal validation. The normalized metadata label limits the scope, so unrelated nested prompts are excluded. CLI bridges are rejected; recovery exhaustion throws instead of returning an empty result. Any partial streamed tool call is discarded, while completed tool results already present in the caller's conversation remain.
- Live-token streaming inspects only deltas with aligned logprob metadata. Content without logprobs is preserved verbatim as opaque response text, which keeps XML tag fragments intact without inventing branch alternatives. Structured tool-call deltas are accumulated separately. Assistant prefill and currently executable tools are allowed together; corrections that disable native calls expose no definitions.
- Non-stream responses and CLI bridge responses use the same normalized shape for `choices[0].message.content` and `choices[0].message.tool_calls`.
- Token-chunked non-stream responses may echo the supplied assistant prefill in `message.content`; only newly generated text is expected in `logprobs.content`. `LLMClient` verifies exact alignment, merges the prefill once, and fails explicitly on missing or mismatched metadata. For a normal `finish_reason: "stop"`, one final `token: ""`, `bytes: []` llama.cpp control record is accepted and omitted from visible-text processing; empty records anywhere else remain invalid.
- Tool-call arguments must be parseable JSON strings. Malformed tool-call payloads throw before callers receive them.
- Empty assistant text is accepted only when one or more valid tool calls are present. Tool-call-only completions return `''` while `onResponse` carries the normalized tool calls.
- `requiredRegex`, expected-root validation, XML validation, and required-tag checks are skipped for intermediate tool-call turns. The terminal text turn is validated normally.
- With XML validation enabled, `Utils.extractFinalXmlBlockFromResponse(...)` normally isolates the final outer XML envelope for parsing and required-tag checks. `expectedXmlRootTag` and `expectedXmlRootTags` instead select the final allowed envelope using `Utils.extractFinalXmlRootBlock(..., { requireComplete: true })`, so analysis or prose may surround it without requiring the root at the response boundaries. An opening expected root without its matching close fails inside the completion retry loop, including when an earlier draft was complete; a valid descendant never replaces an open selected outer envelope. With `validateXML: false`, this performs balanced expected-root presence/completeness validation only; with XML validation enabled, the extracted block is also parsed and its document root is checked. `validateXMLStrict: true` uses `Utils.parseXmlDocumentStrict(...)`; otherwise `Utils.parseXmlDocument(...)` is used.
- A built-in XML validation or custom `responseValidator` retry caused by an actually unclosed root now includes the rejected response, exact validation error, and [XmlRetryFeedback](XmlRetryFeedback.md)'s instruction to close all tags and put `DONE` after the root, even when general `responseValidationRetryFeedback` is disabled. Missing or wrong expected roots and other validation errors retain the existing feedback setting. The marker is requested only on correction; no response is repaired and the existing retry count is unchanged.
- Validation correction feedback appends the quoted insanity sentence from [XmlRetryFeedback](XmlRetryFeedback.md) when its response text exactly repeats the preceding rejected response. Comparison occurs before thinking-tag removal and whitespace trimming, remains local to the completion, and applies only when correction feedback is sent. Transport retries retain their existing behavior.
- Correction conversations retain every rejected XML response and its feedback in order until that completion succeeds; subsequent requests start clean. Region and location generation use the shared retry policy's default retention rather than dropping rejected documents.
- Chat-completion errors, invalid XML, missing tags, and missing regex matches write dedicated error logs containing response text and formatted prompts. Exhausted per-attempt failures return `''`; preflight/configuration errors, strict fixture-resolution errors, and deterministic provider context-limit errors throw.
- Generic `chatCompletionError` records for response-validation failures additionally include the observed `finish_reason`, actual `transport_streaming` flag, and only the numeric `prompt_tokens`, `completion_tokens` and `total_tokens` usage fields. Unavailable values remain `null`. These small metadata fields help distinguish provider stop/length outcomes on later failures without copying another response body, request configuration or headers; they do not retroactively establish the cause of older logs.
- HTTP 400/413 context-window rejections are detected from provider error codes/messages, including JSON bodies returned as streams by Axios. Error-body reads are limited to 64 KiB and two seconds; diagnostics indicate truncation or a failed read. A recognized rejection preserves the original transport error and stack, adds the exact provider message, and sets `code: "LLM_CONTEXT_LIMIT_EXCEEDED"`, `isContextLimitError: true`, and `nonRetryable: true`. It writes one bounded diagnostic without request headers or payload and throws on the first failed attempt, before adaptive streaming fallback. Native tool loops and TinyBrain therefore propagate the context error instead of retrying an identical oversized request or reporting an empty-response parse failure. Ordinary parameter errors and retryable network/rate-limit failures retain their existing retry policy. The client never truncates prompt context or increases the configured context window automatically.

## Prompt Progress And Cancellation
Prompt progress is active when output is not `silent` and either an interactive terminal or `Globals.realtimeHub.emit(...)` is available.

All real transports participate, including configured non-streaming requests and
adaptive/token-chunked non-stream batches. A JSON request appears while waiting;
its preview and decoded-character count update only when actual response content
arrives, excluding any echoed assistant prefill. Batches report returned content
without synthesizing streamed tokens and release their progress-stage ownership
after token inspection, before continuations or response/domain callbacks;
early branch corrections also release their stage before retrying. Grouped batches preserve cumulative
counts through the existing group lifecycle. JSON requests keep their Axios
request timeout and never receive SSE start/continue deadlines; CLI progress and
streaming timeouts retain their existing behavior. `output: "silent"` remains
untracked.

For streamed llama.cpp/Strata requests, the existing progress meter also reports
context prefill separately. `return_progress: true` is added for routes identified
by explicit managed-local startup, llama router lifecycle, Strata runtime/handoff
or Strata prefix-cache configuration. Each original configuration source retains
its endpoint binding: later endpoint-only model overrides cannot inherit an
automatic provider capability from another profile. An unmanaged compatible
endpoint can opt in with the existing `ai.custom_args.return_progress: true`;
explicit `false` disables it. There is no hostname-based provider guessing.
Non-stream requests and CLI bridges omit this extension.

An enabled streamed stage starts with `progressPhase: "context"` and unknown
context fraction. Valid SSE `prompt_progress` reports provide `total`,
`processed`, optional `cache`, and optional `time_ms`; output exposes those as
`contextProgress: { total, processed, cache?, timeMs? }` and
`contextProgressFraction: processed / total` (unknown for zero total). Processed
already includes cached tokens. Counts must be finite and nonnegative, with
`cache <= processed <= total`; invalid reports fail with a field/value diagnostic
outside the JSON-decoding catch.

Context updates refresh the native **start idle** timeout while leaving TTFT's
first-generated-output timestamp, output counts, response previews, and
continuation deadlines untouched. Empty role, keepalive and usage frames do not
change phase or count as output. The first generated content, reasoning or
nonempty tool-argument fragment uses the existing generated-output classifier
to switch to `progressPhase: "response"`, clear context fields, and start the
normal continuation timeout. Late context reports cannot switch it back.
Short or fully cached streams need no prefill report before generated output;
non-stream/batched fallback and CLI requests always use response progress.
Strata also omits these reports when its engine batching is enabled; the context
fraction remains unknown until generated output begins in that mode.

Every new transport/checkpoint resets only its context state through the native
progress-stage lifecycle. Group cumulative response counts, character targets,
output statistics, failed-response history, completion/waiting state and
cancellation ownership retain their existing behavior. `progressFraction`
continues to represent normal output progress independently of the context
fraction; clients select the current phase when rendering the same meter.

Progress entries include:
- `id`, `label`, `model`, elapsed seconds, timeout seconds, retry count, and background flag.
- `promptText` from `formatMessagesForPromptProgress(...)`, which labels each request message and preserves chronological system/user/assistant/tool order. This keeps the current staged user checkpoint immediately before its live response in the prompt viewer. Error-log formatting remains separately grouped by system, user, and other messages.
- `previewText` from streamed assistant text, returned JSON assistant content, or CLI bridge assistant-content events.
- `progressGroupId`, `failedResponses`, and `responseFailed` when a logical staged prompt groups requests and reports parse failures.
- `receivedCount` and `receivedUnit`; OpenAI-compatible streaming/non-streaming and CLI bridge progress count decoded characters.
- `progressPhase`, `contextProgressFraction`, and `contextProgress` as described above; prefill tokens never inflate decoded response-character totals.
- `targetCharacters`, `progressFraction`, `runCount`, and `averageOutputCharacters`.

Cold-start targets come from `config.prompt_progress.character_targets`. Label matching normalizes metadata labels; exact entries win over `*` prefix entries. A prompt label without an exact or prefix match uses 5,000 characters, as does a configuration with no character-target map. Explicit malformed, non-finite, or non-positive configured targets still fail before transport. The default family prefixes cover both direct and derived TinyBrain labels, including `creative_mode_action_tinybrain` and the scheduled-event resolution/interruption groups. When a positive stored average exists for a prompt label, that average is used as the target for the next run, including labels using the cold-start default. Progress advances linearly to 75% at the target and approaches 100% asymptotically after that.

High-frequency progress broadcasts are coalesced to at most one active update every 500 ms. Ordinary completion sends an immediate `progressFraction: 1` update, holds the completed entry for 250 ms, then emits the clear event. A grouped completion instead keeps its stable entry alive with `isGroupWaiting: true`. Its decoded-character `receivedCount` accumulates across requests while `targetCharacters` remains the one multiprompt target selected when the group first starts. Grouped progress uses the same curve as an ordinary prompt: it reaches 75% at the historical/configured target and approaches 100% asymptotically beyond it. Starting another stage cannot lower the percentage because both cumulative received output and the fixed target are preserved. The next request with that group id reactivates the same entry while resetting only stage-local prompt, preview, latency, timeout, and rate state. Grouped sub-requests do not write individual output-stat samples. `clearPromptProgressGroup(..., { recordOutputCharacters: true })` records one aggregate whole-run sample after a successfully completed group, then performs the final 100% completion pulse and removal; failures and explicitly non-recordable action rejections clear without affecting the expected-total history. The shared non-TinyBrain chat-tool loop owns one such group whenever it is not already inside a caller-owned group: after a model returns tool calls, the bar remains at its accumulated percentage in blue during tool execution, then the next model round resumes the same entry. Nested prompts launched by those tools inherit the group as well. `chatCompletion(...)` releases any still-owned stream stage in its finalizer before control returns to tool execution, so a legal outer request -> nested tool prompt -> resumed outer request sequence cannot be mistaken for concurrent stage ownership. Genuine overlap still fails explicitly. Prompt-progress `id` values are the ids accepted by `cancelPrompt(...)` and `retryPrompt(...)`; grouped waiting entries have no active abort controller until their next stage starts.

`recordPromptProgressGroupFailure(...)` force-broadcasts the updated progress entry and also emits `prompt_progress_group_failure`, allowing the browser to recolor a failed response even if the completed stream entry has already left the normal 250 ms hold window. The failed text is display metadata only and is not added to request messages.

## Internal prompt message boundaries

Every `base-context.xml.njk` render places an internal end marker after shared context and before the task include. For non-generic prompts, `chatCompletion(...)` replaces it with two consecutive `user` messages; generic prompts retain one message. Caller tool definitions are preserved here rather than expanded to a shared player-action schema.

Every actual provider/bridge payload filters definitions to the current executable names. Explicit allowlists, `allowToolCalls: false`, original `none` hints, TinyBrain checkpoint restrictions, correction policies, exhausted budgets and `chat_tools.mutating_prompts_only` all apply. Empty permissions omit `tools`, `functions` and parallel flags, with `tool_choice: "none"`, and add no generated tool-permission message. Restricted permissions expose only that subset; any generated guidance lists only exposed names. Unrestricted scopes need no guidance. Forbidden native responses are rejected before capture/response callbacks and retried within the normal completion budget; exhaustion propagates a policy error. Task-only permission guidance preserves requested XML/structured plans and never enters retained conversation history.

Caching-enabled base-context templates also place repeatable section markers between complete top-level context sections and a dedicated marker immediately before `<recentStoryHistory>`. The section boundaries cover older history when present, the world index, current region, current location when present, player, party, supplemental prompt context, and mystery/tracker continuity state when present. Before system-prompt append text, cachebusting, progress display, or backend transport, `chatCompletion(...)` replaces those markers with consecutive `user` messages. Message boundaries alone do not guarantee a backend checkpoint at every section. The cache remains prefix-based: content after the first changed section still requires evaluation. Expansion accepts at most 12 section markers plus one recent-story marker, preserves later assistant/tool/user chronology, and leaves cachebusting on only the final user message. Internal markers are never sent to the model. Markers in non-user messages, markers spread across multiple source messages, duplicate recent-story markers, excessive section markers, and empty content between markers raise explicit errors.

The boundary before scene-specific mod contributions and `<currentRegion>` is the dedicated stable-context marker (`getStableContextMessageBoundaryMarker()`). It follows older history, NPC/world index and factions. Default mod contributors retain their early placement; mods can explicitly put volatile scene references after this boundary through the registry's `scene` placement. `expandPromptMessageBoundaries(messages, { onStablePrefixBoundary })` passes the first message after this boundary to the optional callback. The stable marker counts toward the same 12-section limit and may occur only once.

`ai.shared_prefix_cache: { provider: "strata", endpoint: "http://127.0.0.1:8080/v1/chat/completions" }` explicitly opts that OpenAI-compatible endpoint into Strata's existing `strata_prefix` API. The default is `null`. `resolveSharedPrefixCacheConfiguration(...)` rejects unknown options/providers, malformed URLs, embedded credentials, incompatible backends and an endpoint different from the effective AI configuration. Prompt-specific endpoint overrides must clear the capability with `null` or provide a matching capability. A differing direct endpoint argument also fails explicitly; no endpoint-name heuristic identifies Strata.

For opted-in non-generic base-context requests containing the stable marker, `applySharedPrefixCachePolicy(...)` finds that captured boundary message in the final request list after system append, cachebusting and assistant prefill, then sends `strata_prefix: { messages: K }`. `K` includes all leading messages, including additional system messages, and leaves scene context and the task outside the pinned prefix. No hardcoded message count or token estimate is used. A manual `strata_prefix` conflicts with the enabled capability and throws. Requests without the stable marker (including disabled shared-context caching), without base context, generic editing prompts, and image-bearing requests receive no automatically generated Strata field. Other providers and CLI bridges retain their payloads when the capability is absent. Retries and TinyBrain/native tool continuations reuse their real normalized transcript, so the pin remains before the same scene boundary without changing tools, roles or execution permissions. An earlier changed world/history/system/tool prefix still invalidates reuse; pinning cannot skip it. Backend conversation-state parking capacity is independent of this transport hint.

TinyBrain runs own an immutable snapshot of original execution definitions and mutation eligibility, selected before the first checkpoint. `withTinyBrainToolSchema({ metadataLabel, queueReservation, toolDefinitions, shareBaseContextTools }, callback)` owns it. Omitted definitions default to `[]`; `shareBaseContextTools` never grants permissions or expands definitions. Explicit checkpoint definitions must be unchanged subsets of the original scope. Only the normalized metadata label plus opaque reservation identifies a matching run; unrelated/nested requests remain isolated. Reinitializing an active scope fails explicitly.

Each completion exposes only currently executable definitions. A no-call destination checkpoint, correction or exhausted budget exposes none. Subset checkpoints expose that exact subset; mutation-capable runs retain their eligibility when narrowed to lookup-only checkpoints, while lookup-only runs remain disabled under `mutating_prompts_only`. `getTinyBrainToolChoice(...)` reports the original run’s default choice or `null` outside the scope; it does not override current permissions. Changing tool exposure can invalidate the provider’s early prefix cache.

`getTinyBrainToolExecutionState({ metadataLabel, queueReservation, maxToolCalls })` returns one mutable transient state for the matching run, or `null` outside it. The first loop fixes the positive integer limit; changing it fails. State includes original execution names/eligibility, individual attempted/used counts, negative lookup receipts and exhausted-lookup bookkeeping. Native budgets survive parser retries/checkpoints and remain independent of server-owned XML plan execution. Exhausted payloads advertise no native tools, and unexpected native responses are rejected before callbacks.

TinyBrain player/NPC actions use only their original information lookups; creative actions use enabled prose tools; scheduled-event planning uses its non-mutating native subset. Other families expose none. Player check/attack and scheduled-event plans retain their separate server-side validation/execution contracts. Under `chat_tools.mutating_prompts_only`, lookup-only native scopes disappear while those plans continue normally.

`chatCompletion({ executionAllowedToolNames })` accepts `null` or an array of nonempty names. Native loops supply their authoritative allowlist, including `[]` at budget exhaustion. This option filters wire exposure and supports guidance/rejection; it never introduces a second executor or expands a caller’s definitions. Without it, the client uses the matching TinyBrain scope or original caller definitions. No-call/correction restrictions take precedence.

## Concurrency
`LLMClient` keeps a semaphore per backend/model/auth/session key, plus an optional process-wide semaphore when root `max_concurrent_requests_all_models` is set.

- OpenAI-compatible keys use the resolved API credential or OAuth cache key plus model.
- Codex fresh-mode, Cline, and Kimi bridge keys use backend plus model identity and honor `ai.max_concurrent_requests`.
- Codex resumed-session keys serialize by Codex home and, for `resume_id`, session id.
- The all-model semaphore caps real outbound text-generation attempts across every key. It is acquired only after the per-key permit so a request waiting on a busy model does not occupy an all-model slot.
- `runInBackground: true` lowers queue priority and limits concurrent background occupancy so foreground gameplay prompts can start ahead of queued background prompts.
- `withPromptQueueReservation(...)` retains one current per-model lease and its optional all-model permit until its owning callback completes. Explicit child scopes share that owner, with release-before-wait model handoffs when their targets differ. Other genuinely free configured slots remain available; without an all-model cap, independent model queues remain independent.
- `withPromptQueueReservationYield(...)` releases retained permits only around deliberate human-input waits and reacquires them at the front before the staged caller resumes. Internal prompt-launching tools, parser authoring and correction work retain ownership through `withPromptQueueReservationNested(...)`.
- Reservations reject explicit concurrent reuse outside an owned scope, active-callback self-recursion, all-model concurrency changes, invalid/released ownership and recursive yields. Nested children use their owner's priority. Permits release in `finally` on success, failure or cancellation; cancellation also aborts queued reacquisition after human waiting.
- The model-lifecycle gate permits concurrent ordinary requests. Exclusive image-render lifecycle access waits for active readers, then prevents queued/new text requests from dispatching until the llama.cpp model reload attempt finishes.

## Prompt Logging
Every real transport attempt now emits a threshold-free, request-scoped timing row to `logs/completion-timing-YYYY-MM-DD.jsonl` and the server console. Use `completionId` plus `attempt` to correlate retries; owned gameplay requests also include their request/audit/prompt IDs. `ttftMs` is dispatch to first generated streamed content, while non-streaming responses use `firstResponseMs` or `firstChunkMs`. Preparation/queue, transport remainder, retry backoff, and overall elapsed time are separate fields. See [PromptAuditLog](PromptAuditLog.md#initial-output-latency) for the field definitions.

Enabled XML guards also feed the existing per-turn [XML enforcement audit](PromptAuditLog.md#xml-enforcement). Actual transport dispatches (including continuations), selected sampled/forced corrections and guard failures are grouped independently of error totals. The common guard callback covers standard/TinyBrain and both transport modes, without copying generated text or sampled tokens. Selection does not imply successful application. Nongenerated fixtures and disabled guards have no activation rows; ownerless requests keep their detailed diagnostics without joining a turn.

`LLMClient` sends completion lifecycle events through one `PromptAuditLog.beginCompletionObservation` instance. It composes the thresholded logical-startup audit and per-transport timing recorder, handles provider metadata extraction, and brackets retry delays. The functional response usage and finish-reason values still drive validation, continuations, callbacks, and usage reporting independently of the diagnostic row.

The same attempt row records the model, effective `max_tokens`/`max_completion_tokens` and stop settings, raw provider response ID and finish reason when available, and numeric token usage. The response ID can correlate an OpenAI-compatible request with a provider-side trace. It is written before a caller's later domain parser can reject the response. A CLI bridge's synthetic normalized response ID and finish reason are deliberately excluded; bridge usage is retained when supplied. Streaming usage-only and finish chunks update the current attempt even if a later step fails.

Every actual completion also measures its initial wait through [PromptAuditLog](PromptAuditLog.md), using the current full-prompt or TinyBrain section owner. One tracker spans preparation, queueing, transport retries and chunked continuations. Real streaming text/reasoning/function output ends the wait; headers, keepalives and usage-only updates do not. Non-streaming results are labeled first response/chunk rather than first token. The configurable inclusive threshold defaults to five seconds, and slow waits are separate from failures. Forced outputs and cassette replay without transport are excluded.

`logPrompt(...)` writes `logs/<timestamp>_<prefix>_<metadataLabel>.log` with:
- prompt output-character stats header.
- model, endpoint, and token metadata when available.
- request and response JSON payload sections when supplied.
- system prompt, generation prompt, reasoning, custom sections, and response text.

For incremental logs, pass the path returned by the first call back as `filePath` with `append: true`. Append targets must already exist inside the runtime `logs/` directory. `markResponseBoundaries: true` writes explicit `BEGIN` and `END` headings around the response; `responseLabel` customizes the heading. The tiny-brain player-action runner uses these options so an entire staged conversation occupies one file.

Adaptive live-token failures invoke `onLiveTokenStreamFallback` before the non-stream retry begins. The player-action integration appends that diagnostic to the associated prompt log, including the server response and backtrace when present, so terminal scrollback is not the only record of why fallback was latched.

`writeLogFile(...)` writes error files under `logs/` using sanitized labels. It serializes `Error` objects, including retry metadata (`attemptNumber`, `maxAttempts`, `willRetry`) and common Axios/custom error fields. Chat tool failures use this path for structured `ERROR_tool_call_failed_*` JSON logs. Successful XML-guard selection diagnostics use this writer's `payload` argument; `sections` belongs to `logPrompt` and is not accepted here.

## Prompt Output Character Stats
Successful `chatCompletion(...)` calls record the final assistant text length in decoded characters under `logs/prompt-output-character-stats.json`. Tool-call-only completions do not update averages.

The stats file has `version: 1`, is validated on load, and is written atomically via temp-file rename. Invalid JSON, unsupported versions, non-normalized keys, invalid numeric values, or inconsistent zero-run entries throw. Character-appended labels for `inventory_generation`, `npc_memories`, `npc_progression_assignments`, `npc_ability_assignments`, and `npc_alias_assignments` aggregate under their base label, including compatible persisted per-character entries.

`listPromptOutputCharacterStats()` includes stored stats and configured prompt-progress target labels. `clearPromptOutputCharacterStats()` replaces the stats file with an empty validated file and returns the cleared prompt count.

## Deterministic Outputs
Per-call `forceOutput` accepts either a string or a response-shaped object with `content`, `message`, `choices`, `tool_calls`/`toolCalls`, `finish_reason`/`finishReason`, `model`, `id`, and `usage` fields where applicable.

Explicit deterministic output and file-fixture lookup can run without `Globals.config.ai`. Automatic live-token guard setup skips explicit output before resolving a provider profile; file fixtures without a profile proceed to their strict lookup. A fixture miss that attempts real transport still requires normal provider configuration. Final XML/domain validation and forbidden tool-call checks remain active for deterministic responses.

Forced-output fixtures are loaded from `LLM_FORCE_OUTPUTS_FILE` or `ai.force_outputs_file`. Fixture groups can live under `byMetadataLabel`, `labels`, `outputs`, or top-level keys. Label lookup tries the raw label, normalized label, `unknown`, `prompt_<label>`, and ordered `<label>_group_N` buckets. Fixture strict mode is enabled unless `strict: false`; in strict mode, missing buckets and exhausted buckets throw.

Version 2 completion cassettes instead contain `strict: true`, `complete: true`, and one globally ordered `entries` array. Each entry stores its ordinal, normalized metadata label, SHA-256 semantic request fingerprint, a compact non-secret request summary, and the normalized response-shaped result. The fingerprint covers the provider-visible messages after internal boundary processing, tool definitions and policy, model/backend routing, stable generation controls, assistant prefill/system append text, and the response-validation contract. Canonical object keys make equivalent JSON stable; array order remains significant, and data URLs are replaced by hashes. Secrets, request IDs, headers, generated cachebusters, and generated seeds are not stored. JSON tool-result messages are canonicalized and omit runtime-only `createdAt`, `lastUpdated`, request/client-id, and cachebuster keys, while their entity ids, names, mechanics, and other semantic fields remain fingerprinted.

Recording writes the whole valid JSON document through a same-directory temporary file and atomic rename after every accepted logical completion. `LLMClient` serializes cassette-backed logical completions through one process-wide permit so independently launched event, need-bar, status, and queue prompts receive an unambiguous global order. A normal unreserved call holds the permit for that one logical completion. `withPromptQueueReservation(...)` retains it for the entire reserved staged program, including the gaps between TinyBrain checkpoints; explicit nested prompt-launching work reuses that same permit. Only `withPromptQueueReservationYield(...)` yields and reacquires it with the model permits around human-input waiting. This prevents a later prompt from interleaving between stages or deadlocking behind a reserved parent. The lower-level `LLMCompletionCassette` module still rejects direct concurrent begin calls, which catches callers that bypass `LLMClient`. Recording captures parser retries and repeated TinyBrain labels separately, preserves tool calls for normal execution during replay, and becomes promotable only after `completeCompletionCassetteRecording(...)` writes the completeness marker. `resetIncompleteCompletionCassetteRecording(...)` requires an idle recorder and atomically replaces only an incomplete version 2 document with a fresh empty recording; it refuses completed cassettes so acceptance evidence cannot be silently overwritten. After a process restart, recording startup may claim that reset destination only when it validates as strict version 2, incomplete, and empty. It still refuses completed, nonempty, malformed, or legacy files.

Replay checks the next entry's label and fingerprint before consuming it, never falls through to a legacy bucket or provider, and rejects malformed/incomplete files, mismatches, concurrent calls, and exhausted traces. Every replay failure is latched in status until reset; final consumption assertion fails even if later work happens to consume the remaining entries. Scenario callers must additionally assert that every entry was consumed and the serialization queue is empty. The existing normalization, XML/regex validation, callbacks, tool-loop behavior, and prompt statistics still run on replayed responses.

## Codex Usage And Quota Reporting
When the Codex bridge response includes normalized `usage`, `LLMClient` writes a server-console usage line for that prompt with input, cached-input, output, and total token counts.

Cline and Kimi bridge responses do not currently report quota usage because their CLI JSONL streams do not guarantee token-usage metadata.

Quota snapshots are based on unique gameplay-turn metadata rather than raw prompt count. A prompt counts only when `metadata.__codexQuotaCountAsTurn === true` and `metadata.__codexQuotaTurnKey` is a non-empty stable string. Duplicate keys are ignored; a missing key with counting enabled throws. Every fifth counted turn calls `CodexBridgeClient.readRateLimits(...)`.

When a rate-limit snapshot contains multiple buckets, reporting prefers an exact active-model bucket, then the generic `codex` bucket, then the first available bucket. Successful quota reads append a visible `status-summary` chat entry titled `🌀 Codex Quota` through `Globals.appendChatEntry(...)`; the entry is marked `metadata.excludeFromBaseContextHistory = true`. Quota read or chat-notice failures warn to the server console and do not fail the completed prompt.

## Current Call Patterns
- `/api/chat` uses `player_action`, `question`, `generic_prompt`, and `generic_prompt_nocontext` labels, passes chat tools through `additionalPayload`, and uses `metadata.__codexQuotaCountAsTurn` only for player-action turns.
- Silent housekeeping prompts call `LLMClient.chatCompletion` as plain XML generation. They expose no native tool definitions and do not run a model tool loop. The returned `<housekeeping>` XML is parsed and applied afterward by `Events.js`, so tracker, quest, and relationship maintenance does not depend on provider-emitted tool calls.
- XML output with no available native tools rejects actual `<tool_call>` elements inside the first declared root, or across the existing generic XML scope when no root is declared. The policy uses each attempt's filtered payload, including disabled/exhausted tools and TinyBrain checkpoint restrictions. Live sampled output and EOS alternatives share the check; completed output is scanned before response callbacks and root extraction even with live guarding disabled or forced/cassette output. Comments, escaped text and CDATA are literal; explicit `xmlOutput:false` scopes bypass this XML policy. Failures preserve the element path and instruct the model to return the requested XML without tool-call elements. See [XmlClosingTagGuard](XmlClosingTagGuard.md).
- `chat_tool_calls.js` relies on `onResponse` to inspect normalized tool calls across multiple tool-loop rounds, and logs tool-loop rounds with `LLMClient.logPrompt(...)`. Explicit request tool definitions double as the executor allowlist; an undeclared provider-emitted call becomes a retry-visible `tool_not_declared` result without executing or mutating state.
- `Events.js` uses labels such as `event_checks`, `need_bar_event_checks`, `quest_check`, `mystery_thread_check`, `mystery_box_update`, `alter_location`, and `alter_npc`, with regex/XML validation on structured prompts.
- `server.js` uses the client for generation, summaries, image-prompt writing, NPC/item/location/region creation, and background prompts. Region/location/item/character generation prompts currently use direct tool-free completions; the dormant generation helper can restore a restricted tool loop if a tool is deliberately re-enabled. Background prompt callers set `runInBackground: true`.
- `StatusEffect.js` uses `status_effect_generate` and logs the rendered prompt/response through `LLMClient.logPrompt(...)`.
- `scripts/run_prompts.js` disables XML validation, accepts an optional required regex, and logs each run through `LLMClient.logPrompt(...)`.

## Scoped completion ownership

`chatCompletion` optionally accepts AbortSignal `signal`, synchronous `onPromptId(id)`, and `throwOnError:true`. Scoped cancellation reaches queued semaphore/model-lifecycle work and active stream/nonstream transport; it is terminal, releases owned permits and does not cancel other requests. External abort reasons and prompt-lifecycle callback errors propagate with original stack. Prompt IDs notify the caller as attempts become progress-visible. `throwOnError` preserves exhausted provider errors instead of returning an empty response; existing consumers keep their default behavior. Story generation uses these narrow generic hooks and logs every request/correction/failure. Deterministic forced output alone does not exercise transport cancellation; verify with an isolated local provider.

Scoped signals also cancel acquisition of model/all-model permits within a queue reservation and reserved cassette serialization permits. Joint model/global acquisition consumes no partial capacity while queued; reservation ownership remains with its surrounding callback and is released by the existing reservation lifecycle.

For the XML guard, explicit terminal logprobs are inspected after the final raw
text/assistant prefill and usage are assembled. An actual premature EOS permits
an append branch at the response end; ordinary token rewinds remain strictly
inside the response. Native tool turns skip this EOS decision. Continuations
share a finite original output cap plus a retry-policy-derived EOS round limit,
while ordinary new attempts reset those counters. See
[XmlClosingTagGuard](XmlClosingTagGuard.md#actual-eos-with-incomplete-xml).

`xmlSchema` explicitly selects a named file for the active XML token guard;
`xmlSchemaExtensions` accepts compiled named fragments or a lazy provider, and
`xmlSchemaDirectory` supplies an isolated file root. The same options flow through
`withXmlOutputScope`. Synthetic structural decisions carry no sampled token record,
respect cancellation/token/round bounds and leave final validators enabled. See
[XmlGenerationSchema](XmlGenerationSchema.md).

Named-schema guard hooks may return `documentComplete` with an exact prefix. Shared stream/non-stream transport validates that decision, preserves cancellation and native-tool handling, and continues through ordinary response/domain validators. Verified EOS may add only schema-derived structural tags; ordinary root cutoff inserts nothing. Crossing sampled records are discarded whole, while sampled output and raw provider metadata remain honest. Schema-capable prose hooks receive one final completed-prefix inspection. Local completion uses separate detail-log prefixes from branch correction and separate compact audit completion counts.
