# TechniqueFormulaVariables

`public/js/technique-formula-variables.js` is shared by Node and the browser (`module.exports` / `window.TechniqueFormulaVariables`). It uses the existing FormulaEvaluator name normalizer rather than duplicating naming rules.

- `catalog(actor)` returns `{key, label, kind, name?, value}` rows for `actor.level`, every `getSkills()` entry resolved through `getSkillValue(name)`, and every `getAttributeNames()` entry resolved through `getAttributeModifier(name)`. Skill collections may be Maps or plain objects. Values must be finite numbers. Duplicate canonical keys throw an ambiguity error naming both sources.
- `keyFor({kind, name?})` returns `level`, `skill_<normalized_name>`, or `attribute_<normalized_name>_modifier`. Names normalize to lowercase alphanumeric runs separated by underscores; empty normalized names reject.
- `isCanonical(key)` checks supported identifier syntax without claiming that the character owns the corresponding fact.
- `resolve(formula, actor, bindings?, label?)` resolves only referenced inputs from current authoritative facts. Unknown automatic identifiers reject with the field label. Explicit saved aliases take precedence over automatic names; named saved sources match case-insensitively and missing/ambiguous sources reject. Numeric values supplied by the browser are never authoritative.
- `canonicalize(formula, bindings?)` simultaneously replaces saved alias identifiers with canonical identifiers, preserving calls and avoiding chained replacements. The technique editor uses this when editing saved formulas; serialization/hydration retain old explicit maps unchanged.

Technique normalization validates canonical syntax without needing an actor. Preview, acquisition, personal save and execution validate actual facts and results. Catalogue creation validates with its selected/current actor. Execution recalculates against the caster, so another character's rank/level/modifier and later stat changes are reflected automatically. Saves retain formula references, not current scalar values; receipts retain their resolved inputs as the historical calculation evidence.

The formula table consumes the server catalogue from `GET /api/techniques` (`formulaVariables`), and generation receives the same catalogue through `TechniqueService.getPromptContext`. The shared base context uses `getCompactPromptContext`: canonical keys, kinds and exact source names occur once in `formulaVariableSchema`, while each actor's `formulaVariables` maps its available keys to current values. Actor-specific key subsets remain authoritative; a schema entry does not grant that variable to every actor. UI labels and repeated balance facts are omitted. Costs, failure costs, damage/healing and signed status modifiers share this resolution contract. No arbitrary object/property access, JavaScript evaluation, implicit rounding or clamping is introduced.
