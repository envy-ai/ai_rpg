# Events

## Purpose

Runs LLM-based event checks on narrative text, parses structured outcomes, and applies those outcomes to the game world (locations, items, NPCs, quests, and status effects). Tracks discovered/altered entities to avoid duplicates.

For a full reference of non-dummy event type keys, payloads, and application behavior, see [EventsEventTypes.md](EventsEventTypes.md). For the single-prompt XML event format, see [EventsXmlEventSchema.md](EventsXmlEventSchema.md).

## Key State (Static)

- Dependency container: `_deps` (promptEnv, parseXMLTemplate, prepareBasePromptContext, Location, players, things, findRegionByLocationId, backfillRegionExitTravelTimes, config accessors, etc).
- Parsers/aggregators/handlers: `_parsers`, `_aggregators`, `_handlers`.
- Mod extension registry: `Globals.modExtensionRegistry` or `_deps.modExtensionRegistry` for registered XML tags, parsers, and handlers.
- Tracking sets: `animatedItems`, `alteredItems`, `newItems`, `obtainedItems`, `destroyedItems`, `droppedItems`, `alteredCharacters`, `newCharacters`, `arrivedCharacters`, `departedCharacters`, `defeatedEnemies`, `movedLocations`.
- Timeouts and durations: `_baseTimeout`, `DEFAULT_STATUS_DURATION`, `MAJOR_STATUS_DURATION`.

## Public API (Static)

- `initialize(deps)`: registers dependencies and builds parsers/aggregators/handlers.
- `createTinyBrainEventSequence()`: creates a turn-scoped continuation state used to keep sectioned TinyBrain event checks in one model transcript and prompt log.
- `runEventChecks({ textToCheck, actionText, stream, allowEnvironmentalEffects, isNpcTurn, suppressMoveEvents, allowMoveTurnAppearances, suppressTimeAdvance, locationOverride, ignoredEventKeys, eventCheckIgnoreInstructions, suppressNeedBarEventChecks, suppressHousekeeping, eventSectionKind, eventMode, suppressTrackerUpdates, tinyBrainAcceptedEventXml, tinyBrainEventSequence, initialTimeProgress, _depth, followupQueue })`:
  - When `event_checks.use_xml !== false`, renders one `events-xml` base-context prompt for ordinary event categories, launches the dedicated `need-bars` prompt after the configured stagger when need-bar definitions are present, waits for both, parses the required `<events>` block, converts camelCase XML tags into handler-compatible structured event entries, injects parsed need-bar results as `needbar_change` entries, and applies results through the shared handler pipeline. If the XML contains a travel boundary, events before the move are applied at the origin, the move applies separately, in-transit tags before `<arriveAtLocation/>` are ignored except `thingMoveWithCharacter`, which is deferred to the destination phase, and post-arrival tags apply at the destination with move-turn appearances allowed.
  - When `event_checks.use_xml === false`, renders the numbered grouped event-check prompts plus a dedicated parallel need-bar prompt launched after `Events.resolvePromptLaunchStaggerMs()`, calls `LLMClient.chatCompletion`, parses `<final>` and `<characters>` responses, and applies results through the same handler pipeline. `locationOverride` lets split travel-prose checks run destination prose against the destination location even before the player is mechanically moved.
  - For every `housekeeping.interval`th eligible top-level XML or legacy event-check pass, schedules the registered silent housekeeping prompt and runs it after event outcomes and follow-up checks finish. Waiting for finalized outcomes lets the prompt include the current turn's formatted event results alongside its action and prose. It does not store its assistant response in chat history. It serializes the shared non-generic base-context tool schema for cache stability, receives `Do not make tool calls.`, and does not run a model tool loop. When `debug_tool_calls` is enabled, XML-derived synthetic tool executions are mirrored into the standard prompt-excluded `tool-call-debug` chat entry. Recursive `_depth > 0` event checks and callers with `suppressHousekeeping: true` skip housekeeping without advancing its interval counter.
- `runQuestChecks({ allowWithoutEventChecks, recentTextOverride, bypassInterval })`: LLM check for quest objective completion, including per-objective prompt `statusReason` text for completed objectives. Skips prompt construction and returns `null` when the current player has no active, unpaused quests or the current eligible call is not due under `quest_checks.interval`; `bypassInterval: true` validates but bypasses only the interval gate.
- `eventResultIndicatesAnyQuestObjectivesCompleted(eventResult)`: reads the normalized boolean signal from a normal or split/merged event result.
- `resolveEventSignaledQuestCheck({ eventResult, existingQuestResult })`: returns the existing same-turn quest result when available, otherwise performs one interval-bypassing check for a true event signal, and resets the quest counter after a successful result.
- `applyEventOutcomes(parsedEvents, context)`: applies structured changes to world state.
- `processQuestObjectiveCompletionEntries(entries, context)`: applies quest objective completion and rewards (items/xp/currency, per-faction reputation deltas, and per-NPC disposition deltas when configured on the quest), preserving the prompt-supplied completion reason on emitted objective updates. Quest NPC disposition reward intensities are converted through disposition `typicalStep` / `typicalBigStep`; the first-impression multiplier may further multiply the applied delta when the target NPC has no existing nonzero disposition toward the player.
- `mergeQuestOutcomesIntoStructured(parsedEvents, questOutcomes)`.
- `extractItemAndSceneryNames(rawEvents)`.
- `resolveLocationCandidate(candidate)`.
- `addThingToLocation(thing, candidate)` / `removeThingFromLocation(thing, candidate)`.
- `cleanEventResponseText(text)` / `escapeHtml(text)`.
- `logEventCheck({ systemPrompt, generationPrompt, responseText, label, requestPayload, responsePayload })`.

## Notes

- The default event-check path is the XML pipeline (`event_checks.use_xml: true`): `runEventChecks` renders `prompts/_includes/events-xml.njk` through `base-context.xml.njk`, logs normal prompt/response files under the `event_checks_xml` prompt prefix while retaining the `event_checks` metadata label for model overrides, writes chat-completion error logs with the `events-xml` prompt label, and requires a parseable `<events>...</events>` block. Surrounding markdown fences are tolerated by extracting only the XML block.
- When `ai.tinybrain` is enabled, the XML path renders `prompts/_includes/events-xml.tinybrain.njk` and runs it through `TinyBrainPromptRunner`. `CURRENT`, `ORIGIN`, and `DESTINATION` sections ask separately for scene/location, item/inventory, character/presence, combat/recovery, and quest/progression events, followed by a final non-tracker sweep. A `BETWEEN` section permits only `thingMoveWithCharacter`; tracker-only runs permit canonical tracker-update XML after all movement sections. Sectioned calls share one `tinyBrainEventSequence`, refresh the transcript's one base-context snapshot in place, retain earlier questions and accepted XML, and write to one log. Every category requests one `<events>` block, with `<events><done/></events>` (or the accepted legacy bare `<done/>`) representing no event. A lone allowed root may be wrapped locally, while malformed XML, multiple roots, disallowed tags, missing fields, required-tag omissions, and real semantic contradictions still fail and retry. TinyBrain omits movement-boundary documentation and silently discards stray `moveLocation`, `moveNewLocation`, and `arriveAtLocation` tags because player-action owns movement. It likewise does not burden the prompt with companion/ownership deduplication rules: exact repeated accepted events, companion arrival/departure events already covered by authoritative player movement, `thingArrival` for an already owned/contained/current-location thing, repeated existing status gains, nonexistent status losses, and status gains already applied by an item are suppressed as safe no-ops. They are not returned from local XML assembly and do not consume a parser retry. The shared `dropItem` documentation retains its general drop/place/set-down meaning. Item/healing/status events targeting a dead actor still fail because the schema has no resurrection operation. A zero-health defeated actor must receive one model-chosen `dead` or `incapacitated` outcome; zero health does not force death. Item checkpoints also validate structured consume/container quantities against live stock without scanning prose. The final ordinary-event checkpoint requires `inCombat` and `anyQuestObjectivesCompleted`. A terminal `llmresult('event_xml_result')` assembles only accepted fragments locally.
- Completed-quest reward narration uses the `quest_reward_prose` family when enabled. Its staged plan and draft must cover every indexed, already-applied reward exactly once; the strict final parser rejects missing, duplicated, reordered, or changed coverage. Reward mutation remains outside the runner, so checkpoint retries cannot grant items, XP, currency, faction reputation, or NPC disposition twice. Staged failures propagate instead of dropping into the legacy deterministic reward list; the one-shot path retains its existing warning-and-list behavior.
- Need bars remain separate from the XML schema prompt in normal operation. When need-bar definitions exist, the XML path launches `prompts/_includes/events-xml.njk`, starts `prompts/_includes/need-bars.njk` after `Events.resolvePromptLaunchStaggerMs()` (root `stagger_concurrent_prompts`, 4 seconds by default), waits for both prompts, and injects the parsed need-bar entries into the origin phase as ordinary `needbar_change` events before `applyEventOutcomes(...)`.
- Scoped callers can pass `suppressNeedBarEventChecks: true` to skip the dedicated need-bar prompt, `suppressHousekeeping: true` to skip the automatic housekeeping pass, plus `ignoredEventKeys` / `eventCheckIgnoreInstructions` to tell the event prompt to ignore categories and to hard-remove those keys before handlers run. The while-you-were-away integration uses these controls to run an event pass on return updates while ignoring `needbar_change` and `npc_arrival_departure`, because that prompt already parses need values and NPC arrivals/departures itself and the main turn already runs housekeeping.
- XML event tags are converted into handler-compatible raw event strings and parsed through the parser/aggregator map, so `applyEventOutcomes(...)` handlers remain authoritative.
- Item-triggered status changes retain their canonical applied-effect name and description in the turn outcome context. During TinyBrain extraction, the status checkpoint resolves accepted same-section `itemInflict`/`itemIngest` blocks against the authoritative item definition. A generated status gain that repeats the configured effect or merely renames it from the exact item name (for example, `QA Focus Draught effect`) is suppressed as a safe no-op, while an independently named status remains eligible. This validation reads accepted XML and authoritative item state only; it never classifies player-facing prose. The application handler also discards generated duplicates that exactly normalize to an already-applied item effect for the same actor. Sectioned XML runs carry suppressed parsed entries into their accumulator and remove them from the pre-application merged result before summary construction, so the status summary reports only the canonical item effect.
- Mod-registered XML event tags are accepted during XML parsing. Their direct child elements are converted to a JSON raw payload, parsed with the registered parser, and applied with the registered handler during the normal outcome pass. Unregistered XML tags throw `Unknown event XML tag`.
- XML `<trackerUpdates>` maps into `tracker_updates` and may be omitted when no trackers changed. The one-shot XML parser retains per-entry isolation and logs/skips malformed tracker children. TinyBrain validates every child at the tracker checkpoint and retries the whole tracker checkpoint if any child is malformed; it never assembles partial malformed tracker XML. Legacy grouped responses can also emit `tracker_updates` as `[tracker] -> [type] -> [add|update|remove] -> [value] -> [reason]`, and percentage values may include or omit `%`.
- XML `<npcArrival>` / `<npcDeparture>` tags map into the `npc_arrival_departure` parser/handler, XML `<thingArrival>` / `<thingDeparture>` tags map into `thing_arrival_departure`, and XML `<thingMoveWithCharacter>` maps into `thing_move_with_character`, so the split XML schema uses the same parser/handler semantics as grouped event entries. Before accepting a TinyBrain `<thingArrival>`, the stage parser resolves the referenced existing thing against authoritative placement state and retries if it is currently character-owned or inside a container; ordinary travel cannot turn carried or contained inventory into a destination-scene thing.
- XML `<npcArrival>` / `<npcDeparture>` may include `<hideFromPlayer>true</hideFromPlayer>`, which marks the arriving or departing living NPC hidden at their resulting location. XML `<revealHiddenNpc>` and `<hideVisibleNpc>` map into hidden-NPC event handlers. The XML event prompt includes reveal guidance and the tag in TinyBrain stage allowlists only when the current location has living hidden NPC records, listing their exact names. It tells the model to use `npcFirstAppearance` for a physically present actor missing from game data or `npcArrival` for an existing actor newly arriving. `npcFirstAppearance` is also the recovery path for a prose-revealed hidden NPC omitted from the supplied prompt data: before generation, exact-name and alias resolution can match a stored living hidden NPC, convert the first appearance into a no-check reveal, discard its derived arrival, and avoid generating, relocating, or tracking a duplicate. Explicit `npcArrival` events retain normal arrival semantics. TinyBrain rejects `revealHiddenNpc` targets absent from the authoritative list and retries with explicit creation/arrival/correct-name guidance. Valid reveal attempts ignore already-visible or dead NPCs, failed opposed checks do not reveal the target, and hide attempts run an opposed NPC-hiding vs player-perception check using the active world setting's configured attributes and optional skills unless the same player action already resolved the matching opposed check. That reuse is structured and one-shot across XML sections: actor and canonical opponent must match, configured skills identify skill-configured sides while allowing a valid alternate or omitted attribute, and attribute-only sides require their configured attribute. Reused results are not returned as new `hiddenNpcChecks`, so the chat layer records no duplicate roll. Dead NPCs/corpses are always treated as visible.
- XML `<mysteryBoxMention>` maps into `mystery_box_mention`. Before the private update prompt runs, the handler renders `prompts/_includes/mystery-thread-check.njk` through `base-context.xml.njk` when active mystery threads exist, logs it as `mystery_thread_check`, parses the returned `<resolvedMysteries>` block, marks matching active thread names inactive so capacity can open for new unresolved mysteries, and marks matching mystery-box names resolved. Unknown thread or box names warn to the console and are ignored. Resolved boxes remain persisted but are filtered out of active-thread base context and the mystery-box update prompt's active box lists. The handler then renders `prompts/_includes/mystery-box-update.njk`, exposes mystery-box and mystery-thread lookup tools (`listMysteryBoxes`, `findMysteryBoxes`, `getMysteryBox`, `listMysteryThreads`, and `getMysteryThread`), logs the prompt with `LLMClient.logPrompt()` under `mystery_box_update`, and creates or updates a persisted `MysteryBox` inside a `MysteryThread`. The returned `<name>` is the canonical mystery-box key. Returned XML can also use `<action>skip</action>` when active thread capacity is full and no coherent related thread exists. These prompts are reactive only: they record private continuity, but do not advance offscreen events or write player-facing prose.
- Periodic and manual mystery cleanup runs `prompts/_includes/mystery_box_cleanup.njk` through the same base-context wrapper. It receives explicit active thread and unresolved box ids, parses the returned `<mysteryThreads>` block with `_parseMysteryBoxCleanupResponse(...)`, summarizes resolved/revealed decisions against the prompt candidate ids with `_summarizeMysteryBoxCleanupDecisions(...)`, applies exact-id results with `_applyMysteryBoxCleanupResult(...)`, marks resolved threads inactive, and calls `MysteryBox.markResolved()` for revealed boxes. Manual `/resolve_mystery_threads` surfaces the returned thoughts for candidate ids the model marked resolved/revealed, even if another cleanup already applied the same state change; periodic cleanup logs warnings and does not interrupt the player turn.
- `tradeAvailability` / `trade_availability` entries update NPC barter availability through the same event pipeline. Setting an NPC unwilling stamps a temporary refusal expiry from `barter.refusal_duration_minutes`; setting them willing clears that expiry.
- XML travel boundaries are strict: one `moveLocation` or `moveNewLocation` requires one following `<arriveAtLocation/>`; multiple moves, orphan arrivals, or missing arrivals throw clear parse errors. Direct children before the move apply at the origin, the move applies separately and still uses route travel-time advancement, direct children between the move and arrival are ignored, and direct children after arrival apply at the destination with `allowMoveTurnAppearances: true`. Before a non-NPC cross-region move applies, Events runs the shared destination-region exit travel-time backfill so legacy `0`-minute exits can be populated before route duration is resolved. `thingMoveWithCharacter` is special inside any travel-boundary response: whether it appears before the move, during transit, or after arrival, it is applied in the post-arrival phase so carried/driven objects follow the moving character to the destination. When move events are suppressed for split travel-prose origin checks, the XML move target is still resolved for the arrival phase; the player is temporarily scoped to that destination while post-arrival handlers run, then restored to the pre-check location so the outer travel flow remains authoritative. If the move targets the active vehicle's scheduled destination while that vehicle is still underway, the move is suppressed as impossible, the event context stays at the onboard location, and prompt-authored `time_passed` may still advance the clock so normal vehicle-arrival finalization can run.
- `initialTimeProgress` carries already-applied action elapsed time into the outcome context. When present, `time_passed` / XML `timePassed` handlers leave that progress unchanged so event checks remain a fallback timing source instead of applying a duplicate clock advance.
- When event outcomes advance world time through `time_passed` or route-time movement, Events immediately runs `Player.applyStatusEffectNeedBarsToAll()` before `needbar_change` entries are applied. Event-based need-bar changes therefore resolve against the post-tick values instead of being followed by deferred elapsed-time drift on the next turn.
- The numbered grouped path (`event_checks.use_xml: false`) uses grouped prompts (locations/items and NPC/misc in the current grouping) and runs `prompts/_includes/need-bars.njk` in parallel so need-bar effects are decided independently of the numbered event groups; the dedicated need-bar prompt is launched after `Events.resolvePromptLaunchStaggerMs()` while the grouped event prompts launch immediately.
- Numbered grouped event-check responses must include a `<final>` block; `runEventChecks` enforces this via `requiredRegex` so the LLM client retries when it is missing.
- Combined answers across groups are stitched into a single numbered list and parsed as the final block text (no extra `<final>` wrapper).
- Dedicated need-bar checks require a `<characters>` block, are logged under the `need_bar_event_checks` prompt label, and are converted into ordinary `needbar_change` entries before `applyEventOutcomes(...)` runs. When the `need_bar_event_checks` TinyBrain family is enabled, the same task runs as a plain-text planning checkpoint followed by a strict XML-only characters phase; malformed final XML retries only that second phase while retaining the accepted plan. Its parser accepts the semantically exact `fill`/`drain` aliases as canonical `full`/`empty` changes, while still rejecting invalid direction/magnitude combinations.
- Normal non-travel player-action handling starts `quest_check` through the same stagger helper at two stagger intervals after event checks launch, so with the default `stagger_concurrent_prompts: 4`, post-turn `events-xml`, `need_bar_event_checks`, and `quest_check` prompts start roughly 0, 4, and 8 seconds apart while still being awaited together. A configured value of `5` starts them at roughly 0, 5, and 10 seconds.
- XML `<anyQuestObjectivesCompleted><value>true</value></anyQuestObjectivesCompleted>` is parsed as the strict boolean `any_quest_objectives_completed` signal. During the turn's normal quest-check phase, the chat layer reuses a check that already ran on the normal cadence or runs one interval-bypassing check later in the same turn. A successful signaled check resets `questCheckTurnCounter` to zero, and the turn never runs the quest prompt twice because of this signal. False or malformed values do not trigger it; malformed values fail XML event parsing.
- Silent housekeeping runs after the due turn's event outcomes have been finalized. The prompt receives `<housekeepingTurnHistory>` ordered oldest to newest; each turn groups its persisted player action, Storyteller/NPC prose, and event/status summary text. After a successful run, save metadata advances `lastHousekeepingTurnId`; the next pass includes every player turn after that boundary through the current turn. When the boundary has never been set, the runner sends only the most recent `housekeeping.interval` player turns. A stored boundary missing from full server chat history raises an explicit error instead of silently choosing another range. Manual `/housekeeping` bypasses the interval and uses/advances the same successful-run boundary without changing the automatic interval counter. Sectioned TinyBrain `<moveTurnResult>` origin, between, destination, and tracker sub-checks pass `suppressHousekeeping: true`; after the chat layer merges those sub-check results, it advances the interval once and, when due, runs one housekeeping prompt with the combined movement prose, merged event result, and final location. The prompt returns `<housekeeping>...</housekeeping>` with optional `<quests>`, `<trackers>`, and `<relationships>` sections. `Events._parseHousekeepingXmlResponse()` converts those sections into ordinary `createQuest`, `addTracker`, `updateTracker`, `removeTracker`, and `setRelationship` executions, preserving existing validation and per-item batch behavior. Deferred housekeeping finalization semantically parses the initial response before mutation and uses the configured prompt retry budget for local correction; every rejected attempt is separately logged with its parser error, and only the accepted parse may execute updates or advance the history boundary. Relationship XML supports optional `<action>add</action>`, `<action>update</action>`, or `<action>remove</action>`; remove deletes the directed `characterA -> characterB` edge. Its parser rejects unknown or duplicate fields, missing character or required-label values, relationship or reciprocal labels over six words, and labels attached to removal actions. After successful tracker and relationship executions, `api.js` records visible player-only `tracker-updates` and `relationship-updates` chat entries; those entries are excluded from all LLM-facing prompt-history paths. Housekeeping and quest-check interval counters plus the housekeeping history boundary are persisted in save metadata.
- Before applying outcomes, event checks ensure referenced NPCs exist (excluding death/incapacitation and defeated-enemy mentions), so downstream handlers can resolve actors; new NPC names are normalized via `Utils.capitalizeProperNoun` with leading-article stripping, while existing NPCs are left untouched. During ensure, if no exact name exists but the requested name is a leading token of an NPC currently in the same location (for example `Bob` vs `Bob Ross`), the first matching location NPC is reused instead of generating a new one.
- `npc_arrival_departure` suppresses current-player events and accidental party-member arrivals/first appearances. An explicit `left` departure for a current party member is allowed; the handler removes that NPC from the party before applying the destination move unless the destination is already the current party owner's location, in which case the departure entry is suppressed so same-turn shared travel keeps the NPC in the party. Departures require a concrete non-current destination. If the destination location is not resolved but the destination region is known, the handler creates an offscreen location stub in that region and moves the NPC there without creating a player-visible exit. If the destination region is not resolved, it creates an offscreen pending region-entry stub plus a child location stub, then moves the NPC to that child stub so the character remains trackable.
- TinyBrain character-presence guidance compares the authoritative current-location membership list with physical presence in the checked prose. A named actor physically entering or appearing in the scene requires `npcArrival` even when the actor remains hidden; plans, memories, dialogue mentions, and offscreen actions do not qualify. This is prompt guidance, not application-side prose inspection.
- Event result builders resolve normalized `newCharacters` and `departedCharacters` tracking keys back to authoritative actor names before populating `npcUpdates.added` and `npcUpdates.departed`. A missing actor preserves the trimmed tracking value, while resolved actors retain canonical capitalization.
- Hidden NPC opposed checks generated by event outcomes are returned in `hiddenNpcChecks` so the chat layer can record them as normal `check-results` entries. Automatic first-shared-location checks use no circumstance modifiers, reveal the NPC only on success, and may be hidden from the client for failed checks when `hide_hide_checks` is true.
- `attack_damage` event outcomes do not apply damage directly, but they do reveal a living hidden attacker and request a location refresh so attack narration cannot leave the attacker hidden.
- `thing_arrival_departure` handles existing non-animate items/scenery moving in or out of the scene. Arrivals place the resolved existing `Thing` in the current location. Departures require a concrete non-current destination; the handler moves the thing to a resolved destination location or creates the same style of offscreen destination stubs used for NPC departures, without creating player-visible exits. Missing things are warning-logged and skipped rather than generated; new objects should use `item_appear` / `scenery_appear`.
- `thing_move_with_character` handles existing non-animate items/scenery moving with a character. It resolves the character, uses that character's current resolved location as the destination, and moves the existing `Thing` there. Player and current-party references use the current event context location, so XML travel can carry carts, vehicles, or other things with the player or a party member after arrival. Missing characters or things are warning-logged and skipped.
- Event-created items and characters write any post-generation final name back into the parsed event payload after duplicate/slop-name regeneration. Chat event-summary rows and client-pushed structured events therefore use the final `Thing`/NPC name instead of the originally requested collision/slop name.
- `LLMClient.logPrompt` is always used for event-check logging; failures should surface loudly.
- Quest checks build the active quest list before rendering base context. If there are no active, unpaused quests, `runQuestChecks` logs a skip message and returns `null` without sending an empty `<quests>` prompt. Active quests still use the normal streamed `LLMClient.chatCompletion` defaults.
- Many helpers are defensive and throw on missing dependencies to avoid silent corruption.
- Independent multi-entry handlers skip only the failed entry when a single item/NPC/tracker entry cannot be applied, then continue later entries and emit diagnostics listing the skipped entries and error messages. This applies to item animation, consumption, alteration, transfer, pickup, container placement/removal, dropping, item appearance, tracker updates, disposition checks, and hostile-to-friendly transitions. Handler-level preconditions such as missing dependencies, invalid global config, or missing required current location still throw for the whole handler.
- `hostile_to_friendly` recognizes both the persisted raw hostile flag and current disposition-threshold hostility. This lets it reconcile an actor whose dispositions crossed into hostility while the legacy raw flag remained false; successful reconciliation raises every configured disposition to at least neutral and clears the raw flag. Client serialization, barter, and combat scheduling share the same threshold classifier.
- Item alteration updates `Thing.shortDescription` when provided by the alteration prompt, otherwise preserving the existing value.
- Item alteration treats optional list/effect fields in the returned item XML as authoritative. Missing or empty attribute bonuses and `causeStatusEffectOnTarget`/`causeStatusEffectOnEquipper` tags remove the corresponding previous data; populated tags replace it. Populated target/equipper status effects are synchronously expanded through status-effect generation before the altered item is persisted or logged, so normal `alter_item` events and chat-tool alterations get the same mechanical stats.
- `item_inflict` events ignore the prompt-provided status effect text and always apply the item's configured target inflict effect (`causeStatusEffectOnTarget`) to the target when available.
- Before event application, exactly one consumed item with a configured target effect gains a derived `item_inflict` entry when the same structured event batch identifies exactly one living attack/healing target, reports a compatible gained-status change for that target, and omitted both `item_inflict` and `item_ingest` for that item-target pair. This recovery uses only structured consume/attack/heal/status fields, never generated-prose inspection; multiple items, conflicting item/source fields, ambiguous targets, and absent status signals are left for the model rather than guessed.
- `item_ingest` events parse as `[item] → [target]` and infer the applied status effect from the ingested item's configured target effect instead of requiring the prompt to name the effect.
- Item-triggered status effects treat the item's stored effect as a reusable template: application discards the template's `appliedAt` value so the receiving actor stamps the new instance with the current world minute and timed effects expire from the actual use time.
- Quantity-aware item events require explicit positive-integer quantities for `consume_item`, `transfer_item`, `pick_up_item`, `put_item_in_container`, `remove_item_from_container`, `drop_item`, `harvest_gather`, and `item_appear`; `alter_item` requires a positive integer or `all`; quantity-less forms are rejected during parsing.
- Quantity-aware item handlers move, remove, or alter exact stack amounts instead of implicitly acting on a whole `Thing`. Partial-stack moves/consumption/alterations preserve the original item's stats/image and keep existing `metadata.value` unchanged while only adjusting stack count; partial `alter_item` splits the requested quantity into the same owner/location/container before altering that new stack. `consume_item` spills instantiated contents from fully consumed containers into the consumed container's current holder or location before deleting the container; this is the special destruction path that can delete a non-empty container. `transfer_item` resolves giver inventory first, then matching unowned items in the current location for handed loose scene objects, and generates any remaining shortfall into the giver before moving it to the receiver. `pick_up_item` resolves loose same-name scene items by exact quantity, so separate actors can pick up separate copies from either multiple Thing records or one stacked Thing; exact duplicate actor/item/quantity rows in the same pickup batch are warning-skipped. `put_item_in_container` moves exact quantities from a named actor inventory or loose current-location items into an existing container, while `remove_item_from_container` moves exact direct contents to a named actor inventory or the current location, generating any missing shortfall into the container before removal. `item_appear` adds the appeared quantity to an exact same-name item stack already in the current scene instead of skipping generation.
- If the same turn reports both `item_ingest` and `item_inflict` for the same item-target pair, the `item_inflict` entry is ignored so the effect is only applied once.
- When `item_inflict` or `item_ingest` applies a status, Events emits a synthesized `status_effect_change` entry so status summaries are delivered to the client even if no separate NPC-group status entry is present.
- `status_effect_change` de-duplicates gained effects against same-turn item-triggered status applications for the same entity; duplicate gain entries are skipped when generated status names, descriptions, or detail fields match exactly or start with the already-applied item-triggered effect name.
- The staged TinyBrain event parser validates status changes against current actor state before accepting a checkpoint. A `gained` event for an exact status the actor already has, a `lost` event for a status the actor lacks, or a duplicate of an item-applied effect is suppressed as a no-op rather than retried. A new status for a dead actor remains an error.
- Lost `status_effect_change` entries remove status effects by exact effect name or exact description, matching the XML schema's `statusEffectName` field without requiring the prompt to repeat the full description. The prompt retains the pre-audit general first-aid guidance and no longer adds special stabilization/incapacitation prose rules.
- Newly generated `status_effect_change` gains discard the generated template's `appliedAt` value before actor application, so the actor stamps the occurrence with the current world minute just like an item-triggered effect.
- `death_incapacitation` skips `dead` outcomes for NPCs already marked dead, preventing duplicate death application. New dead outcomes zero current health with a finite delta before setting `isDead`, then apply the `Deceased` status effect; incapacitated outcomes preserve current health and apply `Incapacitated` without setting `isDead`.
- TinyBrain event-stage parsing cross-checks `defeatedEnemy` against live actor health. A zero-health actor that is not already dead requires a matching `deathIncapacitation` outcome in the current or an earlier accepted checkpoint, so defeat XP cannot be accepted while the actor's persistent dead/incapacitated state remains unresolved. Positive-health defeats such as surrender or being driven off remain valid without a death/incapacitation event.
- A future event-schema extension should add an explicit resurrection effect. Until then, ordinary healing, item effects, and status gains cannot resurrect an actor marked dead.
- `alter_npc` requests require an `<npc>...</npc>` block from the model and always log prompt/response payloads through `LLMClient.logPrompt` before parse/apply. Returned `<aiNotes>` values update the persisted NPC `aiNotes` field.
- `alter_location` can be invoked from event checks, the chat `alterLocation` tool, or API helpers such as current-location modification; when a caller supplies `context.location`, the handler matches that location instead of only the global current location.
- `alter_location` accepts `context.preserveBaseLevel=true` or an entry-level `preserveBaseLevel=true` for flows that may rewrite the location name, short description, and description while keeping the existing `baseLevel` unchanged. The location-modification UI endpoint uses this option so player-made scenery/environment changes do not silently retune encounter difficulty.
- `_parseCharacterAlterXml` can parse wrapped or escaped model output by decoding basic entities and extracting the first `<npc>...</npc>` block before XML parsing.
- `suppressMoveEvents` skips applying `move_location` and `move_new_location` outcomes; this is primarily used for split `<moveTurnResult>` origin/destination checks where movement is handled by the travel pipeline.
- `move_new_location` parsing treats `sublocation` as `location` so sublocations generate full location stubs when move events are applied (unless move events are suppressed).
- When `move_new_location` entries are present but `context.location` is missing, the handler logs a warning before skipping movement/exit creation.
- The one-shot and legacy event paths can still infer narrated movement when move suppression is disabled. TinyBrain event stages intentionally omit movement XML and discard stray movement-boundary tags: player-action parsing owns the authoritative movement/no-movement decision and supplies sectioned prose to event extraction.
- Follow-up event-check passes inherit `suppressMoveEvents`/`allowMoveTurnAppearances` from the parent check to keep move-handling behavior consistent across queued reward/follow-up prose.
- `allowMoveTurnAppearances` allows `item_appear` / `scenery_appear` handlers to run even when `Globals.processedMove` is true (used for `<moveTurnResult>` event-check passes). NPC-turn event checks also allow these appearance handlers despite the movement lock, because `/api/chat` sets `Globals.processedMove` before NPC turns only to prevent NPC prose from hijacking player movement.
- `move_location` records destination tracking only after a successful `setLocation` write.
- `movePlayerToDestination(...)` enforces at most one player move per turn (`Globals.processedMove`, unless `allowAdditionalPlayerMoves` is explicitly true in context) and sets `Globals.processedMove` only after verifying the player's `currentLocation` matches the resolved destination id. If an event move targets the active vehicle's scheduled destination while that vehicle is underway, the helper suppresses the move before `setLocation(...)` and leaves `time_passed` available for arrival timing. For non-vehicle player/party event movement, it advances world time using `Location.findShortestTravelTimeMinutes(...)`, immediately resolves time-based need/status ticks, and then suppresses later `time_passed` advancement for that event pass; if no route exists, it uses `1` minute. Any successful player travel suppresses prompt-authored `time_passed` for that event pass even when the effective route/exit duration is `0`.
- `applyExitDiscovery(...)` skips forbidden event-created exits with `console.warn(...)` diagnostics: any new exit from a location vehicle origin, and any new region exit from a region-vehicle origin. Existing matching exits remain usable by event movement.
- `new_exit_discovered` accepts both compatibility four-/five-field entries and the source-aware format: destination name, destination kind, vehicle type, description, travel time, exit/source location, exit/source region, destination region, and optional destination location. XML `newExitDiscovered` maps its nested `destination`, `destinationType`, `destinationHasNewExits`, and optional `origin` tags into the same parsed shape; explicit `destinationType` `region` keeps the region name as the handler target while preserving any explicit destination location for display, but `destinationHasNewExits` promotion from an originally `location` destination promotes the XML `locationName` into the region target/name and clears the destination location field. The handler resolves explicit source locations before wiring exits, creates a missing explicit source location as a stub inside the named source region without adding a separate current-location exit, resolves destination-region hints against live regions and pending region stubs, uses those hints when creating location stubs, parses travel time through `Utils.parseDurationToMinutes`, and accepts four-field compatibility entries with no travel time or source metadata. After application, parsed entries are annotated with origin/destination ids and the created or reused `exitId` so chat summary pills can open the origin-region map and focus the new location or region-exit bubble. Event summaries show non-current source exits as `Origin Location (Region) -> Destination Location (Region)` or `Origin Location -> Region`, omitting region parentheticals when the endpoint is in the current region.
- Event-created location stubs store both a concrete stub base level and the original relative-level base so later stub expansion keeps location-relative difficulty anchored to the origin location level instead of drifting to player/default prompt context; event-created region-entry stubs likewise stamp a concrete stub base level from the current region average.
- `_generateItemsIntoWorld` passes generation `options` to `generateItemsByNames`; `treatAsScenery` / `treatAsResource` preserve scenery classification in generated `Thing` records.
- `_parseCharacterAlterXml` treats a missing/blank `<relativeLevel>` as null (no level write), preventing accidental resets to base-relative level 0 during `alter_npc`.
- `time_passed` parsing ignores the prompt's leading reasoning field and parses only the final arrow-delimited duration segment through `Utils.parseDurationToMinutes` (`HH:MM`, integer minutes, or day/hour/minute/round units); duration-only responses are accepted for compatibility, second-unit model mistakes are tolerated and rounded to the nearest minute, and malformed duration values are logged and skipped.
- `time_passed` accepts `0` from event checks; when this occurs, Events still advances canonical world time by 1 minute to avoid fully static clocks on zero-time turns. `time_passed` is only authoritative for non-travel turns and as a fallback when no `initialTimeProgress` is already present; event movement, XML travel boundaries, and exit-click travel use route/exit timing instead and ignore prompt-authored elapsed-time estimates for that same event pass. The exception is an impossible event move directly to the active in-motion vehicle destination: that move is suppressed, so fallback `time_passed` remains available to advance the vehicle to its scheduled arrival. Travel-prose timed vehicle trip starts use structured travel-time fields for the trip itself, while event-check `time_passed` remains only a fallback elapsed-time source.
- Arrow-delimited event parsing accepts both ASCII `->` and unicode arrows (for example `→`), preventing malformed NPC/item names when models emit typographic arrows.
- `disposition_check` is parsed and applied directly to NPC disposition toward the current player, and applied deltas are emitted as `dispositionChanges` with the configured disposition icon attached for summary rendering.
- `faction_reputation_change` is parsed and applied to player faction standings with fixed magnitudes (`a little` = `1`, `a lot` = `4`, signed by increase/decrease); entries are ignored unless a witness from that faction is present at the current location or in the party, and applied deltas are emitted as `factionReputationChanges`. Player-visible reputation summary rows retain structured faction id/name, signed amount, before/after values, reason, and rendered text in `metadata.factionReputationChange`. `tests/events.faction_reputation.test.js` deterministically covers both boundaries: a colocated matching-faction witness applies and emits the delta, while an unrelated-faction witness applies and emits nothing.
