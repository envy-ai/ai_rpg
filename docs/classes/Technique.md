# Technique

`Technique.js` validates saved discipline and technique mechanics. `Technique.create(value)` preserves a supplied ID or allocates `technique_` plus the normalized first three name words through shared `IdGenerator`, with numeric suffixes for collisions. Techniques are particular actions, separate from broad skills and level-up abilities. A common catalogue identity does not grant knowledge to a character. Unique identities are supported; learning a unique definition checks other living-world owners.

A definition contains `id`, `disciplineId`, `name`, `description`, setting-specific `semanticKey`, optional `aliases`, `unique`, structured `provenance`, and immutable contiguous numbered `revisions` starting at 1. `new Technique(value)`, `fromJSON`, `toJSON`, and `getRevision(number)` validate/copy these records; `create` allocates a compact technique ID. A catalogue edit appends a revision rather than replacing old mechanics.

Candidate identities, requirement/cost/check fields and independent checks within a revision collect up to ten distinct actual problems using [ResponseValidation](ResponseValidation.md). An invalid check is never replaced by an automatic check or inherited override to discover another error. Invalid effect kinds do not select a mechanics branch. Every partially normalized record is rejected before return; saved mechanics and accepted values remain unchanged.

A discipline has `id`, `name`, `description`, `accessRequirements`, optional `publicAccess`, and optional provenance. Ordinary acquisition requires an explicit actor `disciplineAccess` record, a deliberately public discipline, or fulfilled nonempty setting-defined requirements. Baseline initialized skills alone cannot establish access. Starting-technique initialization establishes explicit saved access with the learned repertoire; active ability status grants provide source-bound access without permanent learning. Discipline access is an acquisition gate; requirements for ongoing use belong in the revision's `useRequirements`.

Each mechanical revision contains:

- `revision`, `acquisitionRequirements`, and `useRequirements`.
- `target: { kind: "self" | "single" | "area", allowDead: false }`.
- `check: { kind: "automatic" | "attack" | "skill" | "opposed", ... }`. Attack, skill, and opposed checks require `skill`. Skill checks require one of the existing difficulty labels: `Trivial`, `Easy`, `Medium`, `Hard`, `Very Hard`, `Legendary`. Opposed checks require `opposedSkill`. Optional fields are `attribute`, `opposedAttribute`, `attackType`, `damageType`, `defense`, and `description`.
- `costs` and optional `failureCosts`, arrays of `{ resource: "health" | "need", amount, needId?, direction? }`. Need costs require an explicit `increase`/`decrease` payment direction, either in the authored cost or the need definition's `technique_payment_direction`. Conflicting directions reject. Health always decreases. Missing failure costs means the normal vector; explicit `[]` means free failure.
- Nonempty `effects` with distinct stable `id` values. Optional per-effect `check` overrides the common check. Damage and debuff effects require a nonautomatic check. A rejection identifies the effect kind, effective check kind, inherited revision check versus per-effect override, and exact check-field paths to correct. This diagnostic does not change accepted check kinds or supply mechanics.

Damage is `{ id, kind: "damage", damageMode: "technique", amount }`; it applies the authored amount once, without ordinary weapon damage or hidden bonuses. Weapon-based damage and utility effects are explicitly unsupported. Healing is `{ id, kind: "healing", amount }`; existing health bounds remain authoritative, and it does not change the death flag or remove incapacitation.

Buffs/debuffs contain `status: { name, description, duration, attributes, skills, needBars }`. Duration is integer world minutes, positive or `-1` for permanent. Attribute/skill entries use `{ attribute|skill, modifier }`; need entries use `{ name, delta }`. Modifiers support signed amounts. `stacking` defaults to `refresh`; explicit `stack` adds another instance. `refreshPolicy` is `stronger` (default), `replace`, or `reject`; optional authored `potency` orders variants that cannot otherwise be compared. Stable identity is technique ID plus effect ID, regardless of caster, name, or personal revision. Stronger comparisons require matching mechanical slots and directions and consider original duration; mixed tradeoffs require explicit policy/potency. Weaker repetitions refresh the stronger record's original duration without weakening it.

An amount is a finite number or `{ formula }`. Variables are bound automatically to the acting character's current authoritative facts: `level`, `skill_<normalized_name>` for skill ranks, and `attribute_<normalized_name>_modifier` for attribute modifiers (not raw attribute scores). Names are lowercase with runs of nonalphanumeric characters replaced by underscores and leading/trailing underscores removed. The shared [TechniqueFormulaVariables](TechniqueFormulaVariables.md) helper provides the catalogue and resolution contract. Current scalar values are never saved with a formula. Unknown facts and normalized-name collisions reject explicitly.

Existing saved `{ formula, bindings }` amounts retain their explicit alias semantics, including aliases that shadow automatic names. Bindings map simple identifiers to `{ kind: "level" }`, `{ kind: "skill", name }`, or `{ kind: "attribute", name }`; named legacy sources match case-insensitively. Unmapped canonical variables can coexist with saved aliases. Unused explicit bindings reject. The editor converts saved aliases to canonical identifiers in one pass when editing that amount; loading a save does not rewrite history.

The existing restricted parser supports arithmetic and only `abs`, `round`, `floor`, `ceil`, `min`, and `max`. Unknown variables, property access, `infinity`, `clamp`, unsupported functions, nonfinite output, and negative cost/heal/damage results reject. No implicit rounding or clamping is added. `validateRevisionAmounts(revision, actor, label?)` checks every cost/effect/status formula against current actor facts with field-specific paths; catalogue creation and personal saves use this before mutation.

Formula syntax and evaluation errors retain the original evaluator message/cause and add the amount path and a correction for syntax or finite output. Actor-aware unknown-variable and explicit-binding errors list actual available keys/names. Kind-specific field errors list the allowed fields; nested modifier duplicates explain combining fixed/percentage components into one entry. These diagnostics do not change the supported mechanics.

Requirements use `kind`, and optional `present: false` negates them. Supported shapes are `level` with `minimum`; `skill`/`attribute` with `name, minimum`; `discipline`/`technique`/`equippedItem`/`evidence` with `id`; `equipmentType`/`ability`/`status`/`class`/`race` with `name`; and `alive`. Class/race requirements match the actor's actual identity case-insensitively and introduce no setting-specific names.

`Player.techniques` stores complete learned entries: `{ techniqueId, definitionRevision, personalRevision, mechanics, provenance, acquiredAt, evidence, revisionHistory }`. Personal mechanics start at revision 1 even when learned from a later base definition. Each personal edit retains the old complete mechanics in `revisionHistory`. Another character and item grants retain their own pinned mechanics. Missing legacy actor fields initialize empty; present malformed records throw.

`Thing.techniqueGrants` entries are `{ id, sourceItemId, techniqueId, definitionRevision, teaches, provenance }`. IDs are stable and unique across the world. Ordinary grants provide access only while that item is equipped; `teaches: true` is an owned-item acquisition source for durable learning and does not itself grant equipped access. No historic item acquires an implicit grant. The Thing field registry exposes this validated field to ordinary create/edit contracts.

Status effects can also carry pinned `techniqueGrants` entries `{ id, sourceStatusId, techniqueId, definitionRevision, provenance? }`. A grant is an available `status` source only while its containing actor status is active; the status can be intrinsic, attached to an owned ability, or supplied by equipped gear. A technique buff/debuff status may itself contain grants, including a grant-only status with no numeric modifier. Its applied status binds each authored grant to the committed status ID. Status grants do not create learned entries and disappear with their source. Existing item grants and independently learned entries retain their own behavior.

Technique buff/debuff status modifiers may use `percentModifier` beside fixed `modifier` on attributes/skills, and `maxHealthPercent` on the status. Signed numeric or formula amounts follow the existing status formula validation. Fixed modifiers remain available and can coexist with percentage modifiers.

Provenance uses `kind` (`trainer`, `discovery`, `item`, `story`, `training`, `editor`, `generation`, `milestone`, or `use`) and a nonempty `reason`, with optional `sourceId`, `private`, `worldMinute`, and `operationId`. Private provenance is stored for server validation; availability projections omit it.

Revisions may additionally contain validated `balance` metadata for an engine-managed healing recipe. Present metadata is strict and its saved costs/effects must exactly match recompilation from the saved snapshot; absent historical metadata remains valid. `normalizeRevision` checks this throughout catalogue/learned/history/receipt structures, and `validateRevisionAmounts` additionally validates selected actor facts and resource profile capacity. See [TechniqueBalancePolicy](TechniqueBalancePolicy.md) for semantic recipe DTOs, policy snapshots and configured improvements.
