# LocationNpcGenerationPlan

`LocationNpcGenerationPlan.js` validates the TinyBrain location NPC roster and each full NPC checkpoint before any NPC is registered. The roster uses one strict `<npcsPlan>` root with one or more `<npc>` entries. Every entry has required `<kind>` (`npc` or `hostile`), `<name>`, positive `<quantity>` within the configured `npc_generation.max_quantity`, and a brief durable `<description>`. Names must be distinct without regard to case. The normal zero-total generation hint exits before the roster prompt; nonzero requests cannot silently accept an empty plan. Existing count hints remain hints, and the standard full-batch prompt is unchanged.

`parseLocationNpcXmlPlan(response, { maxQuantity, schema })` checks the named `location-npc-plan.schema.xml` with the native XML guard and strict XML parser, then validates these values. Malformed or duplicate XML fields and invalid domain values return field-specific correction errors.

`parseLocationNpcCheckpoint(response, approvedEntry, { schema, parseNpcXml, validateCandidates })` requires one complete `<response>` with exactly one `<npc>` or `<hostile>` matching the approved kind. It checks the named `location-npc-checkpoint.schema.xml` even if live generation guarding is disabled, then uses the existing location NPC parser and detached construction preflight. The approved name, kind, quantity, description and memory owner are supplied by the server; the model is asked only for remaining fields and memories. Omitted, self-closing, empty or whitespace-only echoes of those known scalar fields are filled from the plan; populated conflicting echoes reject with the offending path and required value. The approved brief description becomes the final character description, so the roster asks for durable appearance/personality/role text using `%NAME%`, not a transient place or action. A distinct `shortDescription` remains an expansion field. The parser preserves the original cause, and explicit prompt cancellation is propagated.

Memory records remain optional as in the native parser. When present, the checkpoint accepts only one record for the planned NPC, binds its owner to the approved name, and leaves the existing up-to-three memory handling in place. Each checkpoint returns detached NPC data, a memory map, and canonical XML for later local assembly. No field is committed during roster or checkpoint correction.
