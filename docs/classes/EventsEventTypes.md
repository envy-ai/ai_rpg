# Events Event Types

## Purpose
Reference for the built-in event keys recognized by `Events.js`. This excludes `dummy_event`, `_instructions_`, the XML travel marker `arriveAtLocation`, and mod-registered XML event keys supplied at runtime through `ModExtensionRegistry.registerXmlEvent(...)`.

`runEventChecks(...)` uses the XML event pipeline by default (`event_checks.use_xml !== false`). The grouped numbered `EVENT_PROMPT_ORDER` pathway is available when XML event checks are disabled, and both pathways feed the same parser and handler tables. Dedicated helper prompts can also inject structured event keys into the same outcome object.

For the XML tag schema, see [EventsXmlEventSchema.md](EventsXmlEventSchema.md).

## Event Type Table

| Event type | Primary source | Parsed payload | Meaning and application |
| --- | --- | --- | --- |
| `new_exit_discovered` | XML `newExitDiscovered`; grouped location checks | Destination name, destination kind (`location`/`region`, XML `destinationType`, promoted to `region` when XML `destinationHasNewExits` is `true`), optional vehicle type, description, optional travel time, optional exit/source location and region, optional destination region, optional destination location name | A route, door, path, portal, or vehicle route was discovered or created. The handler creates or wires the destination/exit without moving the player. Travel times are parsed as minutes and attached to the created exit wiring. Explicit source locations let the event add exits from locations other than the active one; if the named source location is missing but its source region resolves, the handler creates that source as a region-local stub without adding a current-location exit. Destination-region hints are used when resolving or creating location destinations. If XML marks the destination as a region and includes a destination location, the region remains the handler target and the destination location is preserved for summary text. If `destinationHasNewExits` promotes a `location` destination to `region`, the XML `locationName` becomes the region target/name and the destination location field is cleared. |
| `move_new_location` | XML `moveNewLocation` travel boundary; grouped location checks | Origin/difference text, destination name, kind (`location`, `region`, or `sublocation`), optional vehicle type, description | The player/party moved to a destination that does not already exist in the world model. The handler creates/discovers the destination and moves the player there unless movement is suppressed for split travel-prose checks. `sublocation` is promoted to `location` before handling. |
| `move_location` | XML `moveLocation` travel boundary; grouped location checks | Existing destination location name | The player/party moved to an already-known location. The handler resolves the final destination and moves the player there, with single-player-move turn guards in `movePlayerToDestination(...)`. |
| `alter_location` | XML `alterLocation`; grouped location checks | Current location name, new location name, change description | The current location's visual/environmental description updates without the player simply moving away. The handler invokes the location alteration prompt, applies the returned location XML, clears location imagery when needed, and records alteration summaries. |
| `mystery_box_mention` | XML `mysteryBoxMention` | Mystery/actor/thread name plus one observed context sentence | A significant unresolved character, secret, clue, conspiracy, or background thread was introduced or materially expanded. The handler runs the `mystery-box-update` prompt, then creates or updates a persisted `MysteryBox` private note with aliases and mention history. This event records hidden continuity only; it does not emit player-facing prose or advance offscreen events by itself. |
| `currency` | XML `currency`; grouped item checks | Signed integer delta | The player gained or lost currency. The aggregator sums all currency answers and the handler modifies player currency by the resulting delta. |
| `item_inflict` | XML `itemInflict`; grouped item checks | Item name, target name, prompt-provided status text | An item was used in a way that might activate its target effect. The handler ignores the prompt-provided status text for mechanics and applies the item's configured `causeStatusEffectOnTarget` to the target when available. It also emits item-triggered status-change summary data. |
| `item_ingest` | XML `itemIngest`; grouped item checks | Item name, target/consumer name | Someone ate, drank, inhaled, or otherwise ingested an item. The handler infers the applied effect from the ingested item's configured target effect and suppresses duplicate same-pair `item_inflict` applications. |
| `item_to_npc` | XML `itemToNpc`; grouped item checks | Original item/scenery name, new NPC/entity name, short description | An inanimate object became an independent moving entity. The handler resolves and detaches the source thing, ensures/generates the NPC, places it in the current location, and tracks the new character. |
| `alter_item` | XML `alterItem`; grouped item checks | Original item name, quantity or `all`, new item name, change description | An item or scenery object was permanently altered. The handler resolves the source thing, splits stacks for partial quantities, runs the thing alteration prompt, applies the returned item/scenery data, and refreshes images/stats/metadata. |
| `consume_item` | XML `consumeItem`; grouped item checks | Item name, quantity, consumption reason | An item or scenery object was fully used up, destroyed, eaten, spent, or assembled into something else. The handler removes or decrements exact quantities, including stack-aware consumption. If the fully consumed thing is a container, instantiated contents are moved to the destroyed container's current holder or location before deletion. |
| `transfer_item` | XML `transferItem`; grouped item checks | Giver name, item name, quantity, receiver name | An item was handed, traded, taken from, or given from one actor to another. The handler moves exact stack quantities from the giver, can reuse a matching unowned item in the current location, and generates any missing shortfall before giving it to the receiver. |
| `pick_up_item` | XML `pickUpItem`; grouped item checks | Actor name, item name, quantity | A character obtained carryable tangible items by a method other than harvesting/gathering. The handler creates/ensures the item if needed and places exact quantities in the actor's inventory. Separate actors can pick up separate same-name copies from multiple loose records or one loose stack; exact duplicate actor/item/quantity rows in the same batch are warning-skipped. |
| `put_item_in_container` | XML `putItemInContainer`; grouped item checks | Optional character name, item name, quantity, container name | A character or the scene puts existing items into an existing named container. With a character, the handler moves exact quantities from that actor's inventory; without one, it moves loose current-location items. Partial stacks are split before placement. Missing items or containers fail loudly rather than generating replacements. |
| `remove_item_from_container` | XML `removeItemFromContainer`; grouped item checks | Optional character name, item name, quantity, container name | Direct contents are removed from a named container. With a character, the handler gives exact quantities to that actor; without one, it places the items in the current location. Partial stacks are split; if the direct contents are missing or short, the handler generates the missing shortfall into the container before removal. Nested containers are not searched. |
| `harvest_gather` | XML `harvestGather`; grouped item checks | Harvester name, item name, quantity, optional source name | A character gathered resources from a harvestable source, pile, plant, vein, machine, etc. The handler creates/ensures the harvested item, places it in inventory, and records successful harvest history on the source node when available. |
| `item_appear` | XML `itemAppear`; grouped item checks | Item name, quantity, description | New carryable items appeared in the scene for the first time. The handler generates/creates item things in the current location, preserving quantities; if an exact same-name item stack already exists in the scene, it increments that stack by the appeared quantity. |
| `drop_item` | XML `dropItem`; grouped item checks | Character name, item name, quantity | A character dropped, placed, or set down inventory items into the scene. The handler moves exact stack quantities from inventory to the current location. |
| `scenery_appear` | XML `sceneryAppear`; grouped item checks | Scenery name | New non-carryable scenery appeared in the scene for the first time. The parser keeps the scenery name; the XML/numbered description text is not part of the parsed value. The handler generates/creates scenery things in the current location. |
| `harvestable_resource_appear` | XML `harvestableResourceAppear`; grouped item checks | Resource/scenery name | A gatherable or harvestable resource appeared. The parser keeps the resource name; the XML/numbered description text is not part of the parsed value. The handler generates/creates scenery marked for resource harvesting where supported. |
| `thing_arrival_departure` | XML `thingArrival`, `thingDeparture`; grouped item checks | Existing item/scenery name, action (`arrived`/`left`), concrete destination region/location for departures | An existing non-animate thing arrived in or left the scene without being newly generated, picked up, dropped, transferred, consumed, or animated into an NPC. Arrivals place the resolved existing `Thing` in the current location. Departures move it to the resolved destination; unresolved concrete destinations create offscreen tracking stubs without creating player-visible exits. Missing things are warning-logged and skipped instead of generated. |
| `thing_move_with_character` | XML `thingMoveWithCharacter`; grouped NPC movement checks | Existing thing name, character name | An existing non-animate thing moved with a character who traveled or departed. The handler resolves the existing `Thing`, resolves the character, then places the thing at that character's current destination. For player or current-party references, the handler uses the current event context location, so XML travel can defer in-transit carried/driven objects to the post-arrival destination phase. Missing characters or things are warning-logged and skipped. |
| `attack_damage` | XML `attackDamage`; grouped NPC checks | Attacker name, target name | A physical attack happened. This event is tracked and summarized, but the handler does not directly apply damage; attack resolution happens elsewhere before/around narrative generation. If the attacker is a living hidden NPC, the handler clears `hiddenFromPlayer` and requests a location refresh. |
| `alter_npc` | XML `alterNpc`; grouped NPC checks | Character name and physical-transformation description | An animate entity underwent a significant physical transformation by something other than normal attack damage. The parser accepts entries whose alteration category normalizes to `physical transformation`; other categories are filtered out before handling. The handler runs the NPC alteration prompt, applies returned NPC XML, and tracks altered character summaries. |
| `status_effect_change` | XML `statusEffectChange`; grouped NPC checks | Entity name, status effect name/detail, `gained`/`lost`, optional level | A temporary status effect was gained or lost. The handler generates mechanical status-effect stats for gained effects when possible, applies or removes the effect on the actor, and de-duplicates gains already applied by item-triggered events. |
| `npc_arrival_departure` | XML `npcArrival`, `npcDeparture`, parser-compatible `npcArrivalDeparture`; grouped NPC checks | NPC/entity name, action (`arrived`/`left`), concrete destination region/location for departures, optional `hideFromPlayer` | An animate entity arrived in or left the scene. The handler ensures arriving NPCs, places them in the current location, or moves departing NPCs to the resolved destination. Current-player events and accidental party-member arrivals are suppressed, but an explicit party-member `left` departure removes that NPC from the party before moving them to the resolved destination. Departures to unresolved concrete destinations create offscreen tracking stubs: a missing location in a known region becomes a region-local stub, and a missing region becomes a pending region-entry stub plus a child location stub. These tracking stubs do not create player-visible exits. When `hideFromPlayer` is true, the moved living NPC is marked hidden and is treated as attempting to stay hidden the next time the player shares a location with them. Dead NPCs/corpses are always visible. |
| `reveal_hidden_npc` | XML `revealHiddenNpc`; grouped NPC checks | NPC/entity name, reason/description, optional opposed-check flag | A hidden NPC may become visible. Hidden living targets run a player perception vs NPC hiding opposed check unless the entry explicitly disables the opposed check. Failed checks leave the NPC hidden; successful checks clear `hiddenFromPlayer`. Non-hidden, dead, or unresolved NPCs are ignored. |
| `hide_visible_npc` | XML `hideVisibleNpc`; grouped NPC checks | NPC/entity name, reason/description | A visible NPC attempts to hide from the player. The handler runs an NPC hiding vs player perception opposed check using the active world setting's configured hide/perception stats. Successful checks set `hiddenFromPlayer`; failed checks leave the NPC visible. Dead NPCs/corpses are ignored because they are always visible. |
| `npc_first_appearance` | XML `npcFirstAppearance`; grouped NPC checks | Present entity names | A physically present actor was mentioned but was not already known/listed. It is converted into arrival-style entries during parsing so the normal NPC arrival handling can ensure and place the actor. |
| `party_change` | XML `partyChange`; grouped NPC checks | NPC name, `joined`/`left` | A present NPC began accompanying the player or left the party without a separate destination move. The handler adds/removes party membership on the current player. |
| `trade_availability` | XML `tradeAvailability`; grouped NPC checks | NPC name, boolean `willingToTrade`, optional reason | An event made an NPC willing or unwilling to barter with the player. The handler updates the NPC's persisted trade willingness; unwilling entries receive a temporary refusal expiry based on `barter.refusal_duration_minutes`, while willing entries clear the expiry. |
| `environmental_status_damage` | XML `environmentalStatusDamage`; grouped NPC checks | Actor name, `damage`/`healing`, severity, reason | An actor took environmental/status damage or healing. When environmental effects are allowed, the handler converts severity into a health delta, applies it, and records environmental damage/healing summary data. |
| `heal_recover` | XML `healRecover`; grouped NPC checks | Character name, magnitude (`small`/`medium`/`large`/`all`) or healer/recipient/effect, reason | A character recovered health. The handler estimates healing amount from magnitude and actor stats, then applies health recovery. |
| `hostile_to_friendly` | XML `hostileToFriendly`; grouped NPC checks | NPC name, previous disposition, new disposition, reason | A hostile/unfriendly NPC became neutral, friendly, or allied. The handler clears hostility and raises all configured disposition types to at least neutral. |
| `in_combat` | XML `inCombat`; grouped misc checks | Boolean-ish yes/no | The player is currently in physical combat. The handler stores the normalized combat flag in `Globals` and the outcome context. |
| `any_quest_objectives_completed` | Required XML `anyQuestObjectivesCompleted` | Strict `true`/`false` | Signals whether the checked prose likely completed any active quest objective. A true signal causes the chat turn to bypass the normal quest-check interval during its normal quest-check phase, run the full quest check once unless it already ran that turn, and reset the persisted quest-check counter after a successful run. The signal itself does not mutate quests. |
| `received_quest` | XML `receivedQuest`; grouped misc checks | Optional giver, quest/task summary | The player became aware of a quest/task. When quests are enabled, the handler runs quest generation, asks for confirmation through the quest confirmation manager, and records awarded quests when accepted. |
| `death_incapacitation` | XML `deathIncapacitation`; grouped misc checks | Actor name, `dead` or `incapacitated` | An entity died or became incapacitated. The handler zeroes health and marks NPCs dead for `dead`; `incapacitated` preserves current health and applies the `Incapacitated` status effect. Duplicate dead outcomes for already-dead NPCs are skipped. |
| `defeated_enemy` | XML `defeatedEnemy`; grouped misc checks | Enemy name(s) | The player defeated an enemy. The handler awards XP based on enemy/location level and player level, and tracks defeated enemy names. |
| `experience_check` | XML `experienceCheck`; grouped misc checks | Raw XP amount, reason | The player did something that warrants experience aside from defeating enemies. The handler scales the prompt amount by location/player level and awards XP unless an enemy-defeat award already happened this turn. |
| `faction_reputation_change` | XML `factionReputationChange`; grouped misc checks | Faction name, increase/decrease magnitude (`a little`/`a lot`), reason | The player's faction standing shifts. The parser maps `a little` to `1` and `a lot` to `4`, signed by increase/decrease. The handler applies the shift only when a witness from that faction is present with the player, in the party, or at the location. |
| `time_passed` | Grouped misc checks; parser-compatible XML `timePassed` | Reasoning/breakdown and final duration | The non-travel turn consumed in-world time. The parser reads the final arrow-delimited duration segment and converts it to minutes. The handler advances canonical world time unless suppressed or an existing `initialTimeProgress`/action time progress is already present, immediately applies time-based need/status ticks, and `0` still advances by one minute to avoid static clocks. Successful travel suppresses this event so route/exit time stays authoritative. |
| `tracker_updates` | XML `trackerUpdates`; grouped misc checks | Tracker name, type, action (`add`/`update`/`remove`), new value, reason | Plot tracker values changed, or a tracker should be added/removed. XML `<trackerUpdates>` is optional; omitting it means no tracker changes. Each tracker update entry is parsed/applied independently, malformed entries are logged to `console.error` and skipped, and percentage values accept either `45` or `45%` before storing the canonical `%` form. Countdown add/update values are parsed as durations from the current game minute and stored as absolute deadline minutes; countdown displays tick down automatically and should not be updated merely because time passed. Adds create visible trackers with the reason as their LLM-facing description; updates/removes resolve by id or unique name. |
| `triggered_abilities` | XML `triggeredAbility`; grouped misc checks | Raw character/ability entry string | Prompt-only at present. `Events.js` records raw entries and extracts the character name for NPC ensuring, but there is no event handler that applies triggered ability effects. |
| `needbar_change` | Dedicated `need-bars.njk` prompt; parser-compatible XML `needBarChange` | Character name, need bar name/id, direction, magnitude, optional reason | A need bar shifts. The active source during `runEventChecks(...)` is the parallel need-bar prompt. The handler calls `applyNeedBarChange(...)` on the actor and records `needBarChanges` for summaries/client payloads. |
| `disposition_check` | Parser-compatible XML `dispositionCheck`; structured outcomes | NPC name, before feeling, after feeling, reason | A significant NPC disposition toward the current player shifts. The handler resolves direction from before/after text, applies one typical disposition step to the default/platonic disposition type, and records `dispositionChanges`. The async memory/disposition prompting in `api.js` uses its own XML flow, but this Events handler is available for structured event outcomes. |
| `completed_quest_objective` | Quest-check merge pipeline; parser-compatible XML `completedQuestObjective` | Quest index/objective index and optional status reason, with quest/objective IDs and descriptions after normalization | A quest objective was completed. `runQuestChecks(...)` and `mergeQuestOutcomesIntoStructured(...)` inject normalized objective completions into event outcomes. The handler marks objectives complete, applies quest-completion rewards when appropriate, and preserves prompt-supplied completion reasons. |

## Notes
- `dummy_event` entries are scaffolding questions used to steer later grouped answers, not applied outcomes.
- `_instructions_` entries are prompt instructions, not events.
- XML event parsing maps camelCase tags into these snake_case event keys through `_mapXmlEventNodeToLegacyRaw(...)`, then reuses the same parser and handler maps as grouped numbered checks.
- XML travel uses at most one `moveLocation` or `moveNewLocation` boundary plus a required `arriveAtLocation` marker. Events before the boundary apply at the origin, the movement event applies as travel, and events after the marker apply at the destination. During-travel tags are ignored except `thingMoveWithCharacter`, which is deferred to the after-arrival phase.
- Application order starts from `EVENT_PROMPT_ORDER_FLAT`, then appends parsed keys not present there. This lets helper-injected types such as `needbar_change`, `disposition_check`, and `completed_quest_objective` still run. Because `needbar_change` is appended after `time_passed`, event-authored need-bar changes resolve after elapsed-time ticks.
- Some event types are suppressed by context flags: `suppressMoveEvents` skips `move_location`/`move_new_location`; `omit_npc_generation` skips NPC arrival/generation and alteration; `omit_item_generation` skips item/scenery generation and alteration.
- Independent multi-entry handlers report and skip individual failed entries while continuing later entries in the same event list. This covers item animation, consumption, alteration, transfer, pickup, container placement/removal, dropping, item appearance, tracker updates, disposition checks, and hostile-to-friendly transitions. Batch-level setup failures such as missing dependencies, invalid config, or missing required current location still fail the handler.
