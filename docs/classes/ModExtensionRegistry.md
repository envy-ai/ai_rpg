# ModExtensionRegistry

## Purpose
Central registry for mod-provided runtime extension hooks. The server creates one registry, exposes it on `Globals.modExtensionRegistry`, passes it into API/event/prompt contexts, and gives each `mod.js` a namespaced registration wrapper through `ModLoader`.

## Hook Types
- `registerChatTool({ definition, executor, allowedInRegularProse, allowedInGenericPrompt })`: registers a live chat tool. API route filtering combines built-in tools with registry tools at request time, so mods may load after route registration.
- `registerXmlEvent({ tagName, eventKey, promptSchema, parser, handler })`: registers a camelCase XML event tag, parser, prompt-schema entry, and outcome handler. `promptSchema` may be a raw XML example string or `{ name, description, xml }`; object schemas require `xml`, and `name` defaults to the tag name when omitted.
- `registerBaseContextContributor(fn)`: contributes generic mod context for base prompts.
- `registerSceneSummarizeContributor(fn)`: contributes scene-summary guidance. `collectSceneSummarizeContributions({ fullHistoryLines })` invokes enabled-mod contributors for each chunk and returns non-empty `{ modName, text }` entries; non-string results fail loudly.
- `registerPlayerActionPromptStep({ id, step, text, tinyBrainText, order })`: registers a mod-owned step for the `player-action` prompt self-correction process. `step` is required and accepts only `1` or `3`. `tinyBrainText` may provide a checkpoint-sized instruction for staged prompts and falls back to `text` when omitted. The prompt environment exposes `modPlayerActionPromptSteps(startStep)`, which returns and numbers the matching stage's sorted steps.
- `registerGenerationPromptInstruction({ id, generationType, generationTypes, text, textProvider, order })`: registers mod-owned guidance for item, location, and/or region generation prompts. Static `text` is supported; `textProvider(context)` is evaluated when the prompt is rendered and may return an empty string to omit the instruction for that run.
- `registerActorStatusContributor(fn)`: contributes actor profile/status sections for prompts and client payloads.
- `registerAttributeModifierContributor(fn)`: contributes numeric attribute bonuses, used by `Player.getModifiedAttribute`.
- `registerStatusEffectContributor(fn)`: contributes continuous actor status effects, used by `Player.getStatusEffects`.
- `registerThingTargetStatusEffectContributor(fn)`: contributes additional target status effects for a specific actor/item pair, used by attack handling for systems such as installed item modules.
- `registerThingPromptContributor(fn)`: contributes mod-owned XML embedded inside a Thing's full base-context representation. `collectThingPromptContributions(thing, context)` invokes each contributor with the resolved Thing and returns the non-empty string fragments (throwing if a contributor returns a non-string). Used to append detail such as installed modules to items rendered in full.
- `registerInventorySyncContributor(fn)`: lets mods remove stale actor mod-state references after inventory replacement/removal.
- `registerSettingTab({ id, label, description, order })`: declares a mod-owned World Profiles editor tab. The id must be safe for DOM data attributes: start with a letter and contain only letters, numbers, `_`, or `-`.
- `registerSettingField({ namespace, key, label, type, defaultValue, description, tabId, normalize, options, persist, action })`: declares world-profile mod setting fields. Fields with `tabId` render in that registered mod tab; fields without `tabId` render in the Prompt Guidance `Mod Settings` block for compatibility. The Worlds UI renders `object` and `array` fields as JSON textareas, `select` fields from option metadata, and other types as text inputs. Non-persisted action fields can drive UI-only behavior such as applying a preset to other fields.
- `registerEntityField({ entityType, fieldName, type, defaultValue, description, descriptionProvider, validateValue, exposeToCreateTool, exposeToUpdateTool, exposeToGeneratorPrompt, exposeToXmlParser, exposeToEditModal, clearThingSlotWhenPresent, edit, xmlPrompt, xmlPromptPlaceholderProvider, toolSchema })`: declares a first-class mod-owned entity field. Supported field types are `string`, `number`, `integer`, `boolean`, `array`, and `object`; runtime integration supports `entityType: "thing"` and `entityType: "player"`. Registered Thing fields are persisted at top level by `Thing.toJSON()`, exposed through `thing.getExtensionField(...)` / `thing.setExtensionField(...)`, and installed as direct instance accessors such as `thing.implantSlot`. Registered Player fields are persisted at top level by `Player.toJSON()`, exposed through `player.getExtensionField(...)` / `player.setExtensionField(...)`, and installed as direct instance accessors such as `player.sexualTraits`. Dynamic providers can render active world-profile options into prompt/tool field descriptions and XML placeholders. `toolSchema` can override the generated `createThing` or `createNpc` JSON schema for structured fields while the dynamic description is still applied. Optional `validateValue(value, context)` runs after core type normalization and before constructor, hydration, or setter persistence; it should throw an explicit error for invalid values.
- `registerThingImageBadge({ id, fieldName, fieldValue, label, iconUrl, imageUrl, renderMode, position, order, assetPathSetting, labelSetting })`: declares a client-rendered item/scenery image overlay. The badge appears when the Thing has a meaningful value for `fieldName`, optionally matching `fieldValue`. Exactly one of `iconUrl` or `imageUrl` is required, and the URL must point at the registering mod's `/mods/<mod>/assets/...` path. `renderMode` supports `auto`, `mask`, and `image`; `position` supports all four image corners. `assetPathSetting` and `labelSetting` can point at namespaced world-profile settings that override the badge asset path and label in the browser.
- `registerThingContextAction({ id, label, fieldName, fieldValue, contexts, order, handler })`: declares a server-backed item/scenery context-menu action. The client receives only metadata; the registry keeps the handler for `/api/mod-thing-context-actions/:actionId`, which receives the action record, Thing, resolved actor, request body, world maps, and `Globals`.
- `registerStartupValidator(fn)`: runs after mods and merged definitions load.

## Notes
- Duplicate chat tool names, XML tags, XML event keys, setting tabs, setting fields, entity fields, Thing image badges, Thing context actions, per-mod player-action prompt step ids, and per-mod generation prompt instruction ids fail loudly.
- A field that references an unknown setting tab fails during registration.
- Select setting field options are cloned into registry snapshots. Preset-style options may include a `settings` object whose namespace/key values are copied into other editable mod fields by the Worlds UI after confirmation.
- Non-persisted setting fields are UI controls only; they are rendered, but skipped when the Worlds UI writes `SettingInfo.modSettings`.
- Setting field `normalize` must be a function when supplied. The registry stores it with the field snapshot for mod-side use; the Worlds UI save path persists rendered field values without invoking the callback.
- Entity fields whose names collide with built-in `Thing` or `Player` fields fail during registration; fields whose names collide with runtime properties also fail when the entity is instantiated.
- Entity-field `validateValue` must be a function when supplied. It receives a cloned normalized value plus `{ entity, entityType, fieldName }`, so validation cannot mutate the stored value accidentally.
- Entity field names must be JavaScript-style property names. Entity types and UI ids must start with a letter and contain only letters, numbers, `_`, or `-`.
- Chat tools can be allowed separately for regular prose prompts and generic prompts.
- `createThing` and `updateObjectFields` build their Thing-field surfaces from the registry at request/runtime, so fields registered by enabled mods are visible without hard-coding them into core tool definitions. `createThing` uses a field's `toolSchema` when present; otherwise it derives a simple schema from the registered field type.
- `createNpc`, `updateCharacterFields`, and `updateObjectFields({ objectType: "character", ... })` build their Player-field surfaces from the registry at request/runtime, so fields registered by enabled mods are available to direct character field tool calls.
- Thing entity fields can opt into generated item XML by setting `exposeToGeneratorPrompt: true` and `xmlPrompt.placeholder`. `xmlPrompt.tagName` defaults to the field name. `exposeToXmlParser: true` parses that tag from generated item/scenery XML and writes the value into the first-class field on created Things.
- Player entity fields can opt into NPC generation and alteration XML by setting `exposeToGeneratorPrompt: true` and `xmlPrompt.placeholder`. `xmlPrompt.tagName` defaults to the field name. `exposeToXmlParser: true` parses that tag from generated NPC XML and character-alter XML and writes the value into the first-class field on created or altered NPCs.
- Thing XML parser and payload paths coerce registered values according to the registered field type. `array` and `object` values are parsed as JSON from XML/text payloads, and invalid values fail loudly.
- Thing entity fields can opt into the edit modal with `exposeToEditModal: true`; `edit.inputType` supports `text`, `textarea`, `number`, and `checkbox`, with defaults derived from the registered field type.
- `clearThingSlotWhenPresent` is Thing-only. It is used by special equipment-like systems whose compatibility field should never make the item use normal gear slots.
- Registered Thing XML tags fail during registration when they collide with built-in item XML tags.
- Dynamic entity field `descriptionProvider` and `xmlPromptPlaceholderProvider` callbacks are evaluated when snapshots are requested. Non-string provider return values fail loudly; `null` and `undefined` leave the registered fallback text in place. If both properties reference the same callback, the registry evaluates it once per field snapshot and shares that result between the description and XML placeholder.
- Thing image badges are sorted by numeric `order` and then id. Badge asset URLs are validated at registration time so mods cannot point at arbitrary application paths. If a badge uses `assetPathSetting`, the client resolves the configured path under the same registering mod asset root.
- Thing context actions are sorted by numeric `order` and then full id. `fieldName`/`fieldValue` control client visibility, while the server handler performs authoritative validation.
- XML event prompt schema entries are injected into `prompts/_includes/events-xml.njk` through `modEventPromptSchemas`, where the prompt renders each entry's `name`, `description`, and `xml`.
- Registered XML tags are looked up case-insensitively by tag name and by exact event key. Direct child XML is converted to object-shaped raw data before the mod parser runs.
- `getPlayerActionPromptSteps({ startStep })` derives the requested stage from the caller-supplied complete label and numbers that stage. The older explicit `{ step, startStep }` and multi-stage `{ startSteps }` forms remain available to non-template callers. A start label must use a stage prefix followed by one or more letters, such as `1g` or `3m`; later records advance alphabetically, including multi-letter suffixes. `player-action.njk` and `player-action.tinybrain.njk` call the Nunjucks global beside their built-in steps, so adding a built-in prompt item only requires changing the adjacent start label in the prompt template.
- In `player-action.tinybrain.njk`, every mod step is followed by an `llmparse('mod_step_' ~ step.number)` checkpoint. The prompt uses `tinyBrainText` and falls back to `text`; the default mod-step parser currently requires a non-whitespace response and preserves it in the conversation. TinyBrain requests the same prompt-owned starting labels as the standard prompt.
- Generation prompt instructions are collected through `collectGenerationPromptInstructions(generationType, context)` and sorted by numeric `order`, registration order, then full id. The server passes the prompt-render context into item, location, and region generator templates as `modGenerationPromptInstructions`; non-string `textProvider` return values fail loudly.
