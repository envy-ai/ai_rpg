# TinyBrainRetryContext

`TinyBrainRetryContext.js` builds the context retained after a TinyBrain section recovers from a parser/hook failure or failed native invocation. Clean sections retain their original transcript without requiring new hook declarations. The helper changes conversation context only; execution ledgers, tool budgets, retry counts, progress diagnostics and full attempt logs remain owned by their existing components.

`buildAcceptedTinyBrainSectionMessages({ originalMessages, attempts, retainedMessages, acceptedResponse, acceptedAttemptIndex })` receives the section's original input plus original instruction, producer-owned attempt transcripts, keyed hook receipts and the accepted response. Each attempt declares `{ inputMessages, messages, toolInvocations }`; completion and afterParse outputs are separate records. The exact input must remain a prefix of the returned transcript. Only newly appended messages are inspected; earlier accepted sections and unrelated user input are preserved unchanged. The accepted answer follows successful receipts from its completion and precedes successful afterParse execution receipts.

The resulting section contains its original input/instruction, successful native/server tool-call/result pairs, explicitly retained hook messages, and the accepted answer. Failed drafts, parser/tool errors, retry instructions, failed tool pairs and intermediate transport/continuation chatter are omitted. The accepted answer uses parser `normalizedResponse` when supplied; original model responses remain in the log.

Tool receipts are identified by actual invocation records in execution order. Failed calls are excluded before argument parsing, including malformed JSON failures. Successful calls must have valid arguments agreeing with their execution receipt and exactly one matching result. Mixed call bundles keep only successful calls and matching results. Identical repeated receipt IDs/name/arguments are deduplicated within the section. Reused IDs for different operations receive deterministic context-only suffixes on both the assistant call and its matching result; prior-section IDs are reserved, while actual invocation/debug/ledger IDs stay unchanged. Inconsistent claimed-success protocol fails explicitly rather than losing committed results. Context-contract errors stop execution without rerunning committed mutations.

`validateTinyBrainRetainedMessages(previousMessages, hookMessages, declarations)` checks explicit hook provenance for recovered sections. `afterParse` results may return `retainedMessages: [{ key, message }]`; retry errors use `tinyBrainRetainedMessages` with the same shape. Each new hook-authored user message in a recovered section must be declared, or execution fails clearly. The runner annotates declarations with their producer's `attemptIndex`. Latest declarations replace earlier declarations with the same key inside the current section only and move to the latest producer's position. Player-action resolution receipts use `player-action-resolutions`, allowing an accepted complete ledger note to replace a partial-success note after the accepted plan.

A hook throwing after partial execution supplies `tinyBrainRetryConversationMessages` and `tinyBrainRetryToolInvocations` so actual successful protocol receipts remain visible and survive eventual cleanup. Scheduled-event execution attaches successful partial invocations to its exception; its API hook supplies their transcript and logs those receipts. During active retries, failed attempts and correction feedback remain available. Cleanup runs only after recovery and parser/hook acceptance, for both checkpoints and final stages, and cleaned messages flow into continuation state. Fatal/exhausted failures log and propagate their original error/cause before any new retry-provenance checks.
