# PromptAuditLog

`PromptAuditLog.js` keeps an ephemeral prompt-error audit for each gameplay request. It writes one `logs/<timestamp>_turn_prompt_errors_<unique-id>.log` after the actual handler and its owned text/continuity work finish. Writing is asynchronous and does not delay the HTTP response or serialize turns. Clean turns produce a brief zero-error summary.

The file identifies the request/audit ID, route, start/end world location, logical prompt family, section/checkpoint/parser, attempted positions, phase/category, compact error heading, counts, recovered versus failed outcomes, tool name, source site and available detailed-log paths. Categories include context limits, timeout, rate limit, transport, XML, parse, validation and tool failures. Error headings omit quoted values, structured/XML fragments, credentials and request/configuration fields. Prompt bodies, headers, full stacks, secrets and world-state dumps are not copied; existing complete logs remain authoritative.

## Initial Output Latency

Every dispatched `LLMClient.chatCompletion` transport attempt also writes one JSON line to `logs/completion-timing-YYYY-MM-DD.jsonl` and prints the same `LLM completion timing:` JSON to the server console. This has no latency threshold, so a two-second wait is retained. A request-local `completionId` and one-based `attempt` distinguish retries and concurrent completions; owned turns additionally carry `requestId`, `auditId`, `promptId`, and stage. Rows include UTC invocation, attempt, dispatch, transport-end, and attempt-end timestamps; backend, streaming mode, and outcome. The file is append-only and separate from the thresholded turn audit. Forced outputs and cassette replay without transport produce no timing row.

`beginCompletionObservation({ metadataLabel })` is the request-scoped event interface used by `LLMClient`. It composes the logical `beginStartupLatency` tracker with the per-attempt `beginCompletionTiming` recorder, forwarding dispatch and first-output events once to both. It accepts raw response/SSE metadata through `observeResponse`, brackets retry waits through `duringRetryDelay`, and keeps attempt finalization separate from logical completion finalization. The two underlying recorders remain available for focused instrumentation and tests; their existing audit thresholds and JSONL row format are unchanged.

`preparationMs` measures each attempt's preparation and queue wait before dispatch. `completionToDispatchMs` includes any earlier retries for later attempts. `dispatchToFirstOutputMs` measures actual dispatch to first output; `ttftMs` is set only for incremental streaming text, reasoning, or tool-argument content. Non-stream calls and CLI bridge final snapshots instead set `firstResponseMs`; token-chunked non-stream calls set `firstChunkMs`. No-output attempts leave all first-output fields null. `transportDurationMs` and `firstOutputToTransportEndMs` describe the transport/generation window. `postTransportMs` measures validation, callbacks, and retry handling after transport, while `retryBackoffMs` identifies measured wait time within that window. `attemptTotalMs` and `completionElapsedMs` give the attempt and elapsed logical-completion durations. HTTP headers, keepalives, usage-only events, and tool IDs/names without generated arguments never mark streaming first output.

Each row also captures the attempt's model and effective LLMClient request settings at dispatch: `requestMaxTokens`, `requestMaxCompletionTokens`, `requestStop`, and `requestStopSequences`. `settingsForwardedToProvider` is false for CLI bridges, whose adapters do not forward these payload settings. `providerResponseId` and `providerFinishReason` come only from raw HTTP provider responses or SSE chunks; they remain null for CLI bridges because bridge response IDs and `stop`/`tool_calls` finish values are synthesized. `promptTokens`, `completionTokens`, `totalTokens`, `cachedInputTokens`, and `reasoningOutputTokens` contain only observed finite numeric usage values or null. CLI bridge input/output usage is mapped to prompt/completion fields when available. Streaming finish reasons and usage-only final chunks are captured as they arrive, even if later stream handling or validation fails. Fields are isolated per attempt; partial chunks do not erase previously observed values. These rows log neither request bodies nor credentials.

`prompt_audit.high_latency_seconds` defaults to `5`; a measured wait equal to the threshold qualifies. It must be a positive finite number, with fractional seconds supported. `resolveHighLatencySeconds(config)` supplies the same strict validation at startup, persistence, reload and tracker creation.

`beginStartupLatency({ metadataLabel })` captures the invocation's async-local owner, stage and threshold before preparation/queueing. Its `transportStarted()` marks the earliest actual dispatch; calls across retries keep that first time. `firstOutput({ kind })` finalizes exactly once with `first_generated_output` for actual streaming text, reasoning or function output, `first_response` for non-stream responses, or `first_chunk` for chunked non-stream generation. Headers, keepalives, usage-only updates and call IDs alone do not count. Non-stream measurements describe response arrival, not first-token timing. `finish({ outcome })` records the actual observed wait as `no_output` if a dispatched completion ends, fails or is cancelled before output. Invocations without actual transport, including forced outputs and cassette replay, are omitted.

The tracker remains one measurement across transport retries and continuations, so a 500-token chunked response does not produce one entry per chunk. Timing includes queue/preparation and separately reports its total when available. Captured callbacks retain the correct owner even outside their original async-local context; shared image text batches fan out to their captured source turns. There is no global latest-turn attribution or GPU wait.

`recordStartupLatency(durationMs, details)` records a measured duration directly; `thresholdSeconds`, `kind`, `outcome`, `preparationMs`, `metadataLabel`, `attempt` and `logPath` can supply measurement provenance. Snapshots expose separate `latencyCount` and `latencyRows`, with grouped count, `totalMs`, `maxMs`, `preparationTotalMs`, threshold, kind, outcome, checkpoint/parser, attempts, location and detailed-log references. Slow waits never increment error/cancellation counts or imply a cache miss. Latency rows share the existing turn file, cleanup and explicit late-record handling.

## Ownership And Lifecycle

- `runTurn({ requestId, route, startLocation, getLocation, logDirectory }, callback)` establishes an async-local owner. Nested gameplay calls join it. Actual callback settlement closes foreground ownership; `res.finish` does not flush early. `currentTurn()` returns its opaque in-memory owner.
- `runPrompt({ metadataLabel, kind, join }, callback)` owns a logical prompt, with matching labels joining their current owner. `runStage({ stage, parser, checkpoint }, callback)` tracks an independent section outcome. Thus an accepted section remains recovered when a later section ultimately fails. `setAttempt(attempt)` identifies the current section attempt.
- `recordFailure(error, details)` records actual occurrences. `propagated: true` deduplicates the same exception/cause or tool-call IDs as it crosses layers; separate actual attempts still count separately. `terminal: true` preserves failed status when a legacy handler reports failure and returns an empty result. `acceptStage()` clears that terminal marker only after explicit successful validation. Explicit cancellation is recorded separately and never becomes an error occurrence.
- `captureFailureBoundary()` and `details.since` limit manual-loop propagation deduplication to failures raised within that actual attempt, including when an executor reuses an Error object on another attempt.
- `trackWork(promise)` reserves the current owner until that work settles and returns the original work. `reserveWork()` returns `{ run(callback), release() }`, capturing its exact owner before deferred scheduling. Chooser and plot-analysis `setImmediate` callbacks reserve at schedule time; they never attach to a global most-recent turn or a generation-wide drain.
- A reservation captured outside a turn explicitly restores that absent context when run later. Ownerless image requests therefore remain ownerless inside a shared batch rather than inheriting the batch's forwarding context and recursively dispatching their own diagnostics.
- `withoutTurn(callback, { failureContexts })` runs a shared queued text request without assigning it to its first caller. Errors, cancellation and log references fan out through captured per-request handles to their originating logical image-prompt scopes. Shared image batching retains its ordering and model-call behavior; audits wait for text generation, never GPU rendering.
- `addLogReference(path)` associates both existing and later failure rows with known prompt/error logs. References retain full filenames, including long or bracketed names, so the detailed file remains locatable. `snapshot(owner)` exposes ongoing compact grouped diagnostics without prompt contents; `waitForFinalization(owner)` waits for the artifact when explicit tooling/tests need it.

After finalization, grouped rows and transient references are released. Unexpected late owned failures append a clearly marked `LATE` row to the same file and emit a warning rather than disappearing or creating a second turn log. A write/append failure warns with the original filesystem error; explicit finalization waiters observe write rejection. Logging failures do not replace gameplay outcomes.

## Instrumented Paths

API owners cover `/api/chat`, canonical player movement, NPC teleport, crafting, location modification and checked-container opening. Nested NPC/event/generation prompts inherit the request owner. Background continuity work is associated with its own captured owner, even when multiple turns overlap.

Shared hooks cover `LLMClient` retry/validation failures, TinyBrain checkpoint/final corrections, native tool failures, terminal `PromptFailureReporter` reporting, and every production `runPromptWithParseRetries` caller with its real metadata label. Recovered attempts remain auditable after TinyBrain removes failed context. Manual hooks cover slop parser retries, image text validation retries, player ability option completeness, NPC level-up empty/missing/non-novel ability responses and progression validation. Swallowed post-response parser/application failures in plot, supplemental and offscreen background work are explicitly recorded without changing their existing behavior.

Audits never enter chat history, provider messages, saved state or the debugging UI. Existing retry budgets, prompt logs, failure notifications and authoritative tool receipts are unchanged. Background image rendering itself is outside this text-prompt audit; only owned text-generation requests extend turn finalization.
