# Server and LLM Flow Notes

This document describes the server and LLM runtime as it exists in the codebase. It is organized by responsibility rather than by implementation history.

## Startup and Runtime Wiring

`server.js` loads merged configuration from defaults, `config.yaml`, an optional `--config-override` file, and the active save's `gameConfigOverride.yaml` when a save is loaded. It initializes `Globals`, Express, HTTP, `RealtimeHub`, Nunjucks prompt/view/image environments, image clients, lorebooks, `ModLoader`, `ModExtensionRegistry`, `QuestConfirmationManager`, and the in-memory world maps for players, things, skills, factions, locations, exits, regions, pending region stubs, pending images, and in-flight generation jobs.

Runtime configuration validation is centralized through `validateConfiguration()` and `LLMClient.getConfigurationErrors()`. The OpenAI-compatible backend requires an endpoint, model, and either API key or OAuth configuration. The `codex_cli_bridge` backend requires a model plus valid `ai.codex_bridge` command, session, sandbox, reasoning, and timeout settings. The `cline_cli_bridge` backend requires a model plus valid `ai.cline_bridge` command, provider, working-directory, thinking, compaction, and timeout settings. The `kimi_cli_bridge` backend requires a valid `ai.kimi_bridge` command and string settings, uses the authenticated Kimi CLI's saved model when its optional model alias is blank, and does not require endpoint/API-key configuration. Shared AI fields such as assistant prefill, system-prompt append text, reasoning effort, root `max_concurrent_requests_all_models`, and root `stagger_concurrent_prompts` are type-checked before use. Image-generation config, prompt flags, chat-tool config, mod overlays, and several gameplay config sections are validated before startup or reload completes.

Definition files under `defs/` can be overlaid by enabled mods. Enabled mod directories are resolved during startup and exposed through the frozen mod set; config reloads validate the requested state and report enable/disable drift, but running mods are not hot-swapped. Enabled mods can contribute definitions, prompts, chat tools, XML event types, settings fields, entity fields, UI assets, hooks, and validators through `ModExtensionRegistry`.

`server.js` builds the `apiScope` object passed into `api.js`. That scope supplies state maps, prompt helpers, generation helpers, save/load helpers, entity serializers, image/job helpers, event dependencies, mod services, and mutation helpers. `server.js` also exports selected save/load and region-exit travel-time helpers for scripts/tests.

The HTTP server is bound only when `server.js` is run directly (`require.main === module`). Other modules that `require('./server')` purely for shared runtime state (for example `LocationExit.js`, which reads `gameLocations`/`pendingRegionStubs` through lazy requires) get the module's exports and route registration without binding a port. This keeps importing shared state free of listening side effects, so tests and tooling do not hang on an open server handle or hit `EADDRINUSE` when a dev server is already running.

## Prompt Rendering

`promptEnv` is rooted at `prompts/`. Include paths in prompt templates are loader-rooted, so shared partials use paths such as `{% include "_includes/travel-prose.njk" %}`. The main wrapper, `prompts/base-context.xml.njk`, emits `<systemPrompt>` and `<generationPrompt>` nodes and includes `prompts/_includes/{{ promptType }}.njk` inside the generation prompt for most prompt families.

`parseXMLTemplate()` parses rendered wrapper XML and returns `systemPrompt`, `generationPrompt`, `temperature`, `role`, and `description` fields when present. Prompt bodies are wrapped in CDATA, and literal `]]>` sequences inside prompt bodies are split before XML parsing so dynamic story text cannot close the CDATA block early. Template parse failures are logged with `LLMClient.logPrompt()` and then rethrown.

Server-side Nunjucks environments share dice filters, numeric filters, the `eval` filter, rarity globals, `getSystemPromptPrefix(promptType)`, and `randomword()`. The prompt environment also exposes `getLocationInfo(name, id?)`, which resolves a loaded location by destination id when supplied or by an exact/substring case-insensitive name match otherwise, rejects missing or ambiguous matches, and returns its canonical name and full description. Stub locations use their persisted stub/blueprint description metadata when `description` is not populated. `randomword()` returns a random non-empty line from `data/words.txt` and throws if the word list cannot be read or is empty. The setting prompt context includes the active setting profile, writing instructions, currency labels, unified tonal scale selections, and hide/perception mechanics.

`prepareBasePromptContext()` builds the full game prompt context and starts deferred NPC memory-selection work. The context covers the active setting, world time/calendar, player and party, current location and region, exits, visible NPCs, an alphabetized `<allNpcs>` list of every loaded character with a short description, visible things/scenery, inventories, status effects, need bars, factions, quests, active mystery threads/boxes, plot analysis state, latest tonal-scale evaluation metadata, scene summaries, lorebook matches, and compact NPC race/class representation. Local-NPC and party-member records render authoritative `<isDead>true|false</isDead>` state; dead actors remain in continuity context but are excluded from the synthesized `<currentCharacterNeeds>` summary. The top-level `isExterior` Nunjucks variable defaults to false. `/api/chat` sets it to true only for an exit-button travel request whose resolved destination location name ends with `exterior`, matched case-insensitively; already being at an exterior location, ordinary actions, and map/Favorites fast travel leave it false. Player-action travel prompt variables also carry the resolved destination as `travelTargetLocationId` and `travelTargetLocationName`. The TinyBrain exterior branch resolves those values with `getLocationInfo(...)` and prints `Destination name` plus `Destination description` before its exterior/interior deferral checkpoint, so the model does not need to infer the exterior from prior prose or call the model-facing `moreInfo` tool. Compact item rows that render short descriptions include a separate `quantity N;` field after the item name, including single-count items as `quantity 1;`; nested container-content summaries use `Item Name: quantity N` for all contents. It supports caller-specific omissions for game history and prompt subsystems.

The base `<worldOutline>` labels every location with its short description plus a `Characters:` suffix. The suffix lists the player, NPCs, and active party members whose effective location is that location, sorted alphabetically, or `none` when no loaded character is there.

History rendering separates older story entries from the near-turn story window. Scene summaries replace older raw entries when coverage exists; hidden entries and event/status summary entries are excluded from scene-summary history blocks. Stored `metadata.worldTime` snapshots let prompt history labels use in-world relative time when available, while older entries without snapshots render without invented dates. `recent_history_turns` sets the minimum recent prose-turn window, and `recent_history_batch_interval` moves turns into older history in deterministic batches instead of changing that prefix every turn. Every base-context render marks the end of shared context so `LLMClient` can give all non-generic base-context requests the same ordered built-in-plus-mod tool schema and split prompt-specific instructions into a new user message; generic prompts retain their separate message and tool behavior. Previously tool-less paths receive `Do not make tool calls.` at the start of that prompt-specific message and remain direct completions. When `prompt_uses_caching` is true, the template also marks complete top-level section boundaries before older history, world index, current region/location, player, party, supplemental context, optional mystery/tracker continuity, and recent history. Cached requests therefore offer hybrid/recurrent backends several prefix checkpoints; a difference still invalidates all later tokens, but a nearby earlier checkpoint can prevent a full token-1 rebuild. Player-action slop removal reuses the exact parsed system prompt and rendered shared generation prefix from the player action, so every shared section remains byte-stable while the turn is processed. It does not clone live config or mod validator functions. Internal marker text is never sent to the model.

## `/api/chat` Turn Flow

`POST /api/chat` is the primary player-turn endpoint. It creates a realtime stream emitter from the incoming `clientId` and `requestId`, rejects the turn with `409` when player ability picks are pending, applies time-based need/status effects, snapshots world time, triggers region-secret work, prepares turn-local chat-entry collection, and runs autosave when configured.

The route classifies the request as normal player action, creative action, question, generic prompt, no-context generic prompt, prompt-only action, forced event, or travel-assisted action. Inline roll controls are stripped from player text before prompting: `<N>` supplies a raw die override to legacy checks and to TinyBrain/one-shot attack, shared area-attack, unopposed-skill, and opposed-skill tool calls; `<f>` forces per-check client input for skill-style tools without clamping the supplied die value and takes precedence over `<N>` for those skill checks. TinyBrain player-action does not predeclare a fixed checked-actor roster, because actors requiring checks may change during later drafts. Check tools still reject self-opposed calls and enforce their ordinary structured actor semantics.

Normal player actions render `base-context.xml.njk` with `promptType: "player-action"`. Creative actions, questions, generic prompts, and no-context prompts use their corresponding prompt types/templates. Player-action and creative-action responses may be parsed from XML-style `turnResult` or `moveTurnResult` output when repetition-buster XML mode is active. The non-attack TinyBrain player-action path parses movement/vehicle/destination/accompanying-character/prose/hidden/time checkpoints and assembles final XML through `PlayerActionTinyBrainResult.js`. A model-selected destination gets a `moreInfo`-only checkpoint whose parser accepts an `N/A` prefix without a successful lookup or a `READY` prefix after one; trailing blather is normalized away, and a successful lookup supplies local `READY` without another model round. Existing destinations inject name/description context immediately, without requiring rigid reproduction. Known authoritative or graph-derived travel minutes suppress duration estimation. Revisited destinations add expected-arrival absence, visible NPC names, and optional Markdown change planning. Accompanying-character selection accepts canonical names or aliases from living eligible actors and permits movement established explicitly or reasonably inferred; an empty allowlist skips the question. Committed exit-button destinations remain authoritative and fixed-route destination parsers still reject invalid route state. Vehicle occupancy guidance prevents vehicle movement/arrival from automatically disembarking an occupant, while deterministic `UNCHANGED` branches are assigned without asking the model. Rejected XML, WYWA bookkeeping behavior, and tagged invalid-route error propagation remain unchanged.

Fixed-route player-action destination retries retain the first syntactically complete normalized destination in checkpoint-local parser state. Feedback may correct its representation, but cannot replace an off-route request with a different allowed stop merely to pass validation; an impossible request exhausts the checkpoint without committing a turn.

With `ai.tinybrain: true`, the allowlisted family router can stage player actions, XML event checks, need-bar checks, quest rewards, game intros, random/creative/NPC prose, craft/location prose, checked containers, while-away updates, scheduled-event resolution, and interruption rewrites. Per-family flags can retain selected one-shot prompts. Need-bar staging separates planning from strict character XML. Player-action's nine editing questions remain individual checkpoints, while player agency is stated once and referenced by the railroading audit once; this is prompt guidance, never heuristic prose classification. `llmresult` invokes local builders not only for player action and events but also for quest reward, WYWA, game intro, NPC/non-travel random/non-travel creative prose, scheduled results/interruption merges, craft, location modification, and checked containers. These builders assemble already accepted prose and known fields rather than asking for exact reproduction. Their prose drafts and optional revisions pass through a prose-only parser first, so an accidental XML wrapper retries locally instead of becoming nested assembled markup. Parser/tool failures still retry only the active checkpoint. Scheduled planning may use read-only lookups before returning a supported structured plan; mutation calls remain deferred. Direct/no-change plans execute locally, and richer execution loops terminate locally when every accepted planned call has succeeded. Scheduled summaries remain nonempty/non-N/A model judgments. Interruption temporal and event contracts live in its system prompt and are referenced rather than duplicated. Each staged transcript retains one log, queue reservation, and progress group; live deslop still examines only designated player-facing prose. Initial log creation remains required, while later append failures warn and let the turn continue.

TinyBrain NPC narration is deliberately a supplied-outcome prose family rather than a mechanical tool stage. Before that family renders, the NPC-turn caller runs the existing attack detector/resolver for both legacy-check mode and TinyBrain NPC mode. TinyBrain NPC mode passes an explicit opt-in through `runAttackCheckPrompt` and `runAttackPrecheck`, since both helpers otherwise honor the global legacy-disabled early return. If the planned action is an attack, damage is applied and the staged prompt receives the exact attack summary. This closes the otherwise-invalid combination where tool-based config disabled the precheck while the TinyBrain program exposed only lookup tools.

When `ai.xml_repetition_fix: true`, each enabled TinyBrain family's effective model override must use the OpenAI-compatible backend. During each matching staged completion, a balanced explicit XML element over 50 characters that completes an exact `AA` suffix—or completes the fourth direct sibling in exact `ABAB`—aborts the active stream. The duplicate suffix and any partial tool call are dropped, the accepted assistant prefix plus exact user message `continue` are sent back to the model, and the continuation is stitched before normal parsing. Prior completed tool rounds remain in the TinyBrain conversation. The guard is independent of live deslop and fails explicitly after `ai.retryAttempts` recoveries.

Player-action, NPC-action, question, base-context generic, and specialized background prompts that already support model-emitted tool calls run through `runChatCompletionWithToolLoop()` rather than calling `LLMClient.chatCompletion()` directly. Non-generic base-context prompts all serialize the same schema, but only these existing tool-loop paths execute calls. Previously tool-less base-context paths remain direct completions and are explicitly instructed not to call tools. No-context generic prompts do not receive tools. Base-context generic prompts are excluded from schema unification and retain their existing broader world-mutation tool behavior.

Single-target attack results keep canonical defender id/name and target maximum health in their structured summary even when an attack misses or hits for zero damage. The tool formatter can therefore report a zero-damage hit from `attackOutcome.target` without throwing after the attack already resolved. Living hidden attackers are revealed by the authoritative resolution regardless of hit, and the returned location-refresh flag is preserved on misses.

The tool loop returns `conversationMessages` in addition to its final text and invocation metadata. This transcript contains assistant tool-call messages, tool results, and the terminal assistant answer; tiny-brain retries use it to retain tool work across checkpoint boundaries.

The route logs prompt/response artifacts with `LLMClient.logPrompt()` for primary prose, event, quest, slop, generation, and background prompts. The stored assistant prose is scrubbed, summarized, optionally passed through slop/repetition cleanup, and then followed by event checks unless the action type suppresses them.

After player prose is stored, `/api/chat` runs event checks, quest checks, travel finalization, cross-region destination exit travel-time backfill when needed, due vehicle arrivals, due scheduled events, event/status summary row creation, check-result row creation, while-you-were-away prompts on arrival, NPC turns, random events, supplemental story info, offscreen NPC activity scheduling, periodic mystery-box cleanup scheduling, scene-summary threshold scheduling, automatic hidden-NPC checks, NPC sighting recording, and `Player.finalizeTurn()` for all loaded players. The JSON response includes visible messages, world-time payloads, event payloads, refresh hints, check results, NPC turn results, quest results, and stream metadata when relevant.

NPC final prose, random-event prose, and visible while-you-were-away prose emit a `chat_history_updated` refresh immediately after storage. This lets the client display visible prose before the scoped event-check pass or result summaries finish.

Random-event seed pools are not generated while `random_event_frequency.enabled` is `false`. Existing seed pools are only inspected and consumed when random events are enabled.

## Chat Tools

Built-in tool definitions live in `chat_tool_calls.js`, and mod-registered tools come from `ModExtensionRegistry`. `LLMClient` assembles their full canonical ordered union for every non-generic base-context request so a prompt-type transition does not alter the serialized tool prefix. `requestUserInput` is omitted from every such request when `chat_tools.request_user_input_enabled` is `false`; attack/check tools are likewise omitted everywhere when `use_legacy_prompt_checks` is true. Generic and non-base-context prompts keep their existing caller-selected schemas.

The built-in tool categories are:

- Context lookup and history: `moreInfo`, `getHistory`, `getFullScene`, `listLocationEntities`, `getTravelTime`, `locateNpcs`, and `locateThings`.
- Story Tools editing: `editChatLogEntry`, `rerunSceneSummary`, `editSceneSummary`, mystery-box tools, and mystery-thread tools.
- Utility tools: `generateRandomInteger` returns one random safe integer in an inclusive `min`/`max` range and is exposed to selected generation prompts.
- World/entity operations: teleport tools, stub and exit creation tools, hide/reveal tools, `createThing`, `createNpc`, `deleteThing`, tracker tools, `scheduleEvent`, `createQuest`, `alterThing`, `alterNpc`, `alterLocation`, `updateCharacterFields`, `updateObjectFields`, `upsertFactionFields`, and `updatePartyMembers`.
- Resolution tools: `resolveAttack`, `resolveAreaAttack`, `resolveSkillCheck`, and `resolveOpposedSkillCheck`; the runtime also supports plausibility-check aliases for compatibility with prompt-check paths.

Tool-call execution validates function names and JSON arguments, emits lifecycle events for check-result/debug rows, caches repeated check/attack calls within a prompt round, respects top-level `max_tool_calls`, returns tool-visible XML error payloads for recoverable tool failures, and logs tool failures through `LLMClient.writeLogFile()`/`LLMClient.logPrompt()`. When a request supplies a tool schema, that schema is also the execution allowlist: a provider-emitted call to any other registered tool returns `tool_not_declared` to the model and never reaches the tool executor. Requests without an explicit schema retain the runtime's full built-in/mod tool surface for compatibility. TinyBrain's player-action destination lookup preserves its explicit one-tool base-context schema and therefore exposes and permits only `moreInfo`.

`resolveAttack` and `resolveAreaAttack` return explicit authoritative defeated/not-defeated wording alongside damage and remaining-health percentages. A surviving target's tool result directly tells the prose model not to portray that target as dead, incapacitated, or defeated, so low positive health cannot be mistaken for a defeat threshold. At zero health, the prose model chooses the narratively appropriate supported outcome—death or incapacitation—instead of code forcing death. The temporary one-result/one-attack prose micro-policy was removed: a turn may contain multiple attacks, but every mechanically consequential attack still requires its own resolved result. TinyBrain NPC attack checking therefore accepts multiple mechanically complete `<attack>` blocks, validates the acting character and numeric mechanics of each, and retries that structured checkpoint with parser feedback. No regular expression or prose classifier attempts to infer attacks from narration. `resolveAreaAttack` resolves one shared area effect, records one grouped `area-attack` check-results row, and carries per-target attack summaries so the client can show the regular attack breakdown for each affected target.

## Event Checks

`Events.initialize()` receives its dependencies from `server.js`: prompt rendering, template parsing, base-context construction, entity lookup/creation, exit wiring, item/NPC generation, image generation, quest confirmation, currency labels, world maps, and timing constants.

`Events.runEventChecks()` returns `null` when event checks are disabled or the text to inspect is blank. Otherwise it prepares base context for the relevant location, validates its dependencies, and uses the XML event pipeline unless `event_checks.use_xml` is explicitly `false`.

The XML event pipeline renders `base-context.xml.njk` with `promptType: "events-xml"`, calls `LLMClient.chatCompletion()` with metadata label `event_checks`, requires a parseable `<events>` block, logs with prefix `event_checks_xml`, parses XML event tags into the shared structured event shape, injects dedicated need-bar prompt results, and applies outcomes through the same handlers used by the compatibility path.

Need-bar event checks use `promptType: "need-bars"` only when need-bar definitions exist. They launch after one `stagger_concurrent_prompts` interval, require a `<characters>` block, parse affected bars plus optional reasons, log as `need_bar_event_checks`, and merge entries into `needbar_change` before outcomes are applied. With the dedicated TinyBrain family enabled, one plain-text plan is followed by one strict XML characters phase in the same retained conversation. That phase still asks for reasons of ten words or fewer to discourage paragraph-length explanations, but the parser does not enforce the word count or reject an otherwise valid result for exceeding it.

The compatibility event-check path, selected with `event_checks.use_xml: false`, renders grouped `promptType: "event-checks"` prompts based on `EVENT_PROMPT_ORDER`, requires `<final>` blocks, aggregates numbered answers into the structured event shape, merges need-bar prompt entries, and applies outcomes through the shared handlers.

For top-level XML or legacy event-check passes, `Events` starts the silent `housekeeping` prompt registered by `api.js` as soon as event-check prompt context is ready, so the model request can overlap the event, need-bar, and quest checks. It renders through `base-context.xml.njk`, logs as `housekeeping`, serializes the shared non-generic schema for cache stability, and is instructed not to call tools. It does not run a model tool loop or write its assistant response to chat history. The returned `<housekeeping>` XML is still parsed and applied only after event outcomes and follow-up event checks finish, through the shared `createQuest`, tracker, and relationship executors. Deferred finalization treats strict XML and semantic parser failures as correctable prompt failures: it retries with the precise parser error, logs every attempt, and applies only the first accepted complete document. Rejected attempts cannot partially mutate housekeeping state or advance its history boundary. When `debug_tool_calls` is enabled, accepted XML-derived executions are mirrored into the same prompt-excluded `tool-call-debug` entry used by tool-loop prompts. Recursive follow-up event checks and callers using `suppressHousekeeping: true` skip housekeeping so one event pass does not create duplicate maintenance prompts. The while-you-were-away scoped event pass uses that suppression because the main turn already runs housekeeping. Sectioned TinyBrain `<moveTurnResult>` origin, between, destination, and tracker sub-checks also suppress automatic housekeeping; after all are merged, `api.js` runs one housekeeping prompt with the combined travel prose and final location.

XML travel events are phased around `moveLocation`/`moveNewLocation` and `<arriveAtLocation/>`: origin events apply first, the move applies separately, transit tags are ignored, and destination events apply after arrival. Travel time is authoritative; event-authored `timePassed` is suppressed for normal travel-boundary responses unless the boundary targets the active in-motion vehicle destination. `initialTimeProgress` prevents double-applying time already advanced by player-action parsing.

Outcome handlers mutate world state for movement, exits, locations, things, containers, NPCs, party membership, combat, status effects, needs, currency, XP, quests, dispositions, faction reputation, hidden NPC checks, mystery boxes/threads, scheduled events, and follow-up event text. The return payload carries HTML/raw event text, structured events, awards, resource deltas, NPC/location refresh hints, quest outcomes, hidden-NPC checks, follow-up results, and time progress.

Quest checks are separate from event checks. `Events.runQuestChecks()` requires `quest_checks.enabled: true`, active unpaused quests, and a prompt-indexable quest list. It renders `promptType: "quest-check"`, validates XML, logs as `quest_check`, and `/api/chat` applies parsed objective/reward results into the same response and event-summary surfaces. Normal player-action turns launch quest checks after two `stagger_concurrent_prompts` intervals.

## LLM Client

`LLMClient.chatCompletion()` is the common text-generation transport. It resolves the effective AI backend, model, endpoint, API key/OAuth token, headers, custom payload arguments, model overrides, temperature, top-p, penalties, seed behavior, optional system-prompt append text, optional OpenAI-compatible assistant prefill, stream mode, timeout, retry waits, reasoning effort, the per-key concurrency semaphore, and the optional root all-model semaphore for each attempt.

Root `unload_model_on_switch` defaults to false. Router-backed startup first loads root `router_preload_model` when it is nonblank, otherwise `ai.model`; an explicit preload value, enabled model-switch unloading, or effective router-based image handoff activates this startup step. Loading is idempotent, completes before default-player generation can start a prompt, and registers the loaded endpoint/model as the initial switch target. When switch unloading is enabled, real transports are serialized through exclusive model-lifecycle access. A different effective target unloads the previous model through llama.cpp `GET /models` plus `POST /models/unload` and waits for `unloaded`. For the same game-owned local router, it first saves slot 0 under the absolute configured `ai.router_slot_cache_directory`. When the replacement has a saved cache, the game sends its restore immediately and relies on router autoload/wait before restoring, then deletes the cache. Without a cache, it sends the prompt immediately and relies on router autoload/wait rather than explicitly loading and polling the model. Prompt progress begins before lifecycle waiting so this delay is visible to the client. Slot save/restore failures warn and continue; unload and eventual prompt failures remain fatal, as does a post-restore deletion failure. This comparison includes prompt-specific model overrides. Same-target prompts skip router management, forced-output fixtures do not change tracking, and remote routers do not use the local slot-cache lifecycle.

On `SIGINT`, `SIGTERM`, startup failure, self-restart, or ordinary process exit, the server removes the exact slot-cache paths belonging to configured or runtime-observed local-router models. Graceful termination stops the managed router before asynchronous deletion; the synchronous exit hook is an idempotent fallback. The cleanup does not scan or remove unrelated files from the shared cache directory.

The qwen-combo-router local startup path targets `scripts/start-qwen-combo-router.sh`. That wrapper invokes the shared Prism router launcher with `--no-mmproj` and the model-specific `config/llama-qwen-combo-text-only.ini` preset. Router directory discovery otherwise turns sibling projector files into explicit child `--mmproj` arguments even when automatic discovery is disabled; the custom preset replaces those two explicit values with empty paths. The Qwen workers therefore remain text-only and llama.cpp slot persistence stays available without deleting or moving the installed projectors.

OpenAI-compatible calls use normalized `/chat/completions` endpoints and stream by default unless disabled. `codex_cli_bridge` calls delegate transport to `CodexBridgeClient`, keep prompt progress on the same broadcast path, normalize the response into OpenAI-style choices/messages, and report Codex usage/quota notices when usage metadata is present. `cline_cli_bridge` calls delegate transport to `ClineBridgeClient`, run one authenticated Cline CLI subprocess per request, pipe the bridge prompt through stdin, stream JSON-wrapped or plain preview text from Cline NDJSON events, and normalize the final bridge JSON or plain assistant text into the same choices/messages shape. `kimi_cli_bridge` calls delegate to `KimiBridgeClient`, launch a fresh authenticated `kimi acp` process, send the complete prompt through ACP JSON-RPC on stdin, incrementally decode wrapper `content` text from ACP assistant chunks into prompt progress, advertise no client filesystem/terminal capabilities or MCP servers, reject native Kimi tool activity, and normalize strict final bridge JSON content/application tool calls into the same choices/messages shape.

Metadata labels drive model override profiles, prompt-progress targets, prompt-output character statistics, error-log labels, and prompt logs. `ai.custom_args` and `ai.headers` can be merged globally and per override profile; `null` deletes inherited keys in override objects, and reserved core payload keys are rejected from custom args.

`ai.prefill` and override-profile `prefill` add a final assistant message for OpenAI-compatible providers that support assistant response prefill. Runtime response normalization returns the prefill and generated continuation as one assistant text, rejects tool-call requests, and does not support CLI bridges.

Streaming responses assemble text deltas and `delta.tool_calls` chunks. Non-stream responses normalize `message.tool_calls` the same way. Tool-call-only responses skip XML/regex validation and prompt-output character averages. Text responses strip `<think>` blocks before validation/return, can enforce required regexes or XML tags, and can validate strict XML when requested.

Prompt progress is broadcast through `Globals.realtimeHub` as `prompt_progress` and cleared with `prompt_progress_cleared`. Staged requests can share a `progressGroupId`; parse failures in a group also emit `prompt_progress_group_failure` with the ordered failed response text for the persistent viewer. Targets come from configured `prompt_progress.character_targets` or stored averages in `logs/prompt-output-character-stats.json`; missing target coverage throws a clear error when progress tracking is active. Successful text completions update the stats file atomically.

Cancellation and retry are keyed by stream/prompt id. `/api/prompts/:promptId/cancel`, `/api/prompts/:promptId/retry`, and `/api/prompts/cancel-all` call the corresponding `LLMClient` APIs and can also cancel pending player-input tool requests for a client. Retry intent aborts the active attempt and re-enters the retry loop; cancel intent returns an empty response to the caller. Both user-requested and automatic failed-attempt retries take the front position in their existing foreground/background queue lane at the per-model and optional all-model gates.

`LLMClient.logPrompt()` writes prompt artifacts under `logs/` with model/endpoint info, prompt-output stats, optional request/response payloads, system prompt, generation prompt, reasoning, custom sections, and response text. `writeLogFile()` writes structured error logs using `ERROR_<prefix>_<metadataLabel>_<timestamp>.log`.

## Background and Generation Prompts

The same base-context wrapper is used by specialized prompts for generation and maintenance work: location/region generation, NPC generation and aliases, inventory generation, barter pricing, item/thing creation and alteration, crafting and harvesting, scene summaries, plot analysis, plot summaries/expanders, tonal-scale evaluation, supplemental story info, offscreen NPC activity, mystery-box cleanup, scheduled-event resolution, while-you-were-away prose, slop removal, XML repair, skill generation, faction generation, image prompt generation, and region exit travel-time backfill. Travel-time backfill renders `base-context.xml.njk` with `promptType: "set_travel_times"`, passes the destination/current region summary plus pending zero-minute exits into `prompts/_includes/set_travel_times.njk`, and logs with the `set_travel_times` label. Cross-region player arrivals invoke it for the destination region before move duration is resolved, using the destination location as the base-context location. Prompt/render/LLM/parse failures return a nonfatal `promptFailed` result and are logged as warnings, so movement continues with existing travel times.

Region layout generation, region-stub location generation, location generation, location thing generation, inventory generation, named item generation, container contents generation, single NPC generation, location NPC generation, and region NPC generation run through `runGenerationPromptCompletion()`. That helper exposes only `generateRandomInteger` to those generation prompts and tells the base-context policy to preserve that restricted schema, preserving the normal prompt logs while allowing unbiased random integers without exposing unrelated mutation tools. It sets `prefill: null` because `LLMClient` rejects assistant prefill when tool schemas are present. Pending region-entry generation strictly validates the complete `<region>` document and every consumed component before instantiation. Malformed XML, a wrong/missing root, or no direct location entries triggers a fresh completion from the original prompt plus the exact structured-parser error for `ai.retryAttempts + 1` total attempts; every attempt and rejected response is logged. The rejected large document is deliberately omitted from correction context because retaining it caused the local model to copy the same malformed XML byte-for-byte across the whole retry budget. Location item/scenery generation follows the same configured retry semantics rather than stopping at an unrelated hard three-attempt ceiling, but retains its smaller rejected response as the next assistant message and follows it with the exact parser error. Each attempt's prompt log includes the effective retry conversation. The prompt states the exact top-level item/scenery entry counts, explains that an inner `<count>` is stack quantity rather than batch cardinality, and tells the model to close the root immediately after the requested entries. Container-content generation additionally requires strict XML and an exact multiset match between generated item names/counts and the saved pending seeds before creating any objects; the API coalesces concurrent generation requests per container. The location stub-expansion, location NPC, and location things templates define `isExterior` by case-insensitively checking whether the trimmed location name ends in `Exterior`, making exterior-aware prompt branches available locally. The stub-expansion prompt derives its character-concept display name directly from the guarded `stubName` string and strips the trailing ` Exterior`; it never dereferences a `.name` property on that string, so exterior unstubbing cannot abort the player move during prompt rendering.

Location item/scenery generation validates each complete response with the strict Thing XML parser before creating any `Thing` records. It then requires exact top-level item and scenery cardinalities plus exact per-kind rarity multisets; stack quantities do not alter those entry counts. Empty batches, malformed tags, invalid registered-field JSON, extra or missing entries, wrong item/scenery kinds, and wrong rarity mixes cause a parser-guided complete generation retry in the same conversation. After the configured attempt budget is exhausted, the error propagates through location expansion instead of being converted to a successful empty location. Explicit zero-item/zero-scenery generation hints remain a valid no-generation result.

Image generation is optional and can use ComfyUI, NanoGPT, or OpenAI image clients. The server tracks image metadata, image jobs, per-entity active jobs, location weather/lighting variants, uploads, and prompt batching. Prompt-backed image generation uses the image prompt environment rather than `promptEnv`. A nonblank root `ai.local_startup_script_path` makes the game start and own the executable before router preloading or startup prompts, regardless of the image-handoff flags; startup waits for the configured OpenAI-compatible endpoint's `/health`, and normal game shutdown terminates the saved process group. With an effective AI model's `unload_during_image_generation` enabled, every real LLM transport first acquires shared model-lifecycle access and strictly sends ComfyUI `/free` with model-unload and memory-release flags; the request does not start if cleanup fails. A cleanup-only ComfyUI client is initialized even when rendering is disabled. For image prompts, batches also flush immediately and must become quiescent before rendering. `LLMClient` then grants exclusive model-lifecycle access, llama.cpp router management unloads the effective model, the image queue drains, and the server invokes Cache Monitor's `/comfyui-cache-monitor/release_vram` endpoint before the text model reloads and queued LLM requests resume. A failed Cache Monitor request falls back to full `/free` cleanup and broadcasts `comfy_cache_monitor_fallback` so browsers can recommend installing the custom nodes; the warning can be permanently suppressed per browser with localStorage. The mutually exclusive `terminate_during_image_generation` mode adds local-process render handoff: initial startup strictly clears ComfyUI immediately before spawning; before each managed-local prompt, exclusive lifecycle access compares its effective startup path with the active path, reuses matching scripts, or fully stops the old process before cleaning ComfyUI and starting a different script. Render cycles signal the saved process-group PID, drain ComfyUI work, then use Cache Monitor's partial VRAM release—or the same full-cleanup fallback—before starting the currently selected script and reopening the text gate.

Scene-summary generation indexes prompt-eligible chat entries through `scene_summary_index.js`, excludes event/status summary entries, preserves hidden supplemental/offscreen entries in the index, parses only the final `<scenes>` block from the response, and stores scenes with summaries, details, quotes, and entry bounds. Scene summaries can be rebuilt through slash commands and Story Tools chat tools.

Save/load flow persists world maps, chat history, summaries, images, settings, metadata, world time, pending region stubs, scheduled events, and the loaded game's raw config override. Load reconciliation repairs invalid faction references, normalizes mod/save metadata, clears party members from location NPC lists, resolves pending ability-selection state, and fails loudly when required setting hide/perception mechanics cannot be generated or validated.

## Compatibility Modes

The event system retains the grouped event-check path behind `event_checks.use_xml: false`. Prompt-check aliases for plausibility/skill resolution are still accepted by the chat-tool runtime. Saved chat/event entries without newer metadata remain readable by client and prompt-history renderers, but the runtime prefers explicit metadata when present.
