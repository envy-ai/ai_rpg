# StoryEditor

`public/js/story-editor.js` owns the no-game Stories workspace. `views/story-editor.njk` is content rendered inside the registered generic mod page shell at `/mods/story-authoring/pages/stories`; its optional story/node path segments and `tab` query select stable identities. The script boots only when `#story-editor` exists, because mod browser assets also load on Play. The authoritative stylesheet is `public/scss/story-editor.scss`, compiled into `public/css/story-editor.css`.

## Library and outline

The library creates/imports/opens/duplicates/archives/restores/exports standalone projects without a Player. Search, title/update/creation ordering and archived visibility are local presentation of validated server summaries. Import asks whether to allocate a new copy or retain an unused identity; exports use the versioned portable document returned by the server. Corrupt library files remain visible errors.

The hierarchy uses native nested disclosures and lists, stable node links, ancestors, sibling Previous/Next/Up and ordered review lists. It is not an ARIA tree. Browser Back/Forward and refresh restore the selected stable node/tab. At narrow widths the outline opens in a focus-trapped modal drawer, while the editor stays a naturally scrolling column.

Each level exposes every typed content field, with labels above controls. Root premise, Main plot, style/constraints, author notes, dramatic intent, setup/conflict, prerequisites, revelations, unresolved threads, incoming/outgoing intended continuity and references remain editable. Sub-scenes separately expose actor goal AND actor notes, observable criteria, unfavorable resolutions and private author direction. Additional fields are folded, not omitted. Inherited notes identify and link their source independently of local notes. Written/active sections and actual evidence are read-only.

Human approval is revision-specific and separate from accepting a suggestion, YOLO machine acceptance, execution status and accepting an actual outcome. The editor explains the global current-parts gate for chapter expansion and the branch-local chapter/scene gates. The server remains authoritative. Explicit selected-part approval never implicitly approves descendants.

Local content and source-choice drafts retain their captured server revision separately from the current project. For content buffers, consecutive observed revisions may advance without a conflict only when the saved baseline and all authored context are unchanged: only generation records and transaction bookkeeping differ. Node content/history/review/structure/execution, project guidance, sources, bible, binding, receipts and setup records still participate in the comparison. Dirty text stays intact and any safely advanced dirty revision is persisted with its draft. Saving during active generation first reads the current project to account for job status writes; it still submits the captured expected revision. Genuine content/context changes or an older unverified baseline retain the original revision and require explicit conflict review. Dirty drafts are also retained in namespaced session storage for refresh. Polling never replaces typing. Save failures/conflicts keep buffers; conflict review compares local and saved content and requires explicit acceptance of refreshed context before retry. Navigation asks Save / Keep editing / Discard. A story save never implies a game autosave.

## Main plot

The root form places **Main plot** immediately after **Premise**, before **Intent**. Its six-row textarea edits the existing canonical `root.content.outline`; other levels retain their **Outline** label. Main plot describes the overall conflict, progression and intended ending, while Premise stays a brief initial idea. Existing outlines are shown unchanged. Editing the premise does not overwrite the Main plot.

New story includes the same Main plot control after Premise and before folded options. Explicit Create may leave it blank for later editing; a missing-field generation proposes a nonblank complete plot. The creation payload's `mainPlot` becomes root outline without copying or deriving it from premise. Saved stories, exports and imports use only the existing root outline field.

Outline generation uses the Main plot to guide a finite arc through ordered parts, with chapters, scenes and sub-scenes progressing their parent purposes toward specific stopping points. Existing sections remain in place. Planning is private author intention; actual play agency, checks and unfavorable outcomes remain authoritative.

## Generation and YOLO

Generation creates a retained proposal. Expand suggests a missing child collection; refinement scopes a node, selected unwritten siblings, or unwritten descendants. Regeneration feedback is transient suggestion guidance, separate from permanent Author notes. Current/Suggested fields are compared with text labels and change styling; Apply creates drafts, Keep current rejects. Future revision proposals permit explicit selection of changes. Stale apply errors retain both the suggestion and local draft.

The job activity panel reconnects from persisted server jobs, presents every terminal state and original error stack, and exposes job-owned cancel and new-suggestion retry. Each Activity render replaces the `story-authoring.editor` snapshot through shared `AIRPG_PAGE_FEEDBACK.setJobs(scope, jobs)`, including current-project jobs and YOLO runs with their actual named paths. Immediate enqueue/start updates use that same `ownerScope`. Library navigation, a different story selection and read-only saved projections clear only this editor scope. Omitted, terminal and paused records leave the dock; unrelated consumers retain their own scopes and owned prompt identities. Durable Activity retains terminal receipts/errors. Refresh never starts or retries work.

YOLO is off by default and has an explicit scoped enable checkbox, read-only named path, finite automatic/author-count structure policy and Start. Active scope is frozen independently of editor selection. It fills only missing outline content through sub-scene goals and labels machine acceptance distinctly from human approval. Pause finishes the current step; Cancel terminates owned work; Resume requires a review of refreshed context. Completed receipt counts are shown; unknown remaining workload is named explicitly, with indeterminate progress. No fabricated percentage or automatic Play/setup occurs.

A completed scope that needed no generation says “Nothing missing in this scope.” Traversal-only checkpoint receipts do not count as generated content.

## World, protagonist and setup

World and protagonist pickers are independent: neither, world-only, protagonist-only, and both are valid. World profiles are reusable recipes; current/saved game worlds include actual history. Saved sources are read for planning without Load. Character concept adaptation is distinct from same-world actual character reuse; incompatible full mechanics reuse surfaces server errors.

Binding preview shows provenance, compatibility/conflicts/adaptation and planned writes without runtime effects. A matching live-world/live-protagonist choice has a separate explicit Attach action. Materialization is a generated editable setup proposal with recursive typed field controls, concrete adaptation review, and explicit acknowledgement. The author chooses new cloned profile → existing New Game explicit Start, or create/select a protagonist in the actual current world while retaining history. Setup review visibly discloses conditional active-story attachment changes for the actual selected protagonist, including backend-confirmed preservation of prior written history/outcomes/preparation evidence in the separate library and unmet settlement/reconciliation prerequisites. A different unreviewed protagonist disables commit and links to the existing source-choice review; the editor does not change source choices or invent an alternate preview request. New Game instead explains that saving a profile leaves the current story/history in place and actual attachment occurs only at canonical explicit Start. Destination/protagonist changes clear the existing review acknowledgement; the same existing review/commit remains the approval step. Recorded setup retries keep their original envelope and completed stages, with remaining guards enforced by the backend. Source planned-write labels use story titles when known rather than internal story identities.

Setup receipts show committed stages and errors. Retry/resume uses the same reviewed request identity/fields, preserving earlier committed stages. The reviewed New Game handoff is a link; the editor never invokes canonical new-game itself. Setup failure keeps the review controls, receipt and original stack visible. The required published `setupFieldDescriptors` drive optional scalar/list/object controls, nested fixed properties, known map keys and canonical collection entry seeds. Calendar, factions/assets/reputation tiers, registered mod namespaces, attributes and skills support concrete add/remove controls; proposed values stay editable and authoritative. Removed values can be restored, while collection duplication preserves reviewed shapes. Descriptor labels/options use the native controls. No editor invents schema keys or hides these fields in a raw document editor. Fields, raw invalid control values, removed field values and reviewed collection shapes, chosen destination and captured descriptors survive refresh in session drafts. Repeating an unchanged reviewed commit uses the same exact request; changed drafts remain retained and require a fresh preview after an attempt has begun.

## Continuity, written outcomes and Play handoff

Intended facts identify author intent/approved plan and explicit knowledge scope. Observed facts and actual Play prose are read-only evidence; approval never turns a plan into an observation. Written history is chronological and links to stable outline nodes. Outcome review shows achieved/failed/open criteria, deviations and actual passages. Accept actual outcome is separate from reviewing/applying future outline changes. Unfavorable resolutions are valid and rejection of a future suggestion never erases actual history. Enclosing scene/chapter/part/story outcomes have their own evidence-backed reviews; First unfinished stops at an unresolved enclosing checkpoint, with an explicit preparation action if its review must be reconstructed.

The saved-game reconciliation panel distinguishes library/saved snapshots with Continue saved / Import copy / Review differences / Adopt reviewed library / Retry synchronization. There is no implicit merge. Saved snapshot projections have separate read-only buffers, so retained library edits cannot appear as pinned intentions. Continue saved prepares with the pinned snapshot revision. `requiresCopyBeforeWriting` and the actual `continuationPolicy` disable new Play preparation when the library is absent and expose an actionable Import saved story as a copy prerequisite. Normal authoring mutations stay blocked in a saved projection. Differences read the actual independent export when one exists; receipts/history are shown by selected authority, never merged across timelines. Pending synchronization visibly blocks subsequent writing. After copying preserved settled evidence, Prepare outcome review uses the canonical `execution/prepare-outcome` recovery route, including leaf receipts with detached jobs.

Review for Play compares approved leaf goals AND notes with private direction and criteria. Preparing freezes an actor-safe packet without starting gameplay. A named BroadcastChannel (`airpg.story-authoring.handoff`) locates an existing Play page, prefers its current owner and sends an acknowledged packet request; it does not navigate that page. A separate explicit Play link is also available. New Play URLs carry `storyPacket`; `StoryAuthoringRunner` retrieves the server packet, shows frozen actor direction and requires an explicit Start. Return to manual goal writing restores the prior local manual text. Packet Resume uses its saved identity, and every sub-scene boundary pauses for actual-outcome review. Canonical action/choice/ability/input/settlement flows stay in the existing browser runner. Keep Play open. Missing referenced characters/places expose a focused preparation preview with actual existing location/region choices, reviewed names/descriptions and explicit canonical commit. Stage counts/errors and exact same-request resume remain visible; preparation creates no fabricated identities, exits, teleports, or story outcomes. Narrative preconditions require explicit actual visible passage citations; referenced node work must be resolved or explicitly waived and cannot be bypassed by a citation. Draft entity descriptions/destinations/evidence choices survive closing, prerequisite navigation and refresh. Once committing, the exact reviewed envelope is retained in session and reconstructed from server `reviewedEntities`/`reviewedPrerequisites` for cross-session resume.

## Accessibility, errors and verification

Ctrl/Cmd+S saves; explicit shared Ctrl/Cmd+Enter submits edit forms; Alt+Up moves to the parent outside inputs. Play's Ctrl+Shift+P remains its pause shortcut. Approval, archive, setup commit and writing require explicit controls. Native disclosures, visible text statuses, live announcements, keyboard Move alternatives, focus trapping/restoration/Escape, touch-sized controls, wrapping long paths and reduced motion are supported. Phone actions stay in document flow to avoid hiding the software-keyboard field.

Persistent errors preserve the original message/stack/code, use shared page feedback and retain drafts/candidates/receipts. Missing endpoints and malformed responses are errors; the editor fabricates no successful server work.

Owned checks: `node --check` for editor/runner; Nunjucks content-render smoke; Sass compilation. Integration/browser/fixture tests belong to the isolated verification owner and must use the prescribed memory scope. Never restart or point tests at production. Deterministic browser checks cannot establish live-model literary quality.


Compile: `./node_modules/.bin/sass mods/story-authoring/public/scss/story-editor.scss mods/story-authoring/public/css/story-editor.css`.

## Generate missing fields

**New story** includes the same **Generate missing fields** action before a library story exists. It fills only blank title, premise, Main plot, tone/style, constraints and author notes, using the currently loaded game's read-only snapshot when available. Existing values, list entries, formatting and fields typed or cleared during generation are preserved. Generation appears in the shared prompt dock and has an in-form Cancel action; **Alt+G** opens its instructions dialog through the same enabled button. The form stays editable and **Create story** becomes available after the generation settles. Creating remains the only action that saves this draft as a library story.

New-story raw controls, edit counters and generation tracking survive refresh in session storage. Older retained creation drafts acquire an intentionally empty Main plot control. Unfinished pre-update generation is interrupted with an explicit regenerate notice and retained text; terminal or consumed tracking does not produce an interruption error. Closing or replacing the creation dialog cancels its owned active work and retains the draft. A launch response arriving after close is cancelled by its known request UUID and cannot change a reopened draft. Refresh can inspect a remembered transient job; an unavailable job surfaces an explicit error without discarding text or retrying automatically.

Every outline level has **Generate missing fields** above its form; **Alt+G** opens the same instructions dialog. It fills the current premise, part, chapter, scene or sub-scene form and the root's blank tone/style field. It uses unsaved form text as context, retains all nonblank values and nonempty lists, and leaves existing children intact. **Generate parts/chapters/scenes/sub-scenes** and **Regenerate** retain their separate structure/proposal roles.

Generation uses existing cancellable jobs and the shared prompt dock. The button shows **Generating missing fields…** while its section's job is active, and typing can continue. Successful fresh results fill the local draft only. Fields typed or cleared while work was pending are preserved through per-field edit counters; controls update in place to retain focus. Session buffers and per-job tracking survive refresh and prevent reapplying consumed results. Explicitly discarding a draft stops automatic application. Failed, cancelled and conflicted results never auto-merge, and saved-authority views remain read-only. A retained candidate can be inspected and **Fill remaining blanks** merges only blanks still matching its submitted draft. Retry generates from the current draft. **Save changes** and human approval remain separate.

## Shared dialog shell

All Stories custom dialogs adopt a root-contained native `<dialog>` through the portable `NativeDialog` owner, keeping editor query selectors and delegated actions intact while entering the browser's top layer. The page's glass container and higher-z-index header cannot clip or cover the modal title/close control. Native `::backdrop` supplies the shared dim/blur treatment. The header and optional footer remain fixed within the viewport-bounded shell; only the body scrolls. New story's footer submit button associates with its form through `form="story-new-form"`; shared submit handling includes external form-associated controls. Dialog content can be replaced while the shell is open without losing the original focus-return target. Content DOM is still constructed synchronously; an initial/reopened native lifetime waits for `whenClosed()` and checks a logical ticket so queued close events cannot close a newer form. Native cancellation delegates to the existing parent-restoration/close adapter, and native Tab containment replaces the duplicate document trap. The mod retains its creation cancellation, leave-review promises, submit-only disabling and retained draft behavior. A named shared ModalStack lock preserves existing body-scroll behavior without independent class toggles. PageFeedback error dialogs open later in the top layer and return focus to the preserved form.

## Instructions before manual generation

Manual **Generate missing fields**, child generation, **Regenerate**, Activity **Retry**, editable setup preview and actual-outcome preparation ask for **Generation instructions (optional)** before launching. The four-row instruction field comes first, above existing count or scope controls. Explicit operation-specific Generate confirms the request even when instructions are empty. Cancel, Close and Escape return without launching. Ctrl/Cmd+Enter submits the active generation form; Ctrl/Cmd+S and Alt+Up cannot save or navigate the underlying editor while this modal is active. YOLO steps and automatic execution outcome/revision analysis remain unattended.

Instructions apply only to the captured generation and are separate from permanent Author notes, existing filled values and the Main plot. Text is retained in session storage per story/node/operation (or the New story operation) across cancellation and request/provider failure. Successful explicit Create clears the New story instructions along with its draft so a different story does not inherit that guidance. Saved jobs and transient creation jobs retain their captured `feedback`; retries can submit new feedback. Actual-outcome instructions can guide evidence-supported emphasis, never change what happened or its citations.

When New story opens instructions, the shared `dialog(..., {suspendParent: true})` option retains the original body/footer nodes in document fragments. Closing instructions restores those same form elements, listeners, field edit counters, creation identity and invoking focus. No form HTML is recreated and no Create submission occurs. An accepted generation launch restores the parent form with its existing pending-job state; a failed launch keeps the instruction form open. Confirmation callbacks verify the captured story/section or creation identity. Shared PageFeedback errors stay above the active shell and restore focus to its form.

Manual outcome generation/preparation buttons are disabled while their outcome job is active. Existing pending suggestions expose Review actual outcome instead of offering another enclosing-generation action. The server rejects changed instructions against an active job or pending review with an explicit conflict and retains the instruction draft.

## Approve required sections and continue

**Review for Play** remains available when an otherwise playable unwritten branch needs human approval. The editor requests the scoped server preview and opens **Approve required story sections**, listing exact named paths and statuses. A library-approved section whose pinned game approval is older says **Approved in library · update game approval**. A scene queue lists the needed branches of its applicable unwritten sub-scenes. **Cancel** receives initial focus; Close/Escape/Cancel perform no approval or game mutation. Ctrl/Cmd+Enter explicitly submits **Approve all and continue**; Ctrl/Cmd+S and Alt+Up cannot act on the underlying editor while review is open.

Confirmation uses the captured story/section/scope, revision and server context fingerprint, disables duplicate submit and invokes only the focused approval recovery endpoint. It resumes the captured **Review for Play** attempt at actor-goal/notes review, or a captured **Prepare** attempt at packet preparation. It never starts writing. Changed selection/local draft/context rejects the old consent; the list must be reviewed again. Missing library, saved-only editing authority, pending actual synchronization, unresolved outcomes, missing required entities/prerequisites and real content/timeline differences keep their existing guards. Genuine saved/library differences open the existing explicit timeline comparison instead of approval recovery.

Historical form-fill jobs with `STORY_CANDIDATE_STALE` retain their original inline Activity error/stack and candidate without reopening a global error modal on every Activity render. Current owned fill consumption and direct merge still surface failures; freshness validation is unchanged and approvals never revive a stale generated candidate.
